# .NET UI and Client Extraction

.NET UI and client extraction is Archon's static-analysis path for source artifacts that describe user-facing .NET applications. The current implementation includes a unified WP011 API stage that coordinates a Blazor route/component/interaction slice, a server-rendered Razor slice for Razor Pages and MVC Razor views, a Windows Forms desktop slice for legacy forms, user controls, designer partials, resources, events, and bindings, a WPF desktop XAML slice for application definitions, windows, pages, user controls, resource dictionaries, styles, templates, bindings, commands, routed events, navigation, view models, and code-behind dependencies, a WinUI desktop XAML slice for Windows App SDK projects, package manifests, application startup, windows, pages, user controls, resources, styles, bindings, commands, navigation frames, view models, and code-behind dependencies, a .NET MAUI cross-platform XAML slice for single-project MAUI applications, Shell layouts, Shell routes, pages, content views, handler registrations, platform heads, resources, styles, bindings, commands, navigation, view models, and code-behind dependencies, and an Avalonia AXAML slice for cross-platform desktop applications, windows, user controls, style resources, bindings, commands, view locators, ReactiveUI relationships, navigation, view models, and code-behind dependencies. It discovers repository-contained `.razor`, `.cshtml`, `.xaml`, `.axaml`, `.cs`, `.vb`, `.resx`, `.appxmanifest`, `.csproj`, and `.vbproj` evidence where relevant, associates artifacts with their nearest project, reads project metadata where needed, and emits graph facts through the same snapshot accumulator used by repository, semantic, configuration, runtime, data-access, and external-integration extraction.

UI extraction is deliberately static. It does not render Razor components or views, start the target application, execute MVC routing, evaluate tag helpers, load Windows Forms designers, instantiate controls, load WPF, WinUI, MAUI XAML, or Avalonia AXAML, start WPF or WinUI dispatchers, start MAUI platform applications, start Avalonia desktop lifetimes, evaluate resource lookup, start message loops, launch a browser, contact APIs, open database connections, run the Aspire AppHost, invoke MCP tools, write directly to Neo4j, or infer behavior from live UI state.

## Current Blazor slice

A **Blazor component** is a `.razor` artifact that can combine markup, Razor directives, and a C# `@code` block. In the current slice, Archon treats each discovered source `.razor` file as a `UiComponent` node. Discovery is repository-root based but excludes common build output paths such as `bin` and `obj`, because generated or copied artifacts would duplicate source facts and introduce unstable evidence paths.

A **Blazor route** is a literal `@page` directive in a component, such as `@page "/orders/{id:int}"`. Archon emits a `UiRoute` node for each detected route and a `DECLARES_UI_ROUTE` relationship from the component to the route. Route parameters are recorded as metadata when they are visible in the literal template. If a `@page` directive is present but malformed or missing a literal route template, extraction keeps the partial fact as an explicit unknown rather than dropping the file. That means the snapshot can contain a low-confidence route node with an unknown reason and a warning that points contributors back to the source artifact.

A **Blazor layout** is a component selected through an `@layout` directive. The current slice emits a `UiLayout` node for the layout name and a `USES_LAYOUT` relationship from the component to that layout. This first slice does not require semantic type binding for layouts; it records the deterministic type token visible in markup and keeps the relationship evidence attached to the component artifact.

A Blazor `@inject` directive is modeled conservatively as a dependency/configuration-style fact because the existing graph vocabulary already has `ConfigurationKey`, `USES_CONFIG`, and `DEPENDS_ON` relationships that can carry a deterministic dependency name. For example, `@inject HttpClient Http` contributes a `ConfigurationKey` node named `HttpClient`, a `USES_CONFIG` relationship from the component to that node, and a `DEPENDS_ON` relationship from the component to that same dependency node. Later UI/client slices can refine service and API correlations without changing the component's stable identity.

The extractor also records metadata for `[Parameter]`, `[CascadingParameter]`, `EventCallback<T>`, `RenderFragment`, `[Authorize]`, and `AuthorizeView` patterns when simple static evidence is present. Parameters, render fragment names, render modes, and authorization values are stored as metadata on the component node rather than as new framework-specific node kinds. This keeps Blazor-specific details queryable while preserving the shared graph model: framework-specific concepts are metadata values on generic graph facts unless the domain model already has a controlled node kind or edge kind for that concept.

## Blazor interaction and dependency facts

The current Blazor slice now includes a static interaction pass. A **component composition** relationship is a `USES_COMPONENT` edge from the component being analyzed to another component-looking tag in the same `.razor` file. The detector uses the Blazor convention that component tags begin with an uppercase letter, then excludes built-in form and validation controls so those controls are represented as controls rather than project components. Repeated child tags collapse through deterministic stable keys, so two `<FeatureCard />` tags in the same component describe one component dependency unless their static identity changes. `DynamicComponent` is intentionally different: its target type is supplied from runtime state, so Archon emits a low-confidence unknown component usage and a warning instead of guessing which component might render.

UI events and callbacks are represented through command-style facts. A DOM event such as `@onclick="SaveAsync"` or a component callback such as `OnValidSubmit="SaveAsync"` contributes a `Command` node named after the visible handler token, a `HANDLES_UI_EVENT` relationship from the component to the command, and a `USES_COMMAND` relationship that makes the command dependency explicit. This is still static markup analysis. The extractor does not bind the handler through the Razor compiler, does not execute lambdas, and does not prove that an event will fire at runtime. It records the event or callback shape visible in source so impact analysis can find UI code paths that a contributor should inspect when a handler changes.

Forms and validation components are represented as `UiControl` nodes with `USES_CONTROL` relationships. This includes `EditForm`, `DataAnnotationsValidator`, `ValidationSummary`, `ValidationMessage`, and common input controls. These controls describe user-input and validation structure, but they do not imply that Archon has evaluated validation attributes, submitted a form, created an `EditContext`, or observed browser behavior. Render modes are captured from literal `@rendermode` directives as component metadata such as `InteractiveServer`. When the render mode is computed from an expression, the component fact carries explicit unknown state and the snapshot receives a warning because runtime state decides the hosting behavior.

Dependency and outbound-call correlation remains conservative. If a component injects `HttpClient`, direct calls such as `Http.GetFromJsonAsync<object>("https://api.example.test/items")` contribute an `ExternalService` node and a `CALLS_API` relationship. If the first argument is computed from a variable or expression, Archon emits an unknown external-service/API target instead of inventing a URL. If a component injects `IConfiguration`, literal indexer access such as `Configuration["Services:Catalog:BaseUrl"]` contributes a `ConfigurationKey` node and a `USES_CONFIG` relationship. Computed keys produce explicit unknown configuration facts. These correlations can coexist with prior configuration, dependency-injection, runtime, data-access, and integration facts in the same assembled snapshot because they reuse the shared graph vocabulary and accumulator rather than creating a Blazor-only model.

## Razor Pages and MVC Razor views

A **Razor Page** is a server-rendered `.cshtml` file under a `Pages` folder. It can declare an `@page` directive, a page model through `@model`, layout selection, form posts, anchor tag helpers, partials, view components, authorization metadata, and handler methods in a companion `.cshtml.cs` file. Archon records Razor Pages as `UiPage` nodes with `RazorPages` as the `uiFramework` metadata value. Literal or conventional route templates become `UiRoute` nodes with `DECLARES_UI_ROUTE` relationships from the page. Companion page-model types become `ViewModel` nodes connected through `USES_VIEW_MODEL`, and visible handler methods such as `OnPostSave` become `Method` nodes connected through `HANDLES_UI_EVENT` relationships. A form with `asp-page-handler="Save"`, for example, records the event metadata value `post:Save` so contributors can query which page handles a submitted interaction without Archon submitting the form or executing the handler.

An **MVC Razor view** is a server-rendered `.cshtml` file under a `Views` folder. Archon records conventional views as `UiView` nodes with `MvcRazor` as the `uiFramework` metadata value. When a path such as `Views/Orders/Details.cshtml` and a repository-contained `OrdersController` source file with a `Details` action are both present, the extractor emits deterministic `Controller` and `Method` facts and links the view to the action with a `DEPENDS_ON` relationship. This correlation is intentionally conservative. It uses conventional static source evidence only; it does not execute MVC routing, interpret custom view engines, evaluate action selection filters, or infer a controller/action relationship from a dynamic view name.

Server-rendered Razor composition uses the same graph vocabulary as Blazor. Literal `Layout = "_Layout"` assignments or inherited `_ViewStart.cshtml` layouts become `UiLayout` nodes and `USES_LAYOUT` relationships. Partial tags such as `<partial name="_ProductSummary" />`, `Html.PartialAsync("_OrderRow")`, view-component tags such as `<vc:cart-summary />`, and `Component.InvokeAsync("CartSummary")` become `UiComponent` nodes and `USES_COMPONENT` relationships. Repeated static partial usages deduplicate by stable key so repeated markup describes one architectural component dependency unless the static identity changes. Forms become `UiControl` nodes with `USES_CONTROL` relationships, and anchor tag helpers with literal `asp-page`, `asp-controller`, or `asp-action` targets become `NAVIGATES_TO` relationships to route-shaped nodes.

The Razor slice also records context artifacts without treating them as pages or views. `_ViewImports.cshtml` contributes nearest visible tag-helper metadata, such as `Microsoft.AspNetCore.Mvc.TagHelpers`, to analyzed pages and views. `_ViewStart.cshtml` contributes inherited layout context when a child artifact does not declare an explicit layout. These context artifacts are read as static evidence that helps explain the analyzed artifact; they are not rendered, compiled, or executed.

Dynamic server-rendered Razor shapes become explicit unknowns. A route such as `@page DynamicRoute`, a partial name such as `<partial name="@Model.PartialName" />`, a layout such as `Layout = ViewBag.LayoutName`, or an anchor target such as `asp-controller="@Model.Controller"` depends on runtime state. Archon records warnings plus low-confidence unknown graph facts with reasons such as `Razor route template is computed from runtime state`, `Razor partial target is computed from runtime state`, `Razor layout target is computed from runtime state`, and `Razor navigation target is computed from runtime state`. An unresolved Razor Page model that appears as an unqualified type without a companion `.cshtml.cs` file is also preserved as an explicit unknown rather than being silently dropped.

## Windows Forms static UI extraction

A **Windows Forms application** is a desktop .NET application built around `System.Windows.Forms` projects, forms, controls, resources, event handlers, and a message loop commonly started with `Application.Run(new MainForm())`. Archon detects Windows Forms projects from static project metadata such as `UseWindowsForms`, Windows target frameworks, `StartupObject`, Windows Forms references, package/reference hints, and repository source symbols. This classification does not require the Windows desktop workload to be installed for extraction, because the extractor reads local project and source text rather than compiling or loading the target application.

A **form** is modeled as a `UiView` because it represents a user-facing screen, while a Windows Forms **user control** is modeled as a `UiComponent` because it is a reusable UI part hosted by a form or another control. Designer partials such as `MainForm.Designer.cs` or `MainForm.Designer.vb` are correlated to the owning form or user control by partial type name. The designer file is not executed. Instead, Archon reads field declarations, `InitializeComponent` assignments, `Controls.Add(...)` calls, and `DataBindings.Add(...)` calls as static evidence. This produces `UiControl` facts for controls such as buttons, panels, text boxes, and labels; `USES_CONTROL` relationships for form-to-control and control-to-child-control hierarchy; and `Binding` facts connected through `BINDS_TO` when a binding path is literal in designer source.

Windows Forms `.resx` files contribute `UiResource` facts when resource keys are visible. For example, `$this.Icon` in `MainForm.resx` becomes a resource node linked from the form with `USES_UI_RESOURCE`. Resource values and code snippets pass through the shared UI redaction boundary before evidence previews are stored. That boundary now also recognizes common connection-string password segments, so source such as `Password=...` in a UI-adjacent snippet is replaced with `[REDACTED]` before it can appear in evidence.

Event wiring is represented with command-style facts so desktop interactions participate in the same graph vocabulary as Blazor and Razor interactions. A C# subscription such as `saveButton.Click += SaveButton_Click`, a designer-generated `new EventHandler(this.SaveButton_Click)` subscription, or a VB.NET `Handles saveButton.Click` clause contributes a `Command` node and `HANDLES_UI_EVENT` plus `USES_COMMAND` relationships from the form or user control. Inline lambdas, anonymous delegates, factory-created controls, and other runtime-generated UI shapes are not guessed. Archon records a warning and an explicit unknown fact such as `Windows Forms control is created dynamically and cannot be fully resolved statically` or `Windows Forms event handler is wired through runtime-generated code` so contributors can query the static-analysis gap.

The current slice also performs conservative code-behind dependency recognition. Direct service-looking type usage such as `OrderService` contributes a `Type` node and a `DEPENDS_ON` relationship from the form or control. Data-access-looking source or package evidence such as `System.Data.SqlClient` or `SqlConnection` contributes an `ExternalService` node and `CALLS_API`/`DEPENDS_ON` relationships. These relationships are intentionally static correlation hints. They do not prove runtime reachability, execute handlers, open database connections, or replace the richer WP009 data-access slice; instead, they make legacy desktop screens visible in the same assembled snapshot where WP009 can contribute deeper database facts.

## WPF XAML extraction

A **WPF application** is a Windows Presentation Foundation desktop application whose UI is commonly declared in XAML files and connected to C# or VB.NET code-behind. Archon detects WPF projects from static evidence such as `UseWPF`, `PresentationFramework` references, Windows target frameworks, `ApplicationDefinition` project items, `.xaml` artifacts, startup objects, and source symbols. This detection is intentionally text-based. The extractor does not evaluate MSBuild, require the Windows desktop workload, instantiate `Application`, or load any XAML into WPF runtime objects.

WPF has a larger declarative surface than Windows Forms, so the slice separates the concepts that contributors usually need to query. An application definition such as `App.xaml` contributes a `UiApplication` fact with startup metadata when `StartupUri` or startup-object evidence is visible. A **window** is modeled as a `UiView`, because it is a user-facing screen; a WPF **page** is modeled as a `UiPage`, because it is a navigable surface; and a WPF **user control** is modeled as a `UiComponent`, because it is a reusable UI part hosted by another view. Resource dictionaries and keyed resource entries contribute `UiResource` facts, while styles and templates contribute `UiStyle` facts with resource or style keys in metadata. These classifications use shared graph node kinds rather than WPF-specific node kinds, so downstream graph queries can compare desktop, web, and cross-platform UI facts without special framework branches.

WPF controls and composition are extracted from static XAML markup. A named element such as `<Button x:Name="SaveButton" ... />` contributes a `UiControl` node and a `USES_CONTROL` relationship from the owning window, page, or user control. A project-local element that uses a `clr-namespace:` mapping, such as `<local:CustomerSummary />`, contributes a component-style usage relationship because it represents a reusable application-defined UI part. Bindings are represented as `Binding` nodes connected through `BINDS_TO` when a path such as `CustomerName` is visible in `{Binding CustomerName}` or `{Binding Path=CustomerName}`. A bare `{Binding}` expression is different: it depends on the runtime data context shape, so Archon records a low-confidence unknown binding fact instead of inventing a path.

Commands, routed events, and navigation follow the same evidence-first rule. A command binding such as `Command="{Binding SaveCommand}"` contributes a `Command` node connected with `USES_COMMAND`. A routed event attribute such as `Click="SaveButton_Click"` contributes a command-style handler node and a `HANDLES_UI_EVENT` relationship with `eventName` metadata. Static navigation through `Frame Source="DetailsPage.xaml"` contributes a `NAVIGATES_TO` relationship to a page-shaped target. Computed navigation through a binding or markup extension is recorded as an explicit unknown because static extraction cannot know which page will be selected at runtime.

View-model correlation is deliberately conservative. A direct XAML data context declaration such as `<Window.DataContext><vm:MainViewModel /></Window.DataContext>` becomes a high-confidence `ViewModel` node linked with `USES_VIEW_MODEL`. If no direct data context is present, the extractor may look for a convention-shaped source type such as `MainViewModel`; when that type is absent, it emits a convention-only unknown view-model fact. This makes architectural gaps visible without pretending that Archon has executed a dependency-injection container, view-model locator, or runtime data-template selector.

The current WPF slice also correlates code-behind service and data-access hints. Service-looking type usage such as `OrderService` contributes a `Type` node and a `DEPENDS_ON` relationship from the owning UI artifact. Data-access-looking code or package evidence such as `Microsoft.Data.SqlClient` or `SqlConnection` contributes an `ExternalService` node and a `CALLS_API` relationship. This correlation is a static hint that a UI screen can reach service or data-access paths; it does not execute handlers, open connections, or replace the specialized data-access extraction slice.

Dynamic WPF features are represented as first-class unknowns. `DynamicResource`, unresolved binding paths, runtime template selection through `ContentTemplateSelector`, computed navigation, and convention-only view models without source evidence all produce warnings and low-confidence graph facts with explicit unknown state. A contributor reading a snapshot should treat these unknowns as useful worklist items: they identify source locations where WPF intent exists but the target depends on runtime state, resource lookup, template selection, or convention wiring that static analysis cannot safely resolve.

## WinUI XAML and packaging extraction

A **WinUI application** is a modern Windows desktop application built with the Windows App SDK and `Microsoft.UI.Xaml`. It usually declares UI in XAML, starts from an `Application` subclass, creates an initial window in `OnLaunched`, and may be packaged as MSIX through a package manifest such as `Package.appxmanifest`. Archon detects WinUI projects from static evidence such as `UseWinUI`, `Microsoft.WindowsAppSDK` package references, `Microsoft.UI.Xaml` source references, Windows target frameworks, `.xaml` artifacts, startup objects, and package/application manifest metadata. The extractor does not evaluate MSBuild, install the Windows App SDK, load the target application, or validate the package with Windows tooling.

WinUI graph facts use the same shared UI vocabulary as the other WP011 slices. An application definition or package manifest contributes a `UiApplication` fact with `uiFramework` set to `WinUI`, `platformHead` set to `Windows`, and safe package metadata such as package identity, display name, publisher, version, and package type when those values are statically available. A WinUI **window** is modeled as a `UiView`, a **page** as a `UiPage`, and a **user control** as a `UiComponent`. Resource dictionaries and keyed resources contribute `UiResource` facts, while styles and templates contribute `UiStyle` facts. Framework-specific details stay in metadata so graph consumers can query WinUI and WPF side by side without needing new WinUI-only node kinds.

WinUI markup extraction reads named controls, project-local component tags, bindings, commands, routed events, and resources from source XAML. A named element such as `<Button x:Name="SaveButton" ... />` contributes a `UiControl` node and a `USES_CONTROL` relationship. A project-local element declared through a WinUI `using:` namespace, such as `<local:CustomerSummary />`, is treated as component usage because it identifies an application-defined UI part. Binding expressions such as `{Binding CustomerName}` and `{x:Bind CustomerName}` become `Binding` facts when a static path is visible. Bare bindings, theme resources, dynamic resources, and runtime template selectors become explicit unknown facts because the final target depends on data context, resource lookup, or runtime template-selection logic.

Navigation is split between markup and code-behind evidence. Static frame navigation such as `RootFrame.Navigate(typeof(DetailsPage))` becomes a `NAVIGATES_TO` relationship to a page-shaped target. A call such as `RootFrame.Navigate(Type.GetType(RuntimePageName))` becomes an unknown navigation fact instead of a guessed page because the target type is computed at runtime. Routed events and commands follow the same command-style vocabulary as WPF: a `Click="SaveButton_Click"` handler produces a command node and `HANDLES_UI_EVENT`, while `Command="{Binding SaveCommand}"` produces a `Command` node connected through `USES_COMMAND`.

Packaging metadata is intentionally narrow and safe. Archon records package identity fields that are useful for architecture analysis, such as package name, display name, publisher, version, and package type. It does not store credentials, validate signing certificates, evaluate store submission configuration, or infer deployment behavior from the manifest. If a WinUI project declares packaging behavior but no parseable package identity is available, the extractor emits an explicit unknown packaging fact so contributors can distinguish an unpackaged or ambiguous project from one with known package metadata.

The current WinUI slice also correlates code-behind service and data-access hints in the same conservative way as WPF. Service-looking type usage contributes a `Type` node and `DEPENDS_ON` relationship, while data-access-looking source or packages such as `Microsoft.Data.SqlClient` contribute `ExternalService` and `CALLS_API` facts. These are static correlation hints only; they do not execute handlers, start windows, open connections, or replace the specialized data-access extraction slice.

## .NET MAUI Shell and platform-head extraction

A **.NET MAUI application** is a cross-platform .NET client application that commonly uses one project to target multiple platform heads such as Android, iOS, Mac Catalyst, Windows, and sometimes Tizen. A **platform head** is the platform-specific entry-point and asset surface that lets the shared application run on one target platform. In a MAUI project, platform heads are usually visible through target frameworks such as `net10.0-android` or `net10.0-ios` and through conventional `Platforms/{PlatformName}` folders. Archon records those platform heads as metadata on MAUI project and UI application facts so contributors can query whether a page or Shell route belongs to a cross-platform app without starting any target platform runtime.

Archon detects MAUI projects from static evidence such as `UseMaui`, `Microsoft.Maui.Controls` package references, `MauiXaml` project items, `MauiProgram` source, MAUI target-framework suffixes, repository XAML files, and source references to MAUI types. The extractor does not evaluate MSBuild, install MAUI workloads, invoke platform toolchains, start Android or iOS simulators, load XAML into MAUI controls, or validate platform manifests. This matters because MAUI repositories often require platform SDKs that are unavailable in server or CI contexts; the Archon slice is intentionally text-based so architecture facts remain available from repository source alone.

MAUI graph facts use the same shared UI vocabulary as the other WP011 slices. The application project contributes a `UiApplication` fact with `uiFramework` set to `Maui`, `hostingModel` set to `Hybrid`, target frameworks, package evidence, and normalized `platformHead` metadata. A MAUI **Shell** file such as `AppShell.xaml` is modeled as a `UiLayout` because it organizes the navigable structure of the application. A `ContentPage`, `TabbedPage`, or `NavigationPage` is modeled as a `UiPage`, while a `ContentView` or other reusable view artifact is modeled as a `UiComponent`. Resource dictionaries and keyed resource entries contribute `UiResource` facts, while styles and templates contribute `UiStyle` facts. Framework-specific details stay in metadata, not in MAUI-only graph node kinds.

Shell routing is the most important MAUI-specific navigation surface in the current slice. Static markup routes such as `Route="main"` or attached page routes such as `Shell.Route="details"` become `UiRoute` facts connected with `DECLARES_UI_ROUTE`. Static source registrations such as `Routing.RegisterRoute("details", typeof(DetailsPage))` are also recorded as route facts. A navigation call such as `Shell.Current.GoToAsync("details")` becomes a `NAVIGATES_TO` relationship to a route-shaped target. If the route or navigation target is computed from a binding, variable, method call, or other runtime expression, Archon emits an explicit unknown route or navigation fact instead of inventing a target.

MAUI controls, bindings, commands, events, and handler registrations follow the same evidence-first model used by WPF and WinUI. A named element such as `<Button x:Name="SaveButton" ... />` contributes a `UiControl` node and `USES_CONTROL` relationship. A project-local `clr-namespace:` element such as `<views:CustomerCard />` contributes component usage because it refers to an application-defined reusable view. Binding expressions such as `{Binding CustomerName}` become `Binding` facts when the path is visible, while bare `{Binding}` expressions become explicit unknowns. `Command="{Binding SaveCommand}"` contributes a `Command` fact, and event attributes such as `Clicked="SaveButton_Clicked"` contribute command-style handler facts through `HANDLES_UI_EVENT`. `ConfigureMauiHandlers` registrations are represented as command-style handler facts with control and handler metadata because the current graph vocabulary does not define a separate handler node kind.

View-model correlation is deliberately conservative. A direct XAML binding context such as `<ContentPage.BindingContext><vm:MainViewModel /></ContentPage.BindingContext>` becomes a high-confidence `ViewModel` node connected with `USES_VIEW_MODEL`. If no direct binding context is visible, the extractor may look for a convention-shaped source type, such as `MainViewModel` for `MainPage`; when that type is absent, the snapshot receives a convention-only unknown view-model fact. Service-looking type usage and data-access-looking code or packages are correlated as static hints through `Type`, `ExternalService`, `DEPENDS_ON`, and `CALLS_API` facts, but the extractor does not execute handlers, build a MAUI dependency-injection container, open database connections, or replace the specialized data-access slice.

## Avalonia AXAML, view-locator, and ReactiveUI extraction

An **Avalonia application** is a cross-platform .NET client application whose UI is commonly declared in Avalonia XAML files with the `.axaml` extension. Avalonia AXAML is XML-like markup that uses the `https://github.com/avaloniaui` namespace, application definitions such as `App.axaml`, view artifacts such as `Window` and `UserControl`, and style selectors that are closer to CSS than WPF-style keyed styles. Archon detects Avalonia projects from static evidence such as `Avalonia` package references, `Avalonia.Desktop`, `Avalonia.ReactiveUI`, `App.axaml`, repository-contained `.axaml` files, startup source such as `StartWithClassicDesktopLifetime`, and source symbols such as `ReactiveWindow` or `ReactiveUserControl`. The extractor does not evaluate MSBuild, load Avalonia assemblies, instantiate controls, start a desktop lifetime, open windows, evaluate resource lookup, or require the target application's Avalonia packages to be executable on the analysis machine.

Avalonia graph facts use the same shared UI vocabulary as the other WP011 slices. `App.axaml` contributes `UiApplication` evidence, a `Window` artifact is modeled as a `UiView`, and a `UserControl` artifact is modeled as a `UiComponent`. A `Styles` or style include artifact contributes `UiStyle` facts, while keyed resources such as brushes contribute `UiResource` facts. A named element such as `<Button x:Name="SaveButton" ... />` contributes a `UiControl` node and a `USES_CONTROL` relationship. A project-local element declared through an Avalonia `using:` namespace, such as `<views:CustomerCard />`, contributes component usage because it identifies an application-defined reusable view. These classifications intentionally remain generic graph node kinds with `uiFramework` set to `Avalonia`, so downstream queries can compare Avalonia windows, WPF windows, WinUI windows, MAUI pages, and Windows Forms forms without separate framework-only vocabularies.

Bindings, commands, events, and navigation follow the evidence-first rule. A binding such as `{Binding CustomerName}`, `{CompiledBinding CustomerName}`, or `{ReflectionBinding CustomerName}` becomes a `Binding` fact when a static path is visible. A bare `{Binding}` expression becomes an explicit unknown because its target depends on the runtime `DataContext`. `Command="{Binding SaveCommand}"` contributes a `Command` node connected through `USES_COMMAND`, and event attributes such as `Click="SaveButton_Click"` contribute command-style handler facts through `HANDLES_UI_EVENT`. Static ReactiveUI navigation such as `Router.Navigate.Execute(new CustomerCardViewModel())` contributes a `NAVIGATES_TO` relationship to a view-model-shaped target, while runtime navigation expressions become explicit unknowns.

Avalonia view-model correlation uses direct markup evidence before conventions. An `x:DataType="vm:MainWindowViewModel"` declaration is high-confidence evidence because Avalonia compiled bindings use it to describe the view model shape. Design-time data contexts can also identify likely view models with medium confidence. A **view locator** is a source component, commonly implementing `IDataTemplate`, that maps view-model objects to view controls. When the locator has visible static switch arms such as `MainWindowViewModel => new MainWindow()`, Archon records a `ViewModel` fact and links it to the target view/component. When a locator uses reflection or naming conventions such as replacing `ViewModel` with `View`, the mapping is recorded as a low-confidence unknown rather than guessed. ReactiveUI is treated similarly: generic views such as `ReactiveWindow<MainWindowViewModel>` or `ReactiveUserControl<CustomerCardViewModel>` provide direct view-model relationships, while non-generic `ReactiveWindow` or runtime-only ReactiveUI wiring is preserved as an ambiguous unknown. Service-looking type usage and data-access-looking code or packages are correlated as static hints through `Type`, `ExternalService`, `DEPENDS_ON`, and `CALLS_API` facts, but the extractor does not execute handlers, instantiate a view locator, create a ReactiveUI router, or open database connections.

## Stable keys and metadata

UI stable keys are deterministic and repository-relative. A UI application key combines the owning project key, the UI framework, target framework, and hosting or startup identity. A Blazor component key combines the owning project key, `Blazor`, the repository-relative `.razor` path, and the component name inferred from the file name. A Razor Pages or MVC Razor artifact key combines the owning project key, the framework value (`RazorPages` or `MvcRazor`), the artifact kind, the repository-relative `.cshtml` path, and the page or view name. A Windows Forms form, user control, designer control, resource, event command, binding, dependency, and data-access relationship key combines the owning project key, `WinForms`, the repository-relative source/designer/resource path, the owning type name, and the visible control, resource, event, binding, service, or package identity. A WPF application, window, page, user control, resource dictionary, keyed resource, style, template, named control, binding, command, routed-event handler, navigation target, view model, service usage, and data-access usage key combines the owning project key, `Wpf`, the repository-relative XAML or code-behind path, the artifact kind, and the visible type/name/key/path identity. A WinUI application, package manifest, window, page, user control, resource dictionary, keyed resource, style, named control, binding, command, routed-event handler, navigation target, view model, service usage, and data-access usage key combines the owning project key, `WinUI`, the repository-relative XAML, source, or manifest path, the artifact kind, and the visible type/name/key/path or package identity. A MAUI application, Shell layout, page, content view, route, handler, platform-head metadata value, resource dictionary, keyed resource, style, named control, binding, command, event handler, navigation target, view model, service usage, and data-access usage key combines the owning project key, `Maui`, the repository-relative XAML or source path, the artifact kind, and the visible type/name/key/path, route, handler, or package identity. An Avalonia application, window, user control, styles artifact, keyed resource, style selector, named control, binding, command, event handler, view-locator mapping, ReactiveUI view-model relationship, navigation target, service usage, and data-access usage key combines the owning project key, `Avalonia`, the repository-relative AXAML or source path, the artifact kind, and the visible type/name/key/path, selector, view-model, view, or package identity. Route, layout, partial, view-component, handler, controller/action, dependency, evidence, and relationship keys include the same project or source-artifact anchors plus the directive or relationship identity needed to avoid accidental duplicates.

The important rule is that no UI key includes a developer machine root, database ID, enumeration order, browser state, rendered output, or live service result. A component under `src/Sample.Client/Pages/Index.razor` should keep the same logical identity when analyzed on a Windows workstation, Linux CI agent, or another developer's clone.

UI metadata uses stable lower-camel-case names. Current UI metadata includes values such as `uiFramework`, `uiArtifactKind`, `projectKey`, `targetFramework`, `sourcePath`, `componentName`, `pageName`, `viewName`, `windowName`, `startupForm`, `startupUri`, `startupObject`, `routeTemplate`, `routeParameter`, `layoutName`, `hostingModel`, `platformHead`, `renderMode`, `renderFragment`, `eventName`, `commandName`, `methodName`, `controllerName`, `controlName`, `controlType`, `controlProperty`, `parentControlName`, `resourceKey`, `styleKey`, `bindingPath`, `navigationTarget`, `configurationKey`, `detectionMode`, `confidenceReason`, `authorizationPolicy`, `componentParameter`, `viewModelType`, `tagHelper`, `packageIdentity`, `packageDisplayName`, `packagePublisher`, `packageType`, and `packageVersion`. These fields explain UI-specific details without hiding normalized graph concepts such as node kind, relationship kind, confidence, unknown state, evidence path, line span, or stable key inside metadata. MAUI platform heads are currently recorded as a normalized comma-separated `platformHead` value, such as `Android,iOS,MacCatalyst,Windows`, because each head describes the same shared UI application rather than a separate graph node. `unknownReason` remains a normalized graph property and is intentionally carried by unknown state, not metadata.

## Evidence, confidence, unknowns, and redaction

UI extraction follows Archon's evidence-first model. Evidence records use repository-relative file paths, one-based line spans when the extractor can identify a directive line, snippet hashes, and redacted snippet previews. A snippet hash is a deterministic digest of the redacted snippet. It lets snapshots compare evidence without storing large or sensitive source content. A snippet preview is a short human-readable aid that helps contributors find the source line; it is not a substitute for the repository file.

Redaction replaces secret-like assignment values with `[REDACTED]` before previews are stored. The current UI helper recognizes common assignment names such as password, secret, token, API key, and connection string. This is a defensive evidence boundary: UI markup can contain literal attributes or sample values, and those values should not become graph output merely because they appeared near a route, injected service, or parameter.

Confidence and unknown state are explicit. Literal directives, direct designer fields, direct XAML or AXAML names, direct resource keys, direct data-context, binding-context, or `x:DataType` declarations, static binding paths, static navigation targets, static Shell routes, package manifest identities, platform-head evidence, and direct event handler names normally use high confidence. Static relationships such as child component usage, partial usage, view-component usage, event callback usage, Windows Forms control hierarchy, WPF named-control usage, WinUI named-control usage, MAUI named-control usage, Avalonia named-control usage, designer data bindings, WPF binding paths, WinUI binding paths, MAUI binding paths, Avalonia binding paths, MVC conventional action correlation, MAUI handler registrations, Avalonia view-locator mappings, generic ReactiveUI view-model relationships, service-looking type usage, and literal HTTP or data-access targets may use medium confidence when the source evidence is syntactic rather than compiler-bound. Partial or malformed directives, dynamic components, computed Razor Page routes, computed Razor layouts, dynamic partials, dynamic navigation targets, computed render modes, computed API targets, computed configuration keys, factory-created Windows Forms controls, inline Windows Forms event handlers, unresolved Windows Forms startup forms, WPF dynamic resources, unresolved WPF binding paths, runtime WPF template selection, computed WPF navigation, convention-only WPF view models, WinUI theme or dynamic resources, unresolved WinUI binding paths, runtime WinUI template selection, runtime WinUI navigation, ambiguous WinUI packaging, convention-only WinUI view models, MAUI dynamic resources, unresolved MAUI binding paths, runtime MAUI template selection, computed MAUI Shell routes, runtime MAUI navigation, ambiguous MAUI platform heads, convention-only MAUI view models, Avalonia dynamic resources or styles, unresolved Avalonia binding paths, convention/reflection-only view locators, ambiguous non-generic ReactiveUI relationships, runtime Avalonia navigation, and convention-only Avalonia view models use lower confidence and explicit unknown reasons. This behavior is intentional. Static UI extraction should prefer a truthful partial fact over a guessed route, service, component, API, controller, action, view, layout, control, binding source, resource, style, template, package identity, platform head, view model, view locator, ReactiveUI relationship, or configuration target. Unknowns are queryable architecture information because they identify places where the source code contains UI intent but the extractor cannot safely determine the complete target.

## API workflow boundary

The API extraction module registers one pipeline-visible WP011 stage after the WP010 external integration stage. That unified stage identifier is `wp011-ui-client`. A **unified UI/client stage** is an orchestration adapter that runs the framework-specific adapters in a fixed deterministic order: Blazor, Razor Pages/MVC Razor, Windows Forms, WPF, WinUI, .NET MAUI, and Avalonia. The framework adapters still have stable internal identifiers such as `wp011-blazor-route-component`, `wp011-razor-page-view`, `wp011-winforms-static-ui`, `wp011-wpf-xaml`, `wp011-winui-xaml`, `wp011-maui-xaml`, and `wp011-avalonia-axaml`, but API pipeline progress and stage ordering now expose the single `wp011-ui-client` work unit. Each adapter constructs a snapshot-scoped extraction request, runs its extractor project, and merges the returned snapshot into the shared accumulator.

The shared accumulator is the cross-framework deduplication boundary. Nodes, relationships, and evidence records are stable-keyed, so repeated runs of the same framework adapter or overlapping markup/source observations replace the same logical fact rather than creating duplicate graph output. Warning and error diagnostics remain ordered streams because repeated diagnostic text can explain repeated source locations. This means a mixed repository can produce Blazor, Razor Pages, Windows Forms, WPF, WinUI, MAUI, and Avalonia facts in one response-ready snapshot, while downstream API, MCP, rule, metric, diff, and markdown work packages can query by project, framework, route, component, page, view, control, binding, command, view model, navigation target, configuration key, API dependency, service dependency, or data-access dependency without knowing which adapter emitted the fact.

The unified stage does not change the API route contract. `POST /extractions` still accepts explicit repository and solution inputs, records an asynchronous run, and executes pipeline stages in order. The Blazor, Razor, Windows Forms, WPF, WinUI, MAUI, and Avalonia adapters search the accepted repository root for their UI artifacts, while the project and semantic stages still use the explicit submitted solution list for their own boundaries. The result is one assembled snapshot that can contain project, source-symbol, configuration, runtime, data-access, integration, Blazor, Razor Pages, MVC Razor, Windows Forms, WPF, WinUI, MAUI, and Avalonia facts together without any extractor writing directly to persistence.

## Current exclusions and extension guidance

The current UI slice is intentionally static and bounded. For Blazor, it models common event callbacks, render fragments, render modes, nested component usage, forms, validation components, literal `HttpClient` API calls, and literal `IConfiguration` key usage, but it does not compile Razor, evaluate generic component type constraints, resolve component namespaces semantically, execute handler methods, follow navigation managers, infer routes from runtime code, correlate every API call with prior integration facts, or prove that a form or validation control is reachable in a rendered browser. For Razor Pages and MVC Razor, it models common page/view classification, `_ViewImports`, `_ViewStart`, layouts, partials, view components, tag-helper forms and anchors, page models, page handlers, authorization metadata, and conventional controller/action linkage, but it does not execute Razor Pages handlers, render views, evaluate MVC route conventions beyond static conventional evidence, run tag helpers, bind model metadata, follow custom view-location expanders, or infer dynamic view names. For Windows Forms, it models project classification, startup forms, forms, user controls, designer partials, `.resx` resource keys, controls, control hierarchy, event wiring, data bindings, service-looking dependencies, and data-access-looking dependencies, but it does not compile projects, load designers, run `InitializeComponent`, instantiate controls, execute message loops, inspect visual layout, open data connections, evaluate dynamic factories, or prove event reachability. For WPF, it models project classification, application definitions, startup URIs or objects, windows, pages, user controls, resource dictionaries, keyed resources, styles, templates, named controls, custom component tags, binding paths, commands, routed events, static navigation, direct or convention-based view-model evidence, service-looking dependencies, and data-access-looking dependencies, but it does not compile projects, load XAML, instantiate WPF controls, evaluate resource lookup, run data binding, execute commands or routed events, run view-model locators, evaluate template selectors, inspect visual trees, or open data connections. For WinUI, it models project classification, Windows App SDK package evidence, package manifests, package identity metadata, application definitions, startup window construction, windows, pages, user controls, resource dictionaries, keyed resources, styles, named controls, custom component tags, binding paths, commands, routed events, frame navigation, direct or convention-based view-model evidence, service-looking dependencies, and data-access-looking dependencies, but it does not compile projects, load XAML, validate MSIX packages, instantiate WinUI controls, evaluate theme resource lookup, run data binding, execute commands or routed events, inspect visual trees, or open data connections. For MAUI, it models project classification, `UseMaui`, `MauiProgram`, target-framework and `Platforms` folder platform-head evidence, applications, Shell layouts, Shell routes, pages, content views, resource dictionaries, keyed resources, styles, named controls, custom view tags, binding paths, commands, event handlers, `ConfigureMauiHandlers` registrations, static Shell navigation, direct or convention-based view-model evidence, service-looking dependencies, and data-access-looking dependencies, but it does not evaluate MSBuild, require MAUI workloads, load XAML, instantiate MAUI controls, run platform heads, evaluate resource lookup, execute commands or events, run Shell navigation, build a MAUI dependency-injection container, inspect visual trees, or open data connections. For Avalonia, it models project classification, package/reference evidence, `App.axaml`, windows, user controls, styles, keyed resources, style includes, named controls, project-local component tags, binding paths, commands, event handlers, `x:DataType` view-model evidence, view-locator mappings, ReactiveUI generic view relationships, static ReactiveUI navigation, service-looking dependencies, and data-access-looking dependencies, but it does not evaluate MSBuild, load AXAML, instantiate Avalonia controls, start desktop lifetimes, run view locators, create ReactiveUI routers, evaluate selectors or resources, execute commands or events, inspect visual trees, or open data connections. When extending UI extraction, contributors should keep the same safety model: static repository artifacts only, deterministic repository-relative stable keys, explicit evidence, confidence, unknown state for dynamic or unsupported patterns, and redaction before any snippet preview is stored.

New UI frameworks should reuse the shared UI helper project where possible. Framework-specific values such as `Blazor`, `RazorPages`, `MvcRazor`, `WinForms`, `Wpf`, `WinUI`, `Maui`, and `Avalonia` should appear as metadata values, not ad hoc node kinds. Add domain-controlled node or relationship values only when the shared graph vocabulary genuinely lacks the architecture concept and the addition belongs in the domain/application seams.
