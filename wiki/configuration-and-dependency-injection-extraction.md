# Configuration and Dependency-Injection Extraction

Configuration and dependency-injection extraction is the part of Archon that explains how an analyzed .NET application is wired at runtime. Dependency injection, often shortened to DI, is the application-composition pattern where code asks a container for services rather than constructing every collaborator directly. Configuration extraction is the related slice that explains which configuration keys, sections, providers, options models, connection-string names, and environment-specific artifacts influence that runtime composition. WP007 now contains Microsoft DI registration extraction, hosted-service and HttpClientFactory recognition, registration-wrapper traversal, constructor correlation, legacy container and service-locator heuristics, modern appsettings/options extraction, and legacy `.config` extraction. The top-level `ConfigurationExtractor` composes the modern and legacy configuration slices so callers can request one merged configuration snapshot while the source-family-specific classes keep their names and responsibilities accurate. API-triggered extraction also composes the DI and configuration extractors through a dedicated pipeline stage so accepted `/extractions` runs can persist WP007 facts through the same snapshot writer seam as repository, project, and Roslyn semantic facts.

Read this page with [graph domain model](graph-domain-model.md) for graph vocabulary, [Roslyn semantic extraction](roslyn-semantic-extraction.md) for compiler-backed symbol binding and evidence, [API extraction workflow](api-extraction-workflow.md) for the broader orchestration model, and [validation and test workflows](validation-and-test-workflows.md) for focused commands. Terms such as stable key, evidence-first, confidence, semantic model, service registration, and `REGISTERED_AS_SERVICE` edge are defined here in context and in the [glossary](glossary.md).

## Current Microsoft DI registration slice

The current implementation recognizes modern Microsoft.Extensions.DependencyInjection registration calls when Roslyn can bind the invocation to the Microsoft service-collection extension families. A **service registration** is a statement that tells the DI container which implementation type should satisfy a requested service abstraction and how long the produced instance should live. The supported standard forms include `AddSingleton<TService, TImplementation>()`, `AddScoped<TService, TImplementation>()`, `AddTransient<TService, TImplementation>()`, service-only generic overloads such as `AddSingleton<TService>()`, `typeof(...)` overloads, and factory overloads where the service type can be proven even when the concrete implementation cannot.

The extractor also recognizes descriptor-based registration APIs. `TryAdd` means “register this descriptor only if the service has not already been registered.” `TryAddEnumerable` is the enumerable variant commonly used when multiple implementations of the same service contract may coexist. `Replace` removes an existing descriptor for the service type and adds the supplied descriptor. In all three cases, Archon reads the nested `ServiceDescriptor.Singleton<TService, TImplementation>()`, `ServiceDescriptor.Scoped<TService, TImplementation>()`, or `ServiceDescriptor.Transient<TService, TImplementation>()` call to recover the service type, implementation type, and lifetime.

The supported lifetimes use the same vocabulary as the source API. `Singleton` means the container should reuse one instance for the container lifetime. `Scoped` means the container should reuse one instance for a logical scope, such as a web request in ASP.NET Core. `Transient` means the container can create a new instance each time the service is requested. Archon records the lifetime as edge metadata because the lifetime describes the registration relationship between service and implementation, not the identity of either type by itself.

Factory registrations are represented conservatively. A call such as `AddTransient<IService>(sp => new Service())` proves that `IService` is registered with a transient lifetime, but this slice does not evaluate arbitrary delegate bodies to prove every possible implementation return path. The graph therefore records an implementation placeholder with explicit unknown state and medium confidence rather than inventing a concrete implementation. If a call cannot be compiler-bound to a supported Microsoft DI extension family, the slice does not create a guessed registration fact from text alone.

## Hosted services and background services

A **hosted service** is a service that participates in the .NET generic host lifecycle through `Microsoft.Extensions.Hosting.IHostedService`. A **background service** is a hosted service that derives from `BackgroundService`, the common base type for long-running worker loops. The current extractor recognizes `AddHostedService<THostedService>()` and emits a `REGISTERED_AS_SERVICE` relationship from the hosted implementation type to `IHostedService`. It also marks ordinary service registrations as hosted-service registrations when Roslyn proves that the implementation type implements `IHostedService`, and it adds background-service metadata when the implementation derives from `BackgroundService`.

These facts are still DI graph facts rather than worker runtime execution traces. They explain that the application registers a hosted service with the container; they do not prove scheduling intervals, queue names, retry behavior, or external endpoints. Later runtime and configuration work can attach those details through additional evidence-backed facts.

## HttpClientFactory registrations

`HttpClientFactory` is the Microsoft DI pattern for creating configured `HttpClient` instances. The current extractor recognizes default, named, typed, and typed-implementation `AddHttpClient` registrations. A default `AddHttpClient()` registration records that `IHttpClientFactory` itself is available. A named registration such as `AddHttpClient("orders", ...)` records the client name so later queries can distinguish one configured client from another. A typed registration such as `AddHttpClient<TodoClient>(...)` records the typed client type, and a typed-implementation registration such as `AddHttpClient<ITodoClient, TodoClientImplementation>(...)` records the service abstraction and implementation type.

HttpClient registrations often contain a configuration delegate that sets a base address, default headers, handlers, or resilience behavior. This slice preserves a compact delegate preview in metadata when a delegate is present, but it does not yet treat the delegate as a full external-service extraction source. The external target is therefore explicit unknown data for named and typed clients unless a later configuration or HTTP-client slice resolves it from source and configuration evidence. That explicit unknown state is intentional: the graph should show that an outbound client exists without pretending that every remote endpoint is already known.

## Wrapper methods and invocation chains

Real applications rarely keep every service registration directly inside the first startup method. They commonly delegate composition to wrapper methods, module classes, or extension methods such as `services.AddApplicationServices()`. In this page, a **registration wrapper** means a method that accepts an `IServiceCollection` and calls one or more supported Microsoft DI registration APIs, either directly or by calling another wrapper. The current extractor follows compiler-bound wrapper calls inside the same semantic document so the graph can still explain registrations that are hidden behind application-specific composition helpers.

Wrapper traversal stays evidence-first and conservative. When the extractor sees a startup or module call into a wrapper, it inspects the wrapper method body and applies the same Microsoft DI registration rules used for direct calls. A registration discovered inside a wrapper keeps its normal implementation-to-service `REGISTERED_AS_SERVICE` relationship, but the edge metadata marks the registration family as `Wrapper`, records the wrapper depth, and stores a readable invocation chain. The invocation chain is the ordered path of wrapper calls that led to the registration, for example `AddApplicationServices -> AddPersistence`. The registration evidence still points to the inner `AddSingleton`, `AddScoped`, `AddTransient`, descriptor, hosted-service, or HttpClient invocation, and additional wrapper invocation evidence records preserve the outer call sites that explain how the extractor reached that body.

The safeguards are part of the model rather than incidental implementation detail. A wrapper body may be missing because the method comes from a referenced assembly, a source declaration may have no body, a wrapper may recursively call itself through a cycle, or a `dynamic` receiver may defer member binding until runtime. In those cases, Archon emits warnings or explicit unknown diagnostics instead of inventing registrations. Recursion depth is also bounded so a deep or accidental wrapper chain cannot make extraction unbounded. Contributors should treat those warnings as a prompt to inspect the composition code, not as proof that the registration does not exist.

## Constructor correlation

Constructor correlation connects DI registration facts to the dependencies required by registered implementation types. **Constructor injection** is the pattern where a class declares its collaborators as constructor parameters, such as `PrimaryService(IRepository repository)`. Once the DI extractor has proven that `PrimaryService` is registered, it inspects the registered implementation type's public constructors through Roslyn and records deterministic `INJECTS` and `DEPENDS_ON` relationships from the implementation type to each constructor parameter type. This makes questions such as “which registered services depend on `IRepository`?” possible even when the API orchestration path has not yet merged separate semantic extraction output.

These constructor-correlation edges are graph facts derived from compiler symbols, not runtime container resolution traces. The metadata records the implementation type, dependency type, constructor parameter name, and `MicrosoftDI.ConstructorCorrelation` relationship source. Stable keys are based on the implementation type, dependency type, and parameter name so repeated extraction collapses duplicates through the shared accumulator. The same stable identity also keeps the DI correlation compatible with WP006-style semantic facts: if an equivalent constructor dependency is already present in an accumulated snapshot, deterministic keys and fingerprints prevent the DI slice from multiplying the relationship.

## Legacy containers, service locators, and manual factories

Legacy dependency-injection code often predates Microsoft.Extensions.DependencyInjection and therefore does not share a single method vocabulary. A **legacy container** is a third-party or older dependency-injection library that owns service composition through its own registration API. The current dependency-injection extractor recognizes representative compiler-bound registration shapes for Unity, Autofac, Castle Windsor, StructureMap, Ninject, and SimpleInjector. It does this without loading those containers or executing composition code. The test fixtures define local container-shaped APIs, and real repositories are treated the same way: Roslyn must bind the invocation to the expected package, namespace, type, and method identity before Archon emits a graph fact.

The supported legacy container catalog maps each proven registration to the same graph relationship vocabulary used by Microsoft DI. `UnityContainer.RegisterType<TService, TImplementation>()`, `SimpleInjector.Container.Register<TService, TImplementation>()`, and similar two-generic-argument calls emit an implementation-to-service `REGISTERED_AS_SERVICE` edge. Fluent APIs require extra context. Autofac splits the implementation and service across `RegisterType<TImplementation>().As<TService>()`; StructureMap uses `For<TService>().Use<TImplementation>()`; Ninject uses `Bind<TService>().To<TImplementation>()`; Castle Windsor can nest a component factory such as `container.Register(Component.For<TService, TImplementation>())`. In each case, Archon emits the edge only when Roslyn resolves both endpoint types from the full call shape. Metadata records the container kind, registration method, registration source type, detection mode, service type, implementation type, lifetime where the source API exposes one, confidence, and evidence.

Unsupported legacy registration forms are not ignored when they prove meaningful container usage. Assembly-scanning APIs such as Unity `RegisterTypes(...)` or Autofac `RegisterAssemblyTypes(...)` can show that a project uses a container but do not identify every service-to-implementation pair without executing arbitrary scanning rules. Archon represents those forms as explicit unknown registration facts with medium confidence, an `unknownRegistration` metadata marker, and a warning that names the unsupported container method. This behavior keeps the graph honest: it can tell a contributor that a legacy composition mechanism exists while avoiding fabricated service mappings.

A **service locator** is code that asks a global or ambient resolver for a service instead of receiving the service through a constructor. The current implementation detects CommonServiceLocator `IServiceLocator.GetInstance<TService>()` calls as conservative heuristic facts. The service abstraction is known because the generic argument is compiler-bound, but the concrete implementation is not. Archon therefore uses medium confidence, marks `heuristicDetection` in metadata, and records explicit unknown state explaining that service-location usage does not expose a deterministic implementation.

A **manual factory** is project code that creates service implementations behind an abstraction without using a container registration call. The current heuristic is intentionally narrow: a source method whose name starts with `Create` or contains `Factory`, returns an interface, and directly constructs a type implementing that interface can produce a medium-confidence `REGISTERED_AS_SERVICE` fact. This is useful for modernization analysis because manual factories often hide service composition from container-centric extraction. The fact is still labeled as `ManualFactory`, carries heuristic metadata, and should be interpreted as composition evidence rather than as proof that a DI container owns the mapping.

Confidence is part of the contributor-facing contract for this slice. Symbol-resolved legacy container registrations receive high confidence because the container API and both endpoint types are compiler-bound. Chained or nested legacy calls still receive high confidence when all endpoint symbols are resolved, and their detection mode explains that the extractor followed a fluent or nested call shape. Service locator and manual factory facts receive medium confidence because they are evidence-backed composition signals but are not exact container registration records. Unsupported scanning forms also receive medium confidence with explicit unknown state because container use is certain enough to record, while the target registrations are unknown.

## Modern appsettings and options extraction

The modern configuration slice is implemented by `ModernConfigurationExtractor`. Its responsibility is intentionally limited to `appsettings.json`, `appsettings.*.json`, `Microsoft.Extensions.Configuration`, and Microsoft options APIs. It does not parse legacy XML `.config` files and does not interpret `System.Configuration.ConfigurationManager`; those responsibilities belong to `LegacyConfigurationExtractor`. Keeping the classes separated makes each extractor name describe its source family and prevents a contributor from assuming that modern-only tests also exercise legacy configuration behavior.

When a caller needs all current configuration source families, it should use `ConfigurationExtractor` rather than calling only one slice. `ConfigurationExtractor` runs `ModernConfigurationExtractor` and `LegacyConfigurationExtractor`, then merges their snapshots through `ArchitectureSnapshotAccumulator`. The merge step applies the same stable-key duplicate policy used elsewhere in extraction, so composed output remains deterministic while preserving warnings and errors from both slices.

`ModernConfigurationExtractor` reads appsettings files as repository data artifacts. It does not run the target application's configuration builder, execute startup code, expand user secrets, or contact external providers. A **configuration key** is the logical colon-delimited path used by Microsoft.Extensions.Configuration, such as `Service:Endpoint` or `Logging:LogLevel:Default`. JSON object nesting is normalized into that colon-delimited form, and environment-specific files such as `appsettings.Development.json` carry environment metadata so later query work can distinguish a base setting from an environment override.

Each discovered key becomes a `ConfigurationKey` node using the centralized `config://` stable-key prefix. Source usage is represented with `USES_CONFIG` relationships from a relevant source type or options type to the configuration key. The current source-code catalog recognizes `IConfiguration` indexer access, `GetSection`, `Bind`, `Get<T>`, `Configure<TOptions>`, and constructor injection of `IOptions<T>`, `IOptionsMonitor<T>`, or `IOptionsSnapshot<T>`. This catalog is intentionally compiler-bound through Roslyn. A method or property that looks similar in text does not become a configuration fact unless the semantic model proves the Microsoft configuration or options abstraction involved.

Options binding receives special treatment because an options type is often the architecture concept a contributor wants to query. When code binds `ServiceOptions` to the `Service` section, Archon emits a `USES_CONFIG` relationship from the `ServiceOptions` type to `config://Service` with metadata identifying the usage as options configuration. Options injection proves that a type participates in the options pattern even when the binding call is elsewhere; the extractor records that relationship conservatively using the options type name when a deterministic section cannot be recovered from the constructor parameter alone.

Dynamic or constructed keys are explicit unknowns. For example, `configuration[prefix + name]` proves configuration usage but not a stable key path. Archon emits a medium-confidence `USES_CONFIG` relationship to a synthetic unknown configuration key and records a warning rather than inventing a certain key. That behavior keeps uncertainty queryable without hiding the fact that the source depends on configuration.

Secret redaction is a hard boundary for this slice. Secret-like values, connection-string passwords, API keys, tokens, client secrets, certificates, and private-key material must be redacted before snippets, metadata, warnings, errors, logs, or test output can expose them. Evidence previews are navigation aids, not secret storage, so redaction happens before evidence hashes and previews are created.

## Legacy `.config` and ConfigurationManager extraction

Legacy .NET applications commonly keep runtime settings in XML files named `app.config` or `web.config`. Archon handles those files through `LegacyConfigurationExtractor`, not through `ModernConfigurationExtractor`. The legacy extractor treats XML files as repository data artifacts in the same evidence-first spirit as appsettings JSON: it reads the XML text, records supported facts, and never executes application startup code, configuration section handlers, machine configuration, or external providers. A **legacy configuration artifact** is therefore a static file fact, not proof of the exact runtime value after machine-level configuration, transforms, or deployment-time rewriting have been applied.

The current legacy slice recognizes `appSettings`, `connectionStrings`, declared custom XML configuration sections, custom section elements that appear in the file, and assembly binding redirects under `runtime/assemblyBinding`. Each fact still becomes a `ConfigurationKey` node, but the normalized key is category-prefixed so legacy names do not collide across XML concepts. Examples include `Legacy:AppSettings:FeatureFlag`, `Legacy:ConnectionStrings:MainDb`, `Legacy:CustomSections:sampleSection`, and `Legacy:BindingRedirects:Newtonsoft.Json`. This prefixing preserves the semantic casing of the original key or name while making the category explicit for later query and documentation work.

Connection strings are intentionally modeled by name rather than by value. A `<connectionStrings><add name="MainDb" connectionString="..." /></connectionStrings>` element proves that a connection-string name exists, so Archon emits a `ConfigurationKey` node with connection-string metadata. The actual connection string value is redacted before evidence previews or hashes are produced. Custom section payloads receive similarly conservative treatment because arbitrary section handlers may contain secrets or proprietary data. Binding redirects are configuration facts about assembly version policy; they are represented as configuration keys because they influence runtime binding behavior, but they are not treated as package references or source dependencies by this slice.

Source usage detection covers compiler-bound `System.Configuration.ConfigurationManager.AppSettings[...]` and `System.Configuration.ConfigurationManager.ConnectionStrings[...]` indexer access. The source side is modeled as a `USES_CONFIG` relationship from the containing source type to the matching legacy configuration key. If source references a literal key that was not found in any discovered `.config` artifact, Archon still records the usage as an explicit unknown-source-provider fact with medium confidence. This means the graph can answer “this source expects `MissingSetting`” without claiming that the repository contains the provider definition. Machine-level configuration remains an assumption unless repository evidence exists, so missing file definitions are not silently ignored.

Malformed XML is reported as a warning rather than a silent omission. The extractor continues processing other configuration files and source documents so one broken legacy artifact does not erase unrelated facts. When XML line information is available, evidence is attached to the repository-relative file and the redacted XML snippet; otherwise the fact remains file-scoped. Contributors should treat malformed XML warnings as actionable extraction diagnostics: they explain why a particular file may have incomplete facts while preserving the partial snapshot that could be recovered from the rest of the repository.

## Graph shape and relationship direction

A direct Microsoft DI registration contributes two `Type` nodes and one `REGISTERED_AS_SERVICE` edge. The implementation type is the source node, and the service abstraction is the target node. For example, `services.AddSingleton<IClock, SystemClock>()` is represented as:

```text
type://Example.SystemClock --REGISTERED_AS_SERVICE--> type://Example.IClock
```

This direction reads as “the implementation is registered as the service abstraction.” It also keeps the graph aligned with later questions such as “which concrete types satisfy this interface?” and “which registered implementation has constructor dependencies?” The edge is direct, classified as `KnowledgeKind.Fact`, and assigned certain confidence because Roslyn has resolved both generic type arguments and the registration method symbol.

The edge metadata preserves the details needed for contributor explanations and later query/API work. Current DI metadata includes the extractor name, container kind `Microsoft.Extensions.DependencyInjection`, registration family, registration method name, normalized lifetime, fully qualified service type, fully qualified implementation type where known, hosted-service flags, background-service flags, HttpClient client kind, client name, typed client type, configuration delegate preview, unknown-target marker, wrapper invocation-chain details when applicable, constructor-correlation details for `INJECTS` and `DEPENDS_ON`, and the fully qualified registration extension type. Current configuration metadata includes configuration key, provider, environment, usage kind, source type, options type when available, legacy category markers such as connection-string, custom-section, binding-redirect, and unknown-source-provider flags, and extractor name. These details stay in metadata because they are extractor-specific refinements; the normalized graph fields still carry the node or edge kind, source stable key, target stable key, confidence, unknown state, evidence link, and fingerprint.

## Evidence and stable identity

The DI extractor follows Archon's evidence-first model. Each registration edge points to source-code evidence for the invocation span that produced it. Evidence records the repository-relative file path, one-based line span, symbol name, immediate containing symbol from Roslyn, snippet preview, and snippet hash. The snippet preview is a short navigation aid, not a replacement for source control. The snippet hash is deterministic evidence content used for comparison without storing the full source file in graph metadata.

Stable keys are deterministic. Type nodes use the shared domain `type://` stable-key vocabulary from `StableKeyGenerator`, including synthetic type-style identities for DI concepts that do not have a dedicated graph node kind yet, such as named HttpClient registrations. Configuration key nodes use `StableKeyGenerator.ForConfigurationKey`, which produces the required `config://` prefix. Registration edges use an extractor-local `di-registration://` key derived from lifetime, service type, implementation type, registration method, registration family, and client name when present. Constructor correlation edges use extractor-local `di-constructor-injects://` and `di-constructor-depends_on://` keys derived from implementation type, dependency type, and constructor parameter name. Configuration usage edges use extractor-local `config-usage://` keys derived from source endpoint, key, usage kind, and options type when present. Evidence uses extractor-local keys derived from repository-relative paths, source coordinates, key or registration identity, redacted snippet hashes, and evidence role. Repeated extraction of the same source therefore produces the same graph identities and the shared accumulator removes duplicate nodes, edges, and evidence by stable key.

## API orchestration stage

The API extraction workflow now includes a WP007 pipeline stage after project extraction and Roslyn semantic extraction. A **pipeline stage** is a deterministic application-layer unit of work that receives the validated repository input, the accepted run, and the shared accumulator. The WP007 stage uses the accepted repository root and the explicitly submitted solution list as its boundary. It loads supported C# and Visual Basic projects declared by those submitted solutions, creates Roslyn semantic document contexts for their source files, and then delegates extraction to the existing DI and configuration extractor classes. The stage does not create a new HTTP endpoint, does not write directly to Neo4j, does not start the Aspire AppHost, and does not scan unrelated solutions outside the accepted request.

This composition matters because WP007 facts are no longer available only through extractor-level tests or direct library calls. When a caller starts an extraction run through `POST /extractions`, the shared pipeline can now accumulate repository and solution facts, project facts, Roslyn semantic facts, dependency-injection registrations, constructor-correlation edges, configuration-key nodes, `USES_CONFIG` edges, source evidence, warnings, and explicit unknowns into one assembled `ExtractedArchitectureSnapshot`. The orchestrator still owns lifecycle state and persistence handoff, and the configured `IArchitectureSnapshotWriter` still decides whether the run reaches `Completed` or `Failed`. WP007 remains a contributor-facing extraction capability, not a query API; later work packages still need to add graph query endpoints or MCP graph access before external clients can ask rich questions over persisted DI and configuration facts.

The stage deliberately reuses the same source-boundary philosophy as earlier pipeline stages. Submitted solution files are the entry point, supported project declarations are loaded as static repository artifacts, and project source is parsed into Roslyn compilations without restore, MSBuild target execution, Visual Studio automation, target application startup, or external package-feed access. Configuration artifact discovery is repository-scoped because appsettings and `.config` files can influence runtime behavior even when the specific usage source is not in the first submitted project file. The graph facts still carry repository-relative paths and evidence so a contributor can trace each fact back to the source file or configuration artifact that produced it.

WP007 diagnostics also flow through the same shared accumulator used by the rest of extraction. Unsupported legacy container scanning, dynamic configuration keys, malformed XML, missing provider definitions, and solution/project load degradation become warnings or explicit unknown facts instead of raw exceptions. The API status surface exposes accumulated warnings through run status only after the usual diagnostic sanitization boundary, so stack traces, connection strings, request metadata values, and secret-like configuration values must not leave the process.

## Relationship to Roslyn semantic extraction

The DI and source-usage portions of the configuration extractors consume Roslyn semantic document context rather than scanning text independently. A semantic document context includes the syntax tree, matching semantic model, repository root, document path, and project context. The DI extractor walks invocation syntax, asks the semantic model for the invoked method symbol, and only emits a registration when compiler binding proves the method owner, method name, and generic type arguments. `ModernConfigurationExtractor` similarly asks Roslyn to prove `IConfiguration`, `IConfigurationSection`, configuration binder, service collection options configuration, and options wrapper symbols before it emits modern source-code `USES_CONFIG` facts. `LegacyConfigurationExtractor` asks Roslyn to prove `System.Configuration.ConfigurationManager` `AppSettings` or `ConnectionStrings` access before it emits legacy `USES_CONFIG` facts.

This design matters because extension methods and overloads can look alike in source. A project-local method named `AddSingleton` should not become a Microsoft DI fact unless Roslyn binds it to the supported Microsoft extension method. Conversely, when source uses normal extension-method syntax such as `services.AddScoped<IWorker, Worker>()`, Roslyn still exposes the reduced extension method and the original definition, so the extractor can identify the method family without depending on the text shape alone. The same principle governs wrapper traversal: a method is followed only when Roslyn proves it accepts `IServiceCollection` and its body is available to the current semantic document.

The current direct extractor produces graph-ready domain contracts directly through the shared application accumulator. It does not write Neo4j data, does not start the Aspire AppHost, does not expose API or MCP query behavior, and does not run through a separate persistence path. When the API pipeline uses the WP007 stage, Neo4j persistence still receives only the generic `ArchitectureNode`, `ArchitectureEdge`, and `EvidenceRecord` contracts later through the established snapshot writer seam.

## Validation commands

Use the focused DI extractor tests when changing the dependency-injection slice:

```powershell
dotnet test .\test\Archon.Extractors.DependencyInjection.Tests\Archon.Extractors.DependencyInjection.Tests.csproj
```

Use the focused configuration extractor tests when changing the modern or legacy configuration slice:

```powershell
dotnet test .\test\Archon.Extractors.Configuration.Tests\Archon.Extractors.Configuration.Tests.csproj
```

Use the API extraction tests when changing WP007 pipeline composition, stage ordering, cross-slice accumulation, run diagnostics, or snapshot-writer handoff behavior:

```powershell
dotnet test .\test\Archon.Api.Extraction.Tests\Archon.Api.Extraction.Tests.csproj --no-restore
```

The integrated build gate for this work package is:

```powershell
dotnet build .\Archon.slnx --no-restore
```

Run restore first when project or package references have changed or when the local environment has not restored packages yet. Automated validation for this slice must not start the Aspire AppHost, must not require Neo4j credentials, and must not run MCP tools. The DI tests compile in-memory C# fixtures, bind the fixtures through Roslyn, and assert relationship direction, registration-family metadata, lifetime metadata, hosted-service metadata, HttpClient client metadata, wrapper invocation-chain metadata, traversal safeguard warnings, constructor-correlation `INJECTS` and `DEPENDS_ON` relationships, explicit unknown state, evidence quality, deterministic keys, and duplicate-free accumulation. The configuration tests create temporary repository appsettings and `.config` files, compile in-memory C# fixtures, bind configuration usage through Roslyn, and assert `ConfigurationKey` nodes, `USES_CONFIG` relationships, options binding metadata, `ConfigurationManager` usage metadata, dynamic-key and unknown-source-provider unknowns, deterministic stable keys, redacted snippets, malformed XML warnings, and no secret leakage through diagnostics or metadata.
