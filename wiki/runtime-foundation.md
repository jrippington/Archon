# Runtime Foundation

Archon's runtime foundation is deliberately small. The API host and MCP host can start as ASP.NET Core processes, expose operational probes, and run under an Aspire AppHost for local development. The API host now also composes the asynchronous [API extraction workflow](api-extraction-workflow.md), which maps start, status, and recent-history endpoints while keeping extraction validation, run lifecycle behavior, progress updates, orchestration, snapshot assembly, and persistence handoff in application services. When Neo4j infrastructure is composed, the same host composition also supplies durable extraction run history so accepted run records, status reads, and recent-history reads use Neo4j-backed operational storage instead of process-local memory. That workflow executes the current project extraction stage for explicitly submitted solution files, so repository, solution, project, package, analyzer, FilePath, evidence, warning, and application type classification facts can flow into a generalized snapshot. It also runs the current runtime extraction slices for modern ASP.NET Core source, console entry-point source, worker hosted-service source, and non-HTTP runtime consumer source. A **runtime extraction slice** is a static-analysis contribution that describes how an analyzed application starts or exposes runtime-facing behavior without executing that application. In the current implementation, the ASP.NET Core slice recognizes direct minimal API endpoint mappings in C# `Program.cs` files, simple endpoint groups, attributed ASP.NET Core controllers and actions, MVC setup calls, controller endpoint mapping calls, middleware registration order, custom `UseMiddleware<T>()` targets, filter attributes, authorization attributes, anonymous access attributes, and OpenAPI or Swagger setup calls. A console entry-point slice recognizes explicit C# `static Main` methods, explicit VB.NET `Sub Main` or `Function Main` methods, and C# top-level statements from submitted target repository projects. A worker hosted-service slice recognizes C# `IHostedService` implementations, `BackgroundService` implementations, lifecycle execution methods, generic-host setup calls, and hosted-service dependency-injection registrations already emitted by the WP007 dependency-injection slice. A non-HTTP runtime consumer slice recognizes scheduled job registrations, queue and topic consumers, message handler subscriptions, Windows-service-style host setup, systemd-style host setup, Topshelf-style host setup, and conservative custom host-loop patterns from C# source. A separate classic ASP.NET extractor slice recognizes repository-contained `System.Web` application artifacts, `Global.asax`, `web.config`, Web Forms pages and user controls, HTTP handlers, HTTP modules, MVC 5 controllers, Web API 2 controllers, and conventional route configuration. These slices contribute `Endpoint`, `Controller`, `HostedService`, `Queue`, `Topic`, `Type`, `Method`, `FilePath`, and project metadata facts, `DECLARES_ENDPOINT`, `CONTAINS`, `HANDLES`, `USES_CONFIG`, and `DEPENDS_ON` relationships, source/configuration evidence, confidence, and explicit unknown state through the same graph contracts used by the rest of extraction. The runtime foundation still does not implement query APIs, MCP graph tools, markdown export, user-interface behavior, arbitrary build execution, target application startup, dynamic hosted-service activation, broker connections, scheduler connections, Windows service registration, or full runtime pipeline evaluation.

For architecture boundaries, read [solution architecture](solution-architecture.md). For MCP tool contracts and examples, read [MCP tool reference](mcp-tool-reference.md). For persistence details, continue to [Neo4j persistence foundation](neo4j-persistence-foundation.md). For validation commands, read [validation and test workflows](validation-and-test-workflows.md). Terms used here are defined in the [glossary](glossary.md).

## Service defaults

**Service defaults** are shared host configuration that every runtime process uses instead of copying the same setup into each executable project. Archon keeps these defaults in `src/Archon.ServiceDefaults`. They currently configure health checks, OpenTelemetry-compatible logging, metrics, tracing, Aspire-style service discovery, and resilient `HttpClient` behavior.

Keeping this cross-cutting setup in one project prevents the API and MCP hosts from drifting apart. Later work packages can add real API or MCP features while still receiving the same health, telemetry, service-discovery, and HTTP-resilience behavior.

## Readiness and liveness probes

The current operational probe model uses two endpoints:

- `/health` is the readiness probe. It runs registered health checks and answers whether the process is ready to accept work.
- `/alive` is the liveness probe. It answers whether the process itself is responsive.

The distinction matters because a process can be alive before every dependency is ready. For example, when a host opts into Neo4j infrastructure through `AddArchonNeo4j`, the infrastructure adapter contributes a dependency-specific readiness check named `neo4j`. That check opens a read session and runs `RETURN 1 AS healthy`, proving connection configuration, authentication, network reachability, database selection, and Cypher execution without creating graph schema or requiring architecture data.

## Running hosts independently

Developers can run the API and MCP hosts independently while working on the foundation:

```powershell
dotnet run --project .\src\ArchonApi\ArchonApi.csproj
dotnet run --project .\src\ArchonMcp\ArchonMcp.csproj
```

After a host starts, browse or request `/health` and `/alive` on the assigned local ASP.NET Core URL. A successful response confirms the host runtime foundation is working. Stop manually run host processes after verification. Automated validation should use the test projects instead of launching long-running hosts.

In the current runtime slice, absence is still intentional for features that have not been implemented. `ArchonApi` maps health probes and the extraction start, status, and recent-history endpoints, and those endpoints can dispatch the asynchronous orchestration path that runs the project extraction stage and persistence handoff. It does not map Swagger, Scalar, or UI endpoints. `ArchonMcp` still does not map arbitrary shell execution, arbitrary SQL, arbitrary Cypher, direct Neo4j access, filesystem mutation, or code-modification endpoints. It now maps narrow verification paths for implemented read-only tools, `archon://` current and parameterized resources, and versioned prompt listing and retrieval. The MCP host composes a read-only registration catalog internally so readiness can prove that mandatory MCP registrations are present as concrete tools, resources, and prompts are added. That catalog includes the operational capability named `archon.health`, user-facing read-only tools named `archon.search`, `archon.describe_project`, `archon.get_dependencies`, `archon.get_dependents`, `archon.find_dependency_paths`, `archon.describe_symbol`, `archon.find_symbol_usages`, `archon.get_data_access_usage`, `archon.assess_change_impact`, `archon.get_architecture_rules`, `archon.get_hotlist_findings`, and `archon.get_snapshot_diff`, the resource-reader capability named `archon.read_resource`, prompt operation capabilities named `archon.list_prompts` and `archon.get_prompt`, and prompt template capabilities named `impact-analysis`, `modernization-brief`, `refactoring-preflight`, `new-feature-placement`, `legacy-data-access-review`, `hotlist-summary`, and `architecture-rule-check`. `archon.health` is a narrow operational probe for composition validation. The query tools, resources, and prompt templates are evidence-backed architecture investigation surfaces documented in [MCP tool reference](mcp-tool-reference.md). These capabilities exist to prove the host fails closed when required registrations are missing or when a forbidden capability name suggests mutation, arbitrary execution, direct database access, or source modification.

The API extraction and management modules still provide in-memory fallbacks for focused tests and lightweight local composition, but those fallbacks are no longer authoritative when a host has already registered durable infrastructure implementations. A **fallback registration** is a dependency-injection registration that is added only when no earlier registration for the same application port exists. Archon uses this pattern so tests can opt into an explicit in-memory writer, fake run-history store, or fake deletion store without making those process-local components the production system of record. The production composition path should add Neo4j infrastructure at the host boundary so `IArchitectureSnapshotWriter` resolves to the Neo4j-backed snapshot writer, `IExtractionRunHistory` resolves to the Neo4j-backed run-history adapter, `ISnapshotLifecycleQuery` resolves to the Neo4j-backed lifecycle query adapter, and `ISnapshotDeletionStore` resolves to the Neo4j-backed snapshot deletion adapter. The deletion adapter owns both delete-one and confirmed delete-all snapshot cleanup. This follows the dependency-injection principle used throughout the runtime foundation: modules register application workflow defaults, infrastructure adapters register durable outer-boundary implementations, and hosts choose the final composition order without moving Neo4j driver types into API endpoint handlers or application services.

This distinction is easiest to see in the API host. `ArchonApi` composes the extraction, query, and management modules first so the host remains runnable in a narrow test configuration. When the `Neo4j` configuration section contains connection settings, the host then calls the Neo4j infrastructure registration at the outer boundary. The resolved single service for snapshot writing, run history, lifecycle listing, and snapshot deletion is the Neo4j implementation, not the in-memory fallback. Focused endpoint tests can still register explicit fakes before module composition; those tests are asserting transport and orchestration behavior, not claiming that production should store lifecycle state in process memory.

Management readiness follows the same abstraction boundary. The readiness response probes the snapshot lifecycle query port with a bounded sample read and reports a sanitized dependency named `snapshot-lifecycle`. A graph-backed host can therefore be ready even when there are zero persisted snapshots, because readiness answers whether the lifecycle query path is available, not whether a process-local writer happens to contain diagnostic snapshots. If this dependency fails, contributors should investigate the configured lifecycle query adapter and its store connectivity rather than assuming that the in-memory fallback should be present.

The **MCP registration catalog** is an allow-list of stable capability names known to the MCP host. A **capability** is a named tool, resource, prompt, or operational registration that the host can validate before reporting readiness. The catalog now proves the operational path, broad search, project description, outgoing dependency traversal, incoming dependent traversal, dependency-path search, symbol description, symbol usage investigation, data-access usage review, change-impact assessment, architecture-rule catalog review, hotlist finding review, snapshot diff comparison, read-only resource URI handling, prompt listing, prompt retrieval, and all seven curated prompt templates while preserving the read-only boundary. It also carries conservative limit options for MCP responses, including default result count, traversal depth, evidence count, dependency path count, and serialized-context budget. `archon.search` uses the result-count limit to shape grouped search output; project description uses bounded evidence references; dependency and dependent traversal use result and traversal-depth limits; dependency-path search uses path and depth bounds; symbol description and symbol usage use bounded evidence and usage rows; data-access usage uses result and evidence limits; change-impact assessment uses result and traversal-depth limits; rules and hotlist findings use result and evidence-reference limits; snapshot diff uses summary counts plus bounded detail rows; current resources use result and evidence limits when returning rules, findings, and hotspots; parameterized project, symbol, and snapshot diff resources reuse the corresponding bounded tool workflows while preserving the `archon.read_resource` envelope operation; prompt listing returns bounded metadata, and prompt retrieval returns one versioned markdown template at a time. Each bounded response reports truncation metadata, warnings, and narrowing follow-ups when the returned set is incomplete.

Resource handling adds one host-level safety boundary. The host parses only the `archon://` scheme, recognizes only registered resource families, rejects duplicate or blank query parameters, validates decoded stable-key values before query execution, and applies authorization before parsing so disabled resource reads cannot be used to probe URI shapes. Current resources resolve `current` to one concrete snapshot stable key inside an explicit repository and optional solution scope. If resolution has no matching snapshot, the result is `NotFound`; if more than one snapshot ties for current selection, the result is `Ambiguous` rather than an arbitrary choice. Parameterized resources keep the same parser and authorization boundary but address exact `project://`, `symbol://`, and `snapshot://` stable keys in the URI path. They delegate to the approved project description, symbol description, and explicit snapshot diff tool workflows rather than creating a second query path. Prompt handling adds a related but simpler boundary: prompt templates are embedded versioned markdown resources, not repository files, and the host retrieves them through `archon.get_prompt` only after authorization and audit. The shared resource and prompt infrastructure belongs to the runtime foundation, while each resource URI and prompt template's exact usage guidance belongs in [MCP tool reference](mcp-tool-reference.md).

Readiness now includes both the shared service-default checks and the MCP catalog check. If the baseline registration is removed or a later registration uses a forbidden name such as one implying shell, SQL, Cypher, unrestricted graph querying, filesystem access, Neo4j internals, mutation, command execution, or code editing, `/health` returns an unavailable readiness result. The catalog also treats non-read-only registrations as unsafe even when their names look benign. The response remains deliberately terse: it reports high-level readiness failure rather than exposing service-provider details, stack traces, secrets, connection strings, graph internals, or target-repository evidence. `/alive` remains limited to the lightweight liveness check so an orchestrator can still distinguish a running process from a ready MCP runtime.

The MCP host also now composes a shared **MCP response envelope** foundation. An envelope is the outer object that every later tool and resource should use so AI clients receive a consistent operation name, optional snapshot identity, summary, confidence, structured facts, evidence references, findings, unknowns, warnings, applied limit metadata, and suggested follow-ups. This foundation is intentionally available through internal host services before public MCP tool routes exist. The baseline `archon.health` operation can produce a shaped success envelope for tests and future transport wiring, but it remains an operational capability rather than a query tool. That distinction lets contributors validate contract shape without implying that architecture graph tools have been exposed.

The envelope vocabulary matters because MCP clients are usually language-model-driven. A **fact** is structured data returned by Archon, not a sentence invented by the model. A **confidence** value describes how strongly persisted facts, evidence, findings, metrics, or explicit unknowns support the response. An **unknown** states that data is incomplete, unsupported, unresolved, unavailable, or truncated; it prevents missing data from being treated as known absence. A **suggested follow-up** points only to safe Archon investigation paths or safe user questions, not arbitrary shell, database, filesystem, or code-editing actions. A **truncation** record explains when a configured result, evidence, path, traversal-depth, or serialized-context limit shaped the response and how a caller can narrow the request.

Shared validation and mapping helpers enforce that foundation before concrete tools arrive. Stable-key validation rejects raw numeric identifiers that could be confused with Neo4j internal node or relationship IDs. Snapshot selectors accept controlled values such as `latest` or stable snapshot keys instead of free-form descriptions. Count, depth, and page-size requests are bounded by the conservative MCP limit options. Evidence mapping treats repository source, configuration, markdown, and other extracted snippets as untrusted data and redacts representative secret-like values before those snippets can enter an MCP response. Structured error envelopes use stable categories for validation, unsupported operation, not-found, ambiguity, unauthorized, forbidden, dependency unavailable, query-layer failure, and server error cases while deliberately omitting stack traces, exception types, credentials, connection strings, raw sensitive evidence, and graph internals.

The MCP host now also composes the first security and isolation seams that every later tool, resource, and prompt-support operation must reuse. The **caller context** is a provider-neutral identity record: it carries a stable caller identifier, optional display name, and normalized roles, but it never carries access tokens, bearer credentials, raw claims payloads, passwords, connection strings, or identity-provider-specific objects. The default development provider reads a local/test caller identity from configuration so tests can exercise the seam without requiring production identity-provider secrets. Production composition can replace that provider while preserving the same authorization and audit contract.

Authorization is intentionally evaluated before operation delegates can invoke application/query dependencies. This is the host's **fail-closed** boundary: if authentication is required and no caller identity is available, the operation returns the shared unauthorized error shape; if the caller is authenticated but the operation is not enabled by configuration, the operation returns the shared forbidden error shape. The **allow-list** is the configured set of MCP operation names, and later resource-family settings follow the same model for `archon://` resource groups. When no explicit operation allow-list is configured, the host enables only the operational `archon.health` baseline so local readiness and smoke tests remain usable. Once an allow-list is supplied, that configured list is authoritative, which means an omitted operation is disabled and no handler or query-layer path is reached. This distinction is important for contributors adding future tools: validation, authorization, and allow-list checks should happen before expensive graph queries, not after partial work has already happened.

Every operation attempt also passes through a sanitized **audit trail**. An audit trail is the sequence of security-relevant records that lets operators answer who attempted an operation, which operation was requested, whether it succeeded, whether the response reported truncation, what structured error category was returned, and how long the attempt took. Request parameters are normalized for audit by preserving safe parameter names and safe values while replacing password, token, API key, credential, private-key, certificate, and connection-string values with `[redacted]`. Non-sensitive parameter values still pass through the shared text redactor so secret-like fragments embedded in otherwise ordinary text are removed before logging. The logging sink uses `ILogger` and receives only sanitized audit events; it must not log raw source evidence, raw request bodies, credentials, stack traces, access tokens, connection strings, or prompt-injection payloads.

Prompt-injection-aware evidence handling is part of the same security foundation. A **prompt injection** is untrusted analyzed content that tries to instruct an AI client to ignore its higher-priority instructions, reveal secrets, execute commands, or treat repository text as authority. Archon treats extracted source, comments, markdown, configuration values, string literals, rule metadata, SQL previews, and snippet previews as untrusted evidence data. Secure evidence mapping redacts representative secrets and labels the content as `untrusted-repository-evidence`; it also keeps privileged instruction text separate rather than concatenating instructions with repository content. The current redaction vocabulary covers password, token, API key, account key, credential, connection string, certificate, and private-key assignment patterns, including nested secret-like fragments in otherwise ordinary audit parameter values. Later prompt templates and tool responses should build on that separation so an AI client can cite evidence and unknowns without treating malicious source comments or configuration text as commands.

This response-envelope guidance belongs on the runtime foundation page because it explains the host-level MCP runtime contract that later tool and resource slices must reuse. Tool-specific inputs, outputs, examples, and no-match semantics now live in [MCP tool reference](mcp-tool-reference.md), starting with `archon.search`. Detailed MCP tool guidance does not belong on `wiki/home.md`, which remains only a reader-path landing page. The common envelope contract remains a runtime foundation concept because it is shared infrastructure rather than one tool's behavior.

## MCP server setup and local usage

The Archon MCP server is the host-layer projection that lets MCP-compatible AI clients ask read-only architecture questions over persisted Archon knowledge. In practical terms, contributors start the `ArchonMcp` project, verify liveness and readiness, and then call the verification routes that exercise the same internal handlers used by the MCP transport registration. Those verification routes are intentionally narrow: they are useful for local development and automated tests, but they do not turn the host into a general-purpose HTTP API, shell, SQL console, file browser, or Neo4j browser.

From the repository root, run the MCP host directly when you only need to inspect the MCP surface:

```powershell
dotnet run --project .\src\ArchonMcp\ArchonMcp.csproj
```

The Visual Studio launch profile currently binds the project to `https://localhost:56452` and `http://localhost:56453` in the Development environment. A command-line run can choose different ports when ASP.NET Core configuration overrides them, so always read the startup output before copying example URLs. After startup, request `/alive` to confirm that the process is responsive and `/health` to confirm readiness. Readiness includes the shared service-default checks plus the `archon_mcp_catalog` check that proves mandatory MCP tool, resource, prompt, and operational registrations are present, read-only, and free from forbidden capability names.

Local verification uses small HTTP paths that map to implemented MCP handlers. For example, `GET /mcp/prompts` lists registered prompt templates, `GET /mcp/prompts/impact-analysis` retrieves one embedded prompt, `GET /mcp/resources?uri=...` reads one supported `archon://` resource, and `POST /mcp/tools/archon.search` calls the search handler with a JSON request body. The same security pipeline applies to those verification paths: caller context is resolved, the operation allow-list is checked, audit metadata is sanitized, request input is validated, and only then can the handler call an approved query abstraction. Contributors should use these routes to prove setup and behavior, then use the [MCP tool reference](mcp-tool-reference.md) for exact tool, resource, and prompt contracts.

The default local security configuration is deliberately provider-neutral. `Archon:Mcp:Security:RequireAuthenticatedCaller` defaults to `true`, but the development caller provider supplies a local caller identity from `TestCallerId`, `TestCallerDisplayName`, and `TestCallerRoles`. This gives tests and local verification a stable identity without storing production tokens or raw claims. `AllowedOperations` is the operation allow-list. If that section is absent, the host enables the current read-only operation set by default so local development can exercise the product surface. If the section is present, it is authoritative: an omitted operation is disabled and fails before validation or query execution. An explicitly empty allow-list disables every operation. Limit settings live under `Archon:Mcp:Limits`, with defaults of 25 result items, traversal depth 3, 10 evidence references, 5 dependency paths, and an approximate 24,000-character serialized context budget.

A typical manual smoke test starts with prompt listing because it does not require seeded architecture data:

```powershell
Invoke-RestMethod -Method Get -Uri https://localhost:56452/mcp/prompts
Invoke-RestMethod -Method Get -Uri https://localhost:56452/mcp/prompts/impact-analysis
```

After architecture data is available through earlier extraction and query work, verify a current resource by percent-encoding the `archon://` URI as a query-string value:

```powershell
$resource = [Uri]::EscapeDataString('archon://snapshot/current?repository=repository%3A%2F%2Farchon-sample')
Invoke-RestMethod -Method Get -Uri "https://localhost:56452/mcp/resources?uri=$resource"
```

For tool verification, post the documented request shape for the operation you are testing. A search smoke test should use a real repository stable key and terms that exist in the selected snapshot:

```powershell
$body = @{
	searchText = 'orders'
	snapshotSelector = 'latest'
	repositoryStableKey = 'repository://archon-sample'
	resultTypeFilters = @('Project', 'Symbol')
	limit = 10
} | ConvertTo-Json -Depth 10

Invoke-RestMethod -Method Post -Uri https://localhost:56452/mcp/tools/archon.search -Body $body -ContentType 'application/json'
```

When a manual call fails, interpret the structured MCP error before changing code. `Unauthorized` means the caller context is missing while authentication is required. `Forbidden` means the operation is not in the configured allow-list. `Validation` means the request or resource URI was malformed, ambiguous, unsupported, duplicated, or over limit and the query layer was not invoked. `NotFound` means the selected data set was available but the requested stable key or explicit resource target was absent. `DependencyUnavailable` means Archon could not resolve the repository, solution, snapshot, or comparable data needed to answer. `QueryLayerFailure` means the approved query abstraction failed and the host converted that failure into a safe response without exposing stack traces, exception type names, raw graph records, secrets, or unsafe evidence snippets.

Troubleshooting should follow the same boundaries as implementation. Do not work around MCP errors by adding arbitrary graph, SQL, shell, or filesystem routes. If `/health` is unavailable, inspect whether a mandatory capability was omitted, whether a capability name contains a forbidden execution or mutation term, or whether configuration intentionally disabled baseline registration for a fail-closed test. If an operation returns `Forbidden`, inspect `Archon:Mcp:Security:AllowedOperations` before debugging the handler. If a resource URI returns validation errors, check the `archon://` scheme, percent-encoded stable keys, duplicate query parameters, required repository scope for current resources, and supported Boolean or integer query values. If evidence output looks surprising, remember that source snippets, comments, markdown, SQL previews, configuration values, and rule metadata are untrusted repository evidence; the correct behavior is to preserve useful context, redact secret-like values, and prevent those snippets from becoming privileged instructions.

## ASP.NET Core endpoint extraction

ASP.NET Core endpoint extraction is evidence-first. When a submitted solution declares a C# project, the API extraction workflow loads the project source as static Roslyn syntax and semantic documents. It then inspects repository-contained `Program.cs` files for direct minimal API invocations, such as `app.MapGet("/customers/{id}", (int id) => Results.Ok(id));`, `app.MapPost("/orders", () => Results.Ok());`, or grouped calls such as `var api = app.MapGroup("/api"); api.MapGet("/orders", () => Results.Ok());`. A **minimal API endpoint** is an HTTP route declared directly in startup code rather than through a controller class. An **endpoint group** is a route builder prefix created with `MapGroup`, and Archon combines a literal group prefix with the endpoint route when both parts are deterministic. The extractor does not start Kestrel, call `WebApplication.CreateBuilder`, run middleware, invoke endpoint delegates, evaluate dependency injection, restore packages, or execute MSBuild targets. It reads source files as repository artifacts and projects the observed route mapping into graph facts.

For each supported direct mapping, Archon emits an `Endpoint` node whose metadata uses stable lower-camel-case field names such as `runtimeKind`, `framework`, `routeTemplate`, `httpMethod`, `handlerSymbol`, `detectionMode`, `confidenceReason`, and, when applicable, `endpointGroupPrefix`. The current minimal API `runtimeKind` is `MinimalApi`, the current `framework` is `ASP.NET Core`, and direct `MapGet` detection continues to use the compatibility detection mode `DirectMapGetInvocation`. Additional supported mapping calls include `MapPost`, `MapPut`, `MapDelete`, `MapPatch`, `MapFallback`, and literal `MapMethods` method collections. The endpoint is connected to its declaring project by a direct `DECLARES_ENDPOINT` relationship. This direction is intentional: the project is the extracted architecture boundary that declares the runtime HTTP surface, while the endpoint is the surface that later query, impact-analysis, and MCP features can reason about.

Stable identity is deterministic and excludes machine-local paths. Endpoint stable keys include the declaring project stable key, HTTP method, normalized route template, and handler identity. The handler identity comes from compiler binding when Roslyn can resolve the handler expression and falls back to a repository-relative source location for lambdas or unresolved delegates. Evidence records use repository-relative source paths, source line spans, the mapping symbol name, bounded snippet previews, and SHA-256 snippet hashes. The snippet preview is meant to help a contributor find the source line; the hash is meant to support deterministic comparison without treating full source text as graph metadata. A useful fixture for this behavior is a temporary project containing a `Program.cs` with `MapGet("/customers/{id}", ...)`; the expected graph contains one `Endpoint` node, one project-to-endpoint `DECLARES_ENDPOINT` edge, and one source evidence record whose path is repository-relative rather than absolute.

Unknowns are represented explicitly instead of being guessed. If the route template is not a compile-time string literal, for example `app.MapGet(route, () => Results.Ok())`, Archon still emits an endpoint fact with the route metadata set to an unknown placeholder and `UnknownState` explaining that the `MapGet` route template is not a compile-time string literal. If an endpoint group prefix is computed, for example `var group = app.MapGroup(prefix);`, the grouped endpoint carries an unknown route state rather than an invented combined route. This preserves the important fact that the application exposes a minimal API mapping while making unsupported dynamic route shapes visible to contributors and future extraction work. Contributors writing new fixtures should prefer one fixture per uncertainty shape, such as a literal group prefix fixture and a separate computed group prefix fixture, so stable-key and unknown-state assertions remain easy to diagnose.

## ASP.NET Core controller and action extraction

Controller extraction broadens runtime discovery beyond startup-only minimal APIs. An **ASP.NET Core controller** is a class that participates in MVC-style request handling, usually by inheriting from `ControllerBase` or `Controller`, ending with the `Controller` suffix, or carrying controller marker attributes such as `ApiController` or `Route`. An **action** is a controller method that can handle an HTTP request through attributes such as `HttpGet`, `HttpPost`, `HttpPut`, `HttpDelete`, or `HttpPatch`. Archon scans every C# semantic document in the submitted project boundary for controller classes and action methods. It does not instantiate controllers, evaluate filters, execute model binding, call routing services, or infer convention-only routes that are not visible as deterministic source evidence.

For each recognized controller, Archon emits a `Controller` node. Controller stable keys include the project stable key and the qualified controller type name. Controller metadata records `runtimeKind`, `framework`, `controllerName`, `routeTemplate` when a literal controller-level route attribute is present, authorization metadata when an `Authorize` attribute exposes a literal policy, anonymous-access metadata when `AllowAnonymous` is present, filter attribute names when filter attributes are visible, `detectionMode`, and `confidenceReason`. Controller action endpoints become `Endpoint` nodes with `runtimeKind` set to `ControllerAction`, the combined controller/action route template, the HTTP method from the verb attribute, the handler symbol for the action method, controller and action names, inherited authorization or anonymous metadata, inherited and action-level filter metadata, evidence, and confidence.

Controller-level and action-level routes are combined only when the source templates are deterministic. The supported token replacement currently handles the common `[controller]` token by using the normalized controller name, so `[Route("api/[controller]")]` on `OrdersController` and `[HttpGet("{id}")]` on `Get` becomes `/api/orders/{id}`. The `DECLARES_ENDPOINT` relationship for controller actions points from the `Controller` node to the `Endpoint` node. That differs from minimal API endpoints, where the project node declares the endpoint directly, because a controller is the immediate runtime declaration boundary for action routes.

## ASP.NET Core pipeline metadata extraction

The current graph contract does not yet define dedicated middleware or OpenAPI node kinds, so pipeline observations are represented as project-level runtime metadata instead of invented graph shapes. A **middleware registration** is a startup call such as `UseRouting`, `UseAuthentication`, `UseAuthorization`, `UseMiddleware<T>()`, `UseSwagger`, or `UseSwaggerUI` that participates in request processing order. Archon records supported middleware calls in source order through a `middlewareOrder` metadata array and records generic `UseMiddleware<T>()` target types through `middlewareTypes` when the type can be read syntactically or through Roslyn binding. This is source-order metadata, not proof of the final runtime pipeline after conditional branches, environment checks, or extension methods that hide additional middleware.

MVC setup and controller mapping are also project-level metadata. Calls such as `AddControllers`, `AddControllersWithViews`, or `AddMvc` are recorded as `mvcSetupCalls`; calls such as `MapControllers`, `MapControllerRoute`, and `MapDefaultControllerRoute` are recorded as `controllerMappingCalls`. OpenAPI and Swagger setup calls such as `AddEndpointsApiExplorer`, `AddSwaggerGen`, `AddOpenApi`, `UseSwagger`, `UseSwaggerUI`, and `MapOpenApi` set `openApiEnabled` to `true`. These facts help contributors understand whether a project appears to expose controller endpoints, middleware, or generated API documentation without requiring Archon to run the application.

This page is the correct home for the runtime mental model because endpoint, controller, middleware, filter, authorization, and OpenAPI extraction change how the runtime foundation should be understood. The more operational details of where the stage runs in the asynchronous workflow are described in [API extraction workflow](api-extraction-workflow.md). `wiki/home.md` remains a landing page and table of contents rather than the place for the detailed endpoint extraction model.

## Classic ASP.NET runtime extraction

Classic ASP.NET extraction covers older `System.Web` applications whose runtime surface is usually split across project files, XML configuration, markup, and source code. A **classic ASP.NET application** is a legacy web application that uses `System.Web` rather than the ASP.NET Core hosting model. Archon treats these applications as static repository artifacts: it reads the project file, `web.config`, `Global.asax`, `.aspx` page markup, `.ascx` user-control markup, and C# source files without loading the target application, evaluating MSBuild, invoking ASP.NET, or executing route registration code.

The project-level fact records application evidence such as `System.Web`, MVC 5, or Web API 2 references, the repository-relative `Global.asax` path, and the repository-relative `web.config` path. `Global.asax` is the classic application directive file that commonly points to an application class such as `MvcApplication`; Archon stores it as evidence and scans source code for lifecycle methods such as `Application_Start`, `Application_Error`, and `Session_Start`. Lifecycle methods become `Method` nodes and are connected to the project with `DEPENDS_ON` relationships because they represent runtime entry hooks owned by the application boundary.

Web Forms uses markup files as runtime-facing artifacts. An `.aspx` page is addressable by a virtual path, so Archon emits it as an `Endpoint` node with `runtimeKind` set to `WebFormsPage`, the virtual path in `routeTemplate`, and the directive `Inherits` type as `handlerType` when available. A `.ascx` user control is not directly addressable by itself, so the current graph contract represents it as a `FilePath` node with `runtimeKind` set to `WebFormsUserControl`. Markup evidence currently uses the existing `SourceCode` evidence kind because the compiled graph contract does not yet define a dedicated markup evidence kind.

HTTP handlers and HTTP modules are classic pipeline extension points. An **HTTP handler** is a type that implements `IHttpHandler` and can directly handle requests, often through a configured `web.config` path such as `orders.axd`. Archon emits the handler type as a `Type` node, emits a configured handler path as an `Endpoint` node, and connects the type to the endpoint with a `HANDLES` relationship. An **HTTP module** is a type that implements `IHttpModule` and participates in request processing without declaring a single endpoint; Archon emits modules as `Type` nodes with `runtimeKind` set to `HttpModule`.

MVC 5 and Web API 2 controller extraction is deliberately deterministic. Archon detects controller classes from naming, base-type text, and source location hints, then emits `Controller` nodes with framework metadata values `ASP.NET MVC 5` or `ASP.NET Web API 2`. Action endpoints are emitted only when attribute route evidence exists, such as `[Route("orders/{id}")]` or `[Route("api/customers/{id}")]`; the action endpoint records `controllerName`, `actionName`, `handlerSymbol`, `httpMethod`, and `routeTemplate`, and the controller declares the endpoint through `DECLARES_ENDPOINT`. Conventional route tables such as `{controller}/{action}/{id}` are preserved as explicit unknown endpoint facts rather than expanded into invented endpoints, because one convention pattern can represent many runtime URLs that are not deterministic from the route string alone.

This classic guidance belongs on the runtime foundation page because it teaches contributors how legacy runtime artifacts map into the shared graph vocabulary. No new wiki page was needed for Work Item 3 because classic ASP.NET extraction is a runtime foundation concept rather than a separate operational workflow. `wiki/home.md` remains a landing page and should link readers here rather than carrying detailed classic extraction rules.

## Console entry-point extraction

Console entry-point extraction identifies where execution begins for applications that start from a command-line process rather than from an HTTP request pipeline. An **entry point** is the method or source file that the .NET runtime calls first when a console application starts. In C# that entry point is commonly an explicit `static Main` method, but C# can also use **top-level statements**, which are statements written directly in `Program.cs` and compiled by the C# compiler into an implicit `Main` method. In VB.NET the common entry-point shape is `Sub Main` or `Function Main`, often inside a module. Archon treats all of these as static source evidence. It does not execute the console application, evaluate command-line arguments, run the compiler output, infer environment-specific startup behavior, or inspect Archon's own host projects unless those projects are part of the submitted extraction input.

Target repository context is important for this slice. A **target repository context** is the accepted repository root, submitted solution path list, and project path carried by the extraction request. The WP008 runtime stage reads only source documents loaded from those submitted project declarations. That boundary is how Archon distinguishes the application being analyzed from Archon host code, test harness code, package cache files, or arbitrary directories on the developer machine. The C# and VB.NET semantic documents are still lightweight static inputs: Roslyn provides syntax trees and opportunistic symbols, but Archon does not restore packages or run MSBuild targets to decide which entry point will win at build time.

For an explicit C# or VB.NET `Main` method, Archon emits a `Method` node with `runtimeKind` set to `ConsoleEntryPoint`, `runtimeClassification` set to `ConsoleApplication`, `detectionMode` set to `MainMethodSymbol`, and method identity in `entryPointSymbol` and `handlerSymbol` metadata. When a containing type or module is visible, Archon also emits a `Type` node and connects the project to the type and the type to the method with direct `CONTAINS` relationships. For a C# top-level statement file, Archon emits a `Method` node whose display name is `<top-level statements>` and whose stable identity uses the project key plus the normalized repository-relative source file path. That file-path identity avoids depending on compiler-generated type names that can change across compiler versions.

Stable identity follows the same machine-independent rule as endpoint extraction. Explicit entry-point stable keys are scoped by project stable key plus fully qualified method identity when Roslyn can provide one, and by a repository-relative fallback method location when symbol binding is incomplete. Top-level statement stable keys are scoped by project stable key plus normalized top-level-statement file path. Evidence records store repository-relative source paths, one-based line spans, the source symbol name or `<top-level statements>` marker, bounded snippet previews, and SHA-256 snippet hashes. If more than one candidate entry point is visible for the same project, Archon emits the candidate facts with medium confidence and explicit unknown state explaining that multiple console entry-point candidates were detected. It does not guess which method the project file or compiler would select. The recommended ambiguity fixture places two valid `Main` methods in one project and asserts that both method facts survive with the same unknown reason; that pattern is preferable to expecting the extractor to mimic compiler entry-point selection.

This console guidance belongs on the runtime foundation page because entry points define runtime startup behavior and use the same graph, evidence, confidence, and unknown-state vocabulary as endpoint and classic runtime extraction. No dedicated `runtime-extraction.md` page was created because the runtime foundation page remains the coherent topic page for current runtime concepts. `wiki/home.md` remains a concise landing page and does not carry these detailed startup semantics.

## Worker hosted-service extraction

Worker hosted-service extraction identifies long-running background components that participate in the .NET generic host lifecycle. A **hosted service** is a service type that implements `Microsoft.Extensions.Hosting.IHostedService`; a **background service** is a hosted service that derives from `Microsoft.Extensions.Hosting.BackgroundService`; and a **worker service** is a project that uses the generic host to run background work without exposing an HTTP endpoint as its primary runtime surface. Archon treats these as static source and prior-graph facts. It does not construct the generic host, resolve the service provider, start background loops, call `StartAsync`, call `ExecuteAsync`, evaluate timers, or run target application code.

The worker slice scans submitted C# semantic documents for hosted-service implementation classes. When a class implements `IHostedService`, Archon emits a `HostedService` node with `runtimeKind` set to `HostedService`. When a class derives from `BackgroundService`, Archon emits a `HostedService` node with `runtimeKind` set to `BackgroundService` and `backgroundService` metadata set to `true`. The implementation type is also emitted as a `Type` node, and lifecycle methods named `StartAsync`, `StopAsync`, or `ExecuteAsync` are emitted as `Method` nodes. Direct `DEPENDS_ON` relationships connect the hosted-service runtime fact to its implementation type and execution methods, preserving the distinction between the runtime role and the source symbols that implement that role.

Generic host setup is represented as project-level runtime metadata because the current graph contract does not define a dedicated host-builder node kind. Calls such as `Host.CreateDefaultBuilder`, `Host.CreateApplicationBuilder`, `ConfigureServices`, `Run`, `RunAsync`, `UseWindowsService`, and `UseSystemd` can contribute `runtimeKind` metadata of `WorkerServiceHost` and a `genericHostSetupCalls` source-order list on the project fact. This metadata means Archon saw static host setup evidence; it is not a claim that every branch, environment-specific service registration, or hosted-service instance will execute at runtime.

Registration correlation uses the accumulated graph snapshot rather than re-running dependency-injection logic inside the worker extractor. WP007 emits hosted-service registrations such as `AddHostedService<T>()` as `REGISTERED_AS_SERVICE` relationships with hosted-service metadata. WP008 reads those prior facts and correlates them with source-proven implementation types. A hosted-service source fact is still emitted when no matching registration is found, but it carries explicit unknown state and a warning explaining that no matching `AddHostedService` registration fact was available. If multiple hosted-service registrations match the same implementation, Archon preserves the fact with explicit unknown state instead of guessing the active registration. When exactly one prior registration matches, metadata records `registrationCorrelated`, `registrationEdgeStableKey`, `registrationMethod`, and `registrationLifetime` so downstream query and reporting work can navigate from runtime behavior to composition evidence.

This worker guidance belongs on the runtime foundation page because worker services are another runtime startup model alongside HTTP endpoints, classic ASP.NET artifacts, and console entry points. No dedicated `runtime-extraction.md` page was created for Work Item 5 because the runtime foundation page remains the single coherent topic page for current runtime concepts. `wiki/home.md` remains a concise landing page and does not carry these detailed hosted-service semantics.

## Non-HTTP runtime consumer extraction

Non-HTTP runtime consumer extraction identifies runtime behavior that does useful work without declaring an HTTP route. A **scheduled job** is a method or type registered with a scheduler such as Hangfire or Quartz so work can run at a time or recurrence expression. A **queue consumer** reads messages from a queue, a **topic consumer** reads messages from a topic or subscription, and a **message handler** is the method or class that processes those messages. Archon treats all of these as static source facts. It does not connect to queues, topics, brokers, scheduler services, Windows services, operating-system service managers, or databases while extracting these facts.

The current non-HTTP slice recognizes common C# source shapes rather than attempting a universal framework simulation. Hangfire-style `RecurringJob.AddOrUpdate` calls and Quartz-style scheduler registration calls can emit `Method` facts whose metadata has `runtimeKind` set to `ScheduledJob`, the scheduler technology, detection mode, schedule expression when it is a compile-time literal, and confidence explanation. The current graph contract does not define a dedicated scheduled-job node kind, so the scheduled executable is represented as a method-level runtime fact. If the scheduler call proves that scheduled work exists but the target method cannot be resolved, Archon preserves the source evidence and emits explicit unknown state instead of inventing a handler name. If the scheduled method is visible but the schedule expression is computed, Archon still records the scheduled method fact and omits `scheduleExpression` metadata rather than copying a job identifier or placeholder value into that field. This distinction lets contributors query scheduled work without trusting an unsupported cron expression.

Messaging consumers use the graph's queue and topic vocabulary. Source calls such as Azure Service Bus `CreateProcessor` or `CreateReceiver`, MassTransit-style receive endpoints, or subscription-style setup can emit `Queue` or `Topic` nodes with metadata such as `runtimeKind`, `transportKind`, `queueName`, `topicName`, `subscriptionName`, `detectionMode`, and `confidenceReason`. A one-argument Azure Service Bus processor call such as `client.CreateProcessor("orders")` is treated as queue evidence. A two-argument processor call such as `client.CreateProcessor("orders-topic", "billing-subscription")` is treated as topic/subscription evidence and stores the topic and subscription names separately. When source assigns a processor event such as `ProcessMessageAsync += HandleOrderAsync`, Archon emits a `Method` node for the handler and a direct `HANDLES` relationship from the handler to the queue or topic node. If the queue or topic name is computed, configuration-driven, or otherwise not a compile-time string literal, the queue or topic fact carries explicit unknown state and a warning. That preserves the important fact that a consumer exists while refusing to claim a broker target name that source evidence does not prove.

Fixture design for non-HTTP runtime work should keep scheduler, queue, topic, handler, and host-loop patterns small and named after the behavior under test. A literal schedule fixture should assert `scheduleExpression`; a computed schedule fixture should assert the scheduled method remains while the schedule metadata is absent; a literal queue fixture should assert a `Queue` node and optional handler `HANDLES` edge; and a topic fixture should assert a `Topic` node with `topicName` and `subscriptionName`. This naming discipline matters because later query, MCP, rule, metric, diff, and markdown work will depend on the same graph vocabulary and should be able to reuse these fixtures as examples of supported runtime evidence.

Service-style host extraction covers application shapes that run like services but are not necessarily `BackgroundService` implementations. Calls such as `UseWindowsService`, `UseSystemd`, and Topshelf `HostFactory.Run` are represented as project-level runtime metadata because the graph contract does not yet define a dedicated service-host node kind. Custom long-running loops are represented conservatively as method-level `CustomHostLoop` facts when source contains a loop together with delay or cancellation evidence such as `Task.Delay`, `Thread.Sleep`, or `IsCancellationRequested`. These loop facts use medium confidence because a loop is a heuristic signal: it often indicates a polling service or manual runner, but the extractor cannot prove operational deployment behavior without executing the target application, which Archon deliberately avoids.

This non-HTTP consumer guidance belongs on the runtime foundation page because scheduled jobs, message consumers, service-style hosts, and custom host loops are runtime-facing behavior that sits beside HTTP endpoints, classic ASP.NET artifacts, console entry points, and hosted services. No dedicated `runtime-extraction.md` page was created for Work Item 6 because the existing runtime foundation page remains coherent and can teach the runtime model in one sequence. `wiki/home.md` remains a concise landing page and does not carry these detailed scheduler, broker, or host-loop semantics.

## Aspire AppHost

The **AppHost** is the Aspire project in `src/Archon`. Aspire uses an AppHost to describe a local distributed application: which services, containers, and dependencies should run together for a developer. Archon's AppHost is also the **composition root**, which means it wires resources together but does not implement business behavior.

The current AppHost composes four resources:

- `neo4j`, a Neo4j container resource.
- `ArchonApi`, the API host project resource.
- `ArchonMcp`, the MCP host project resource.
- `ArchonExplorer`, the Vite-hosted React workbench shell resource.

The AppHost establishes the local runtime seam. It must remain composition-only. It may configure resource relationships and health checks, but it must not contain extraction rules, API endpoint handlers, graph persistence code, domain logic, or MCP tool behavior.

ArchonExplorer is declared through Aspire's JavaScript hosting support as a **Vite resource**, which means the AppHost starts the frontend development server from `src/ArchonExplorer` instead of embedding browser assets into an ASP.NET Core host. The AppHost supplies the safe `VITE_ARCHON_API_BASE_URL` development environment value from the `ArchonApi` HTTP endpoint and waits for the API resource so the dashboard presents the shell alongside the API, MCP host, and Neo4j container. This is a composition relationship only. React components, frontend routes, API client behavior, server-state queries, and workbench state remain outside the AppHost and belong in the frontend or later application layers.

## Local Neo4j runtime seam

Neo4j is a graph database. Archon uses it as the system of record for deterministic architecture facts. The AppHost uses Aspire's generic container support with the official `neo4j:latest` image.

Neo4j starts in secured mode. The AppHost reads the `neo4j-username` and `neo4j-password` Aspire parameters from `src/Archon/appsettings.json` and uses them to set the container's `NEO4J_AUTH` value. The password parameter is marked as secret in the Aspire resource graph so the same parameter flow can later move to user secrets or another secure provider without changing the composition contract.

The local Neo4j container uses named Docker volumes for `/data`, `/logs`, `/var/lib/neo4j/import`, and `/plugins`. The data volume is what keeps extracted Archon graph records available across normal AppHost or container restarts. If a contributor intentionally wants a clean local graph, they should use the guarded graph recreation workflow or explicitly remove the `archon-neo4j-data` Docker volume after stopping the AppHost. Restarting the AppHost alone should not erase persisted graph records.

The AppHost binds Neo4j's HTTP browser endpoint to `localhost:7474`, binds Bolt to `localhost:7687`, and advertises those host-reachable addresses to Neo4j. If you open the Neo4j Browser during manual verification, connect to `bolt://localhost:7687` with the configured `neo4j-username` and `neo4j-password` values. The direct Bolt URL avoids routing-discovery errors that can appear when Browser is pointed at a routing-style `neo4j://` URI for this local single-container instance.

## Manual AppHost verification

Manual AppHost verification is useful for local runtime exploration but must not be used as an automated build or test step because it starts a long-running distributed application and waits for manual shutdown.

Before running the AppHost, ensure Docker Desktop or another OCI-compatible container runtime is available. Then run:

```powershell
dotnet run --project .\src\Archon\Archon.csproj
```

When the Aspire dashboard opens, confirm that `neo4j`, `ArchonApi`, `ArchonMcp`, and `ArchonExplorer` appear as resources. No `ArchonUi` or Discovery UI resource should appear. The API and MCP resources should expose `/health` checks after they are ready. Open the `ArchonExplorer` resource URL from the dashboard and confirm that the browser renders the foundation workbench shell with safe placeholder states and an API configuration indicator. Stop the AppHost manually after verification, usually with `Ctrl+C` in the terminal or by stopping the debug session in Visual Studio.
