# Neo4j Persistence Foundation

The Neo4j persistence foundation turns assembled graph contracts and operational run-history contracts into durable graph records. It provides validated Neo4j configuration, dependency-injection-owned driver lifecycle, a credential-safe readiness probe, idempotent schema initialization, explicitly guarded graph recreation for local development and tests, snapshot persistence for every currently supported graph section, and durable extraction run history for accepted asynchronous extraction work.

This page assumes familiarity with the [graph domain model](graph-domain-model.md) and [solution architecture](solution-architecture.md). Runtime composition is described in [runtime foundation](runtime-foundation.md), validation commands are collected in [validation and test workflows](validation-and-test-workflows.md), controlled snapshot lifecycle management is introduced here and in the [API extraction workflow](api-extraction-workflow.md), and specialized terms are defined in the [glossary](glossary.md).

## Configuration, driver lifecycle, and health

Neo4j host configuration is represented by the `Neo4j` configuration section. It contains the Bolt-compatible `Uri`, target `Database`, `Username`, `Password`, `ConnectionTimeout`, `MaxTransactionRetryTime`, optional `EncryptionMode`, and `PersistenceBatchSize`. A **Bolt-compatible URI** is the address used by the Neo4j driver protocol, such as `bolt://localhost:7687`; it is separate from the HTTP browser endpoint on port `7474`.

The adapter validates these settings before creating the driver and reports only safe setting names and structural problems. Password values and other secret material must come from secure configuration providers in real environments and must not be copied into logs, validation messages, wiki examples, or test assertions.

The official Neo4j driver is created by infrastructure code and owned by dependency injection. Application and domain projects do not reference Neo4j driver types. Callers open short-lived sessions through the infrastructure session provider and dispose those sessions after each operation.

The Neo4j readiness check opens a read session and runs `RETURN 1 AS healthy`. This checks configuration binding, authentication, network connectivity, database selection, and Cypher execution without requiring schema or architecture data.

`PersistenceBatchSize` controls how many homogeneous snapshot records or relationship endpoint rows the writer sends in one bounded list-parameter persistence statement when a write path has been converted to batched execution. A **list-parameter persistence statement** is a static Cypher statement that receives a list of already-mapped parameter dictionaries and uses `UNWIND` or an equivalent set-oriented shape to process those rows. The setting defaults to `1000` records when omitted, which keeps local-development and container payloads bounded while reducing the overhead of executing one Cypher statement per graph row as optimized write paths are introduced. Repository, solution, architecture node, metric, canonical evidence, snapshot-to-solution relationship, node-to-evidence relationship, metric-to-evidence relationship, and metric-to-node relationship writes use this path. Metrics, architecture nodes, evidence, and support relationships are high-volume snapshot sections in real extraction runs, so converting them to bounded batches materially reduces Cypher execution overhead without changing the graph vocabulary.

Contributors should treat the batch size as infrastructure tuning rather than graph semantics. Changing it must not change stable keys, evidence deduplication, relationship identity, snapshot validation, or the single-transaction success rule. A smaller value can be useful when a low-resource Neo4j container or constrained development machine needs smaller parameter payloads for troubleshooting. A larger value should be chosen cautiously because fewer Cypher executions can also mean larger in-memory parameter lists and more transaction pressure. Invalid values such as zero or negative numbers are rejected during options validation before the writer can start a persistence attempt.

## Schema initialization

A **graph schema** is the set of constraints and indexes that make graph writes safe and queryable. A **constraint** is a rule enforced by Neo4j, such as “repository stable keys must be unique.” An **index** is a lookup structure that helps later queries find records efficiently by stable key, snapshot scope, kind, status, confidence, knowledge classification, or fingerprint.

Schema initialization is exposed through the application-layer `IArchitectureGraphInitializer` port and implemented by `Neo4jGraphInitializer` in `Archon.Infrastructure.Neo4j`. This preserves Onion Architecture: application and host code can ask for graph initialization without depending on Neo4j driver types, while the infrastructure adapter owns the Cypher statements.

Initialization is **idempotent**, meaning it can run repeatedly against the same database without failing merely because expected constraints and indexes already exist. That property is important for local development, CI, and future startup flows because contributors should be able to verify or repair schema state without manually deleting the database.

The initialized graph uses stable labels such as `ArchonRepository`, `ArchonSolution`, `ArchonSnapshot`, `ArchonNode`, `ArchonRelationship`, `ArchonEvidence`, `ArchonRule`, `ArchonFinding`, `ArchonMetric`, `ArchonGeneratedSummary`, `ArchonExtractionRun`, and `ArchonExtractionRunRequest`. Constraint and index names use stable `archon_` prefixes, such as `archon_repository_stable_key_unique`, `archon_node_kind_index`, and `archon_extraction_run_run_id_unique`. Stable names matter because Neo4j Browser and `SHOW CONSTRAINTS` / `SHOW INDEXES` output can be compared directly with the source catalog in `Neo4jSchemaStatementCatalog`.

## Guarded graph recreation

Graph recreation is a separate maintenance workflow exposed through the application-layer `IArchitectureGraphRecreator` port and implemented by `Neo4jGraphRecreator`. **Graph recreation** means deleting Archon-owned graph records and then recreating the required constraints and indexes.

Recreation is destructive by design and exists only for local development and automated integration tests where a clean Archon graph is needed quickly. It is not a schema migration, not a data repair operation, and not a production management endpoint. A migration changes stored data or schema from one version to another while preserving intended information. Recreation intentionally discards Archon graph records, so it must never substitute for future migration planning.

The recreation guard is deliberately explicit. Callers must provide the exact confirmation phrase `DELETE ARCHON GRAPH DATA AND RECREATE SCHEMA` through `GraphRecreationRequest`. Near misses, different casing, missing words, and trailing spaces are rejected before a write session opens. Resolving `IArchitectureGraphRecreator` from dependency injection is not enough to erase data, and no API route, health check, snapshot writer, or startup hook invokes it in the current implementation.

When authorized, recreation deletes nodes carrying Archon-owned labels from the closed schema catalog and uses `DETACH DELETE` so relationships attached to deleted nodes are removed in the same clear operation. The label list comes from `Neo4jSchemaNames`; contributors must not extend this workflow with caller-provided labels or ad hoc dynamic Cypher. After clearing data, recreation runs the same idempotent initializer so the database remains ready for persistence tests.

## Extraction run history persistence

Extraction run history persistence stores operational lifecycle records beside snapshot graph records in the same Neo4j database. An **operational lifecycle record** is the durable account of one accepted extraction request: when it was accepted, what safe request summary was retained, which lifecycle status it has reached, what progress is visible, which warning and error counts were recorded, and which snapshot stable key was produced when completion succeeded. This record is intentionally separate from the architecture snapshot. A failed or cancelled run can remain queryable even when no `ArchonSnapshot` was produced, and a completed run can link to the produced snapshot without making snapshot deletion or graph cleanup erase the historical fact that the run occurred.

The run-history adapter implements the application-layer `IExtractionRunHistory` port. The API and application layers therefore continue to speak in application-owned contracts such as `ExtractionRun`, `ExtractionRunId`, and `ExtractionRunRequestSummary`; they do not depend on Neo4j sessions, transactions, raw records, or driver-specific exceptions. The infrastructure adapter opens Neo4j sessions through the shared session provider, initializes schema idempotently before writes, and uses parameterized static Cypher built from schema-name constants. Caller values such as repository paths, solution paths, request metadata keys, progress messages, and snapshot stable keys are passed as parameters rather than interpolated into Cypher.

Accepted run creation writes an `ArchonExtractionRun` node and an associated `ArchonExtractionRunRequest` node in one write transaction. The run node is merged by the public `runId` property and stores lifecycle fields such as `status`, `startedUtc`, optional `completedUtc`, progress stage, progress message, progress percentage, progress last-updated timestamp, warning count, error count, optional `snapshotStableKey`, and compact serialized diagnostic sections. The request node is also merged by `runId` and stores the credential-safe request summary: normalized repository root directory, normalized solution paths, optional branch name, optional commit SHA, optional requested-by value, and metadata keys. It does not store metadata values. This distinction protects callers who use metadata for local correlation, automation context, or other values that may not be safe as durable operational history.

Progress and terminal updates replace the run node's current lifecycle properties while preserving the associated request summary. This replacement style matches the immutable application run model: orchestration creates a new run snapshot for each visible status change and asks the store to persist that snapshot. Repeated updates for the same public run identifier remain idempotent at the graph identity level because the adapter uses `MERGE` on `runId`.

Produced snapshot linkage is deliberately narrower than storing a snapshot stable key. The run node stores the public `snapshotStableKey` property whenever the application run snapshot carries one, because that value is part of the status and history contract. The `PRODUCED_SNAPSHOT` relationship is created only for a completed run and only when Neo4j can match an existing `ArchonSnapshot` node by that same stable key. This keeps failed and cancelled runs visible without a snapshot, keeps a completed run's public identity readable if the snapshot node is unavailable, and avoids inventing placeholder snapshot nodes from run-history data. If a later terminal update removes the snapshot identity or no longer represents a completed run, the adapter removes stale produced-snapshot relationships while preserving the run and request records.

Recent-history reads query `ArchonExtractionRun` records in newest-first order using `startedUtc` and the public run identifier as a deterministic tie-breaker. Individual status reads match by `runId` and follow the `HAS_EXTRACTION_RUN_REQUEST` relationship to reconstruct the accepted request summary. These reads are controlled adapter operations, not arbitrary graph queries: callers can ask for one run by public id or a bounded recent list, and the adapter maps Neo4j data back to application models without exposing Neo4j internal node IDs.

Diagnostics are currently stored as compact JSON properties on the run node rather than as separate diagnostic child nodes. This shape is the documented compact equivalent for the current query surface: status and history need to reconstruct the complete diagnostic collections for one run, while no current endpoint queries individual diagnostic records independently by category or timestamp. The compact properties preserve warning diagnostics, error diagnostics, top-level timing diagnostics, and the nested persistence diagnostic breakdown without expanding the graph model before those child-node query requirements exist. The JSON contains only application-owned diagnostic records and safe messages. It must not contain raw Cypher, stack traces, driver exception strings, credentials, connection strings, or environment dumps. If future work needs queryable diagnostic children, it can introduce `ArchonExtractionRunDiagnostic` nodes while preserving the current public run-history contract and migrating the compact data carefully.

Dependency injection follows the same outer-boundary rule as snapshot persistence. `AddArchonNeo4j` registers the Neo4j-backed run-history implementation, while the extraction API module registers the in-memory run-history implementation only as a fallback when no host has already supplied `IExtractionRunHistory`. The snapshot writer follows the same pattern: the extraction and query modules can supply `InMemoryArchitectureSnapshotWriter` for focused tests and lightweight local composition, but a Neo4j-composed host resolves `IArchitectureSnapshotWriter` to `Neo4jArchitectureSnapshotWriter`. This lets local tests and lightweight hosts remain simple without forcing production hosts back to process memory after Neo4j infrastructure has been composed.

## Snapshot lifecycle listing for management

Snapshot lifecycle listing is the read-only management view over persisted `ArchonSnapshot` records. A **snapshot lifecycle row** is not a full architecture snapshot and not a Neo4j node dump. It is a bounded operational summary containing the public snapshot stable key, repository stable key, optional solution stable key, lifecycle status, branch name, commit SHA, started and completed timestamps, and warning and error counts. The row exists so contributors and management API consumers can answer “which snapshots are currently persisted?” without running arbitrary Cypher or reading high-volume architecture facts.

The management application layer now reads lifecycle rows through the `ISnapshotLifecycleQuery` port. That port is deliberately separate from `IArchitectureSnapshotWriter`. A writer persists assembled snapshots; the lifecycle query lists already-persisted snapshot headers. Keeping the two responsibilities separate removes the old assumption that management listing could inspect `InMemoryArchitectureSnapshotWriter` directly. In-memory lifecycle listing remains available as a lightweight fallback for focused tests and hosts without Neo4j, but it is only an adapter behind the same application port. When `AddArchonNeo4j` is composed, dependency injection registers the Neo4j-backed lifecycle query implementation so `GET /management/snapshots` reads graph-backed state. Production-style composition tests should therefore assert the application ports, not the concrete module fallback objects: `IArchitectureSnapshotWriter`, `IExtractionRunHistory`, `ISnapshotLifecycleQuery`, and `ISnapshotDeletionStore` should all resolve to Neo4j adapters when Neo4j configuration is present.

The Neo4j lifecycle query uses static, parameterized Cypher with approved filters only: repository stable key, solution stable key, status, started timestamp range, commit SHA, and a bounded take limit. It matches `ArchonSnapshot` nodes by stable public properties, optionally follows `INCLUDES_SOLUTION` relationships to a solution record, and projects named scalar fields rather than returning graph nodes. It orders results newest first by `startedUtc` and then by snapshot stable key as a stable tie-breaker. Neo4j internal node IDs, relationship IDs, raw records, raw Cypher, driver exception text, connection strings, and credentials remain inside infrastructure code and logs.

Warnings from lifecycle listing describe response completeness, not database internals. If more rows match than the requested take limit allows, the response carries a safe truncation warning. If a row has incomplete lifecycle timestamps, the response can report that lifecycle data is incomplete without exposing the stored record or the query text. These warnings are intentionally conservative because the management API is an operations surface: callers need enough information to narrow or troubleshoot their request, but they should not receive infrastructure implementation details.

Management readiness probes the same lifecycle query port with a one-row bounded request. A Neo4j-composed host therefore reports the lifecycle dependency as available when the graph-backed lifecycle query can run, even if no snapshots are currently present. Readiness no longer degrades merely because the active snapshot writer is not the in-memory fallback. That distinction matters for production-like local development: an empty durable graph can still be ready to answer lifecycle queries, while absence of process-local writer state is no longer a dependency failure.

## Snapshot deletion for management

Snapshot deletion is the controlled destructive counterpart to lifecycle listing. A **snapshot-scoped subgraph** is the set of records whose lifecycle is owned by one snapshot stable key: the `ArchonSnapshot` header itself, snapshot-scoped architecture nodes, relationship-node records, evidence, findings, metrics, generated summaries, and direct support relationships attached to those records. Deleting a snapshot removes that scoped content so a local development database can be kept small without recreating the entire Archon graph.

The management application layer asks the storage-neutral `ISnapshotDeletionStore` port to delete one snapshot by public stable key. The port deliberately accepts only a normalized snapshot stable key and returns safe counts. It is not a general graph mutation surface, and it does not accept caller-supplied labels, relationship types, property names, Cypher fragments, retention filters, date scopes, repository scopes, shell commands, or dry-run expressions. In Neo4j composition, `Neo4jSnapshotDeletionStore` initializes schema, opens a write session, uses static parameterized Cypher, and deletes the snapshot-scoped records in a controlled transaction. Lightweight tests and hosts without Neo4j can use the in-memory fallback behind the same port, but that fallback is local-only and reports conservative count precision.

Deletion preserves shared and operational records by default. Repository and solution records are not deleted merely because a snapshot referenced them, because those records can be shared by other snapshots. Versioned rule catalog records are global analysis definitions and are likewise preserved. Extraction run records are operational lifecycle records, not snapshot content, so deletion does not remove `ArchonExtractionRun` or `ArchonExtractionRunRequest` nodes. When a completed run had a `PRODUCED_SNAPSHOT` relationship to the deleted `ArchonSnapshot`, deleting the snapshot removes that relationship with the snapshot node, but the run keeps its public `snapshotStableKey` property. Contributors should read that retained value as historical identity: the run produced a snapshot with that stable key, but the graph snapshot is now unavailable because a management cleanup operation removed it.

The same deletion store also supports confirmed delete-all cleanup. Delete-all is intentionally narrower than a retention engine: it removes every `ArchonSnapshot` record and every snapshot-scoped subgraph in the configured database after the management service has validated the exact confirmation phrase `delete-all-snapshots`. It does not accept repository, solution, date, status, commit, label, property, dry-run, or arbitrary filter inputs. That strict shape is deliberate. The current product need is local development database cleanup when accumulated snapshots have become too large or stale to be useful, not an operator-tuned retention policy. A dry-run for this operation would produce large preview counts without giving the caller a meaningful partial-deletion decision, and scoped deletion policies need their own future specification before they become safe operational behavior.

Delete-all uses the same preservation boundary as delete-one. Repository, solution, rule catalog, extraction run, and extraction run request records are preserved by default. Produced-snapshot relationships disappear with the deleted snapshot nodes, but each preserved run keeps its public `snapshotStableKey` property when it had one. Contributors should interpret that retained value as historical run evidence rather than as proof that the snapshot graph is still available. The aggregate response reports how many snapshot headers were deleted, how many snapshot-scoped data nodes were deleted, how many relationships were counted for removal where practical, how many preserved runs referenced deleted snapshots, safe warnings, and audit metadata at the management API boundary.

Deletion responses report public identity or aggregate counts only. They must not include Neo4j internal IDs, raw records, raw Cypher, driver exceptions, connection strings, stack traces, or deleted evidence snippets. A not-found delete-one snapshot is reported as a controlled management validation problem rather than a storage exception. A confirmed delete-all call against an empty graph is a successful no-op with zero counts, because the caller intentionally requested global cleanup and there was no snapshot-scoped data to remove.

For manual delete-one verification, seed or produce a snapshot in a local or test Neo4j database, call the delete-one management endpoint with the URL-encoded snapshot stable key, list lifecycle rows again, and then inspect the producing run through status or run history. The expected result is that `GET /management/snapshots` no longer returns the deleted snapshot, snapshot-scoped graph records for that stable key are gone, shared repository/solution/rule records remain, and the producing run remains queryable with the same public snapshot stable key. For manual delete-all verification, seed multiple snapshots in a disposable local or development database, call the delete-all management endpoint with the exact confirmation body, list lifecycle rows again, and inspect run history. The expected result is that no snapshot lifecycle rows or snapshot-scoped records remain, while run history and shared records are still queryable. Use these operations only against local or development data unless a deployment has an explicit operational policy for destructive snapshot cleanup.

## Snapshot persistence

Snapshot persistence is exposed through the application-layer `IArchitectureSnapshotWriter` port and implemented by `Neo4jArchitectureSnapshotWriter`. **Snapshot persistence** means taking an assembled `ExtractedArchitectureSnapshot` from the application layer and writing its graph facts to Neo4j using stable logical identities.

The current writer persists repositories, solutions, one snapshot header, architecture nodes, architecture relationship records, evidence nodes, versioned rule catalog entries, finding records, metric records, generated-summary records, snapshot-to-solution relationships, node-to-evidence support relationships, relationship endpoint relationships, relationship-to-evidence support relationships, finding-to-rule relationships, finding-to-primary-node relationships, finding-to-evidence support relationships, metric support relationships, and generated-summary target relationships.

The write order matters because graph records reference one another. Repositories and solutions are written first, then the snapshot header, architecture nodes, canonical evidence, architecture relationship nodes, global rule catalog entries, snapshot-scoped findings, metrics, generated summaries, and finally supporting relationships. The writer initializes schema before the write transaction and then uses a single Neo4j write transaction for supported snapshot data. If the transaction fails, the writer does not return a successful completed result for partial graph data.

Architecture nodes are written with bounded `UNWIND $nodes AS nodeRow` batches rather than one Cypher execution per node. `UNWIND` is the Cypher operation that expands a list parameter into rows inside the database engine, which lets the writer send one static statement plus a bounded list of mapped node dictionaries. The merge identity remains the snapshot stable key plus the node stable key, so rerunning persistence for the same snapshot updates the same `ArchonNode` records instead of creating duplicates. The batched statement sets the same normalized properties as the earlier per-record statement: node kind, display name, qualified name, search name, language, optional project and parent stable keys, knowledge classification, ownership, external category, confidence, unknown-state fields, optional primary evidence stable key, deterministic metadata JSON, and fingerprint. Nullable values are passed as parameters exactly as before; batching changes how many rows a statement writes, not what an absent language, parent, ownership, or evidence value means.

Canonical evidence records are also written with bounded `UNWIND $evidenceRecords AS evidenceRow` batches. Evidence canonicalization still happens before this write stage. **Evidence canonicalization** is the adapter step that collapses duplicate evidence payloads within one snapshot to the first canonical evidence stable key and records a stable-key remapping for every duplicate input. Only canonical records are sent to the evidence batch, and later support-relationship statements use the remapping so nodes, metrics, findings, and relationship nodes continue to point at the canonical `ArchonEvidence` record. The merge identity remains the snapshot stable key plus the canonical evidence stable key, and the batched statement preserves evidence kind, repository-relative file path, optional source line span, optional symbol context, optional snippet hash and preview, knowledge classification, confidence, unknown-state fields, deterministic metadata JSON, and fingerprint.

Metric nodes are written with bounded `UNWIND $metrics AS metricRow` batches rather than one Cypher execution per metric. The merge identity remains exactly the same: `snapshotStableKey` plus the metric `stableKey`. The batched statement sets the same normalized properties as the earlier per-record statement, including metric kind, scope kind, optional node target, optional relationship target, optional primary evidence key, display name, numeric value, text value, unit, confidence, unknown-state fields, deterministic metadata JSON, and fingerprint. These batched node, evidence, and metric writes are performance shape changes, not graph model changes. Numeric-only metrics, text-only metrics, mixed numeric/text metrics, node-targeted metrics, relationship-targeted metrics, evidence-backed metrics, nullable architecture-node fields, and nullable evidence source-location fields continue to persist through stable public keys, and Neo4j internal IDs remain hidden from application contracts, tests, API responses, and documentation examples.

Support relationships are written after the endpoint records exist. A **support relationship** is a direct Neo4j relationship that explains or connects an already-persisted fact, such as a snapshot including a solution, a node being supported by evidence, a metric being supported by evidence, or a metric measuring a node. The current writer batches four support relationship families with static `UNWIND $relationships AS relationshipRow` statements: snapshot-to-solution `INCLUDES_SOLUTION`, node-to-evidence `SUPPORTED_BY_EVIDENCE`, metric-to-evidence `SUPPORTED_BY_EVIDENCE`, and metric-to-node `MEASURES_NODE`. A **relationship family** is one of those grouped relationship write shapes with the same source label, target label, relationship type, endpoint keys, and diagnostic timing name. Grouping by family keeps the Cypher static and makes timing evidence easier to interpret than one large mixed relationship statement.

Batched relationship writes still match endpoints by stable-key properties and snapshot scope rather than by Neo4j internal IDs. For example, a metric-to-evidence row carries the snapshot stable key, metric stable key, and canonical evidence stable key; the Cypher statement matches the `ArchonMetric` and `ArchonEvidence` nodes by those properties and then uses `MERGE` to create the link idempotently. `MERGE` is important because repeated persistence attempts for the same snapshot must update or confirm the same graph shape instead of creating duplicate relationships. Relationship batches also return a matched-row count for each bounded statement. The writer compares that count with the number of submitted endpoint rows and fails the write transaction if required endpoints are missing, so a relationship batch cannot silently become a successful no-op for incomplete graph data. Controlled pre-transaction validation also rejects metrics that target missing architecture nodes before the writer opens the transaction.

Evidence canonicalization still applies before relationship rows are materialized. If two supplied evidence records have equivalent payloads and only the first canonical evidence node is persisted, node and metric support rows are remapped to the canonical evidence stable key. Contributors reading the graph should therefore expect support links to point to persisted canonical `ArchonEvidence` records, not necessarily to every input evidence stable key that appeared before deduplication.

Stable keys remain the only logical identities used by the writer. Repository, solution, and snapshot records are merged by global stable keys. Architecture nodes and evidence are merged by snapshot scope plus stable key. Neo4j internal IDs are never surfaced in persistence results, tests, API-facing values, or documentation examples.

The persistence result can carry an application-owned diagnostic breakdown for status polling. A **persistence diagnostic breakdown** is a run-lifecycle observation that explains the persistence handoff; it is not part of the persisted architecture snapshot and it is not a Neo4j schema concept. The breakdown contains ordered sub-stage timings, count values, and a completion flag. Stage names use scoped display-style names such as `Persistence.PrepareSnapshot`, `Persistence.WriteWarnings`, `Persistence.Commit`, and `Persistence.Total` so contributors can relate them to the existing top-level `Persistence` timing without confusing them for separate extraction pipeline stages.

Count values describe the volume handled by the same persistence attempt. Repository, solution, project, file, node, relationship, evidence, finding, warning, error, metric, generated-summary, operation, batch, metadata-entry, and serialized-payload measurements are represented at the application boundary when the writer can provide them accurately. Known empty collections should be reported as zero; unknown or unmeasured values should remain `null`. This current diagnostic contract is intentionally conservative because collecting diagnostics must not require reading the graph back from Neo4j or materializing large duplicate payloads solely to populate a status response.

The current Neo4j writer collects these diagnostics during the real handoff path. A **diagnostic collector** is the small per-write object that starts before snapshot preparation, uses a monotonic elapsed-time clock for measured durations, and appends timings in the order sub-stages finish. It records preparation and validation as `Persistence.PrepareSnapshot`, schema initialization and synchronous index/constraint work as `Persistence.Indexing`, evidence canonicalization as `Persistence.MaterializePayload`, the already-materialized stable-key remapping as `Persistence.NormalizeIdentities`, and write groups such as `Persistence.WriteRepositories`, `Persistence.WriteSolutions`, `Persistence.WriteSnapshotHeader`, `Persistence.WriteNodes`, `Persistence.WriteMetrics`, `Persistence.WriteEvidence`, and `Persistence.WriteRelationships`. `Persistence.WriteNodes`, `Persistence.WriteMetrics`, and `Persistence.WriteEvidence` now measure the full bounded-batch stage for each record family rather than an individual row loop. `Persistence.WriteRelationships` remains an aggregate wrapper around support relationship persistence, and the current writer also emits family-level timings for `Persistence.WriteSnapshotSolutionRelationships`, `Persistence.WriteNodeEvidenceRelationships`, `Persistence.WriteMetricEvidenceRelationships`, and `Persistence.WriteMetricTargetRelationships`. Those family timings are nested persistence diagnostics, not separate top-level extraction stages. They let contributors distinguish solution inclusion, node evidence support, metric evidence support, and metric target-link costs when relationship volume becomes the dominant persistence hotspot. The surrounding Neo4j write transaction is measured as `Persistence.Commit`, which is the durable write finalization boundary for this adapter: once that stage succeeds, the writer can report a completed persistence result. `Persistence.Total` is appended last and represents the whole persistence attempt, including successful and controlled-failure paths.

The optimized persistence path is therefore best read as one atomic handoff with several bounded internal write shapes. A successful default write still reports one `persistenceBatchCount` because the current adapter uses one Neo4j write transaction, even though that transaction may contain many statement batches for nodes, evidence, metrics, repositories, solutions, and direct support relationships. This distinction prevents a common troubleshooting mistake: a contributor should not expect `persistenceBatchCount` to rise merely because `PersistenceBatchSize` split a high-volume record family into several `UNWIND` executions. The value that moves with those internal statement batches is `persistenceOperationCount`, while the value that marks transaction finalization remains `Persistence.Commit`.

The emitted timing names are intentionally stable display names rather than Neo4j method names. `Persistence.PrepareSnapshot` covers application-level validation of the snapshot before any graph write begins. `Persistence.Indexing` covers schema initialization, including constraints and indexes. `Persistence.MaterializePayload` covers canonical evidence preparation from already-materialized snapshot data. `Persistence.NormalizeIdentities` records the identity-normalization step that the adapter can identify without extra work. `Persistence.WriteRepositories`, `Persistence.WriteSolutions`, `Persistence.WriteSnapshotHeader`, `Persistence.WriteNodes`, `Persistence.WriteMetrics`, and `Persistence.WriteEvidence` cover the corresponding node or record groups. `Persistence.WriteRelationships` covers the aggregate direct support relationship stage. `Persistence.WriteSnapshotSolutionRelationships`, `Persistence.WriteNodeEvidenceRelationships`, `Persistence.WriteMetricEvidenceRelationships`, and `Persistence.WriteMetricTargetRelationships` cover the current relationship families inside that aggregate stage. `Persistence.Commit` wraps the Neo4j write transaction, and `Persistence.Total` wraps the full attempt. Future writer slices may add additional scoped `Persistence.*` names for newly separated write groups, but they should preserve this convention and keep detailed persistence timings nested under run diagnostics rather than adding them to the top-level extraction timing list.

The count fields follow the same conservative contract. `repositoryCount`, `solutionCount`, `projectCount`, `fileCount`, `nodeCount`, `relationshipCount`, `evidenceCount`, `findingCount`, `warningCount`, `errorCount`, `metricCount`, and `generatedSummaryCount` describe the graph or diagnostic volumes known from the snapshot and completed writer counters. `metadataEntryCount` reports the number of non-empty metadata objects that can be counted from the in-memory snapshot model. `persistenceOperationCount` reports how many Neo4j statements the writer actually executed when that value is known. As batched `UNWIND` write paths are introduced, one statement that writes many rows counts as one persistence operation because the diagnostic value is meant to explain Cypher execution overhead, not logical row volume. `persistenceBatchCount` continues to describe the write transaction count for the current single-transaction Neo4j writer, so the default successful snapshot write reports one persistence batch even when individual record groups are internally partitioned into several list-parameter batches. `serializedPayloadBytes` remains `null` in the current writer because no large serialized payload is built solely for persistence; a future adapter should only populate it when payload materialization already happened for the write itself. This feature adds diagnostic visibility, not a persistence-throughput optimization by itself, and contributors should compare operation counts with timing evidence before drawing conclusions about throughput.

Manual WP017 performance review should compare the same real repository extraction before and after the optimized writer rather than introducing synthetic large repositories or generated snapshot payloads. The useful comparison fields are the top-level extraction `Persistence` timing, nested `Persistence.Total`, `Persistence.Commit`, `Persistence.WriteNodes`, `Persistence.WriteMetrics`, `Persistence.WriteEvidence`, the relationship-family timings, `persistenceOperationCount`, and `persistenceBatchCount`. A lower operation count shows that fewer Cypher statements were executed, but it does not by itself prove end-to-end throughput improved; contributors should read it together with stage durations because transaction commit, index maintenance, container I/O, or database resource pressure can still dominate the completed run. The focused command sequence and local-output guidance for this comparison are maintained in [validation and test workflows](validation-and-test-workflows.md#wp017-neo4j-persistence-performance-validation).

When closing a persistence-performance change, keep durable guidance on this page and keep measurement procedure on the validation page. The implementation plan may record concise validation outcomes, but it should not become a parallel handbook for interpreting Neo4j diagnostics. If later writer slices batch additional graph sections or split more relationship families, update this current-state explanation and the validation workflow together so contributors can still move from a completed extraction status response to the correct mental model and command sequence.

Not every requested diagnostic stage appears for every snapshot or every adapter. The current writer omits non-applicable stages instead of emitting misleading zeroes for work it did not perform. For example, warning, finding, metadata, generated-summary, or relationship-node write stages are emitted only when the current implementation has a distinct group it can measure accurately. Serialized payload bytes currently remain `null` because the writer maps already-materialized domain objects directly to parameter dictionaries and does not build one large serialized payload. This is intentional: duplicating a large snapshot solely to count bytes would make the diagnostic feature part of the performance problem it is meant to explain.

When reading a slow run, compare the top-level `Persistence` timing in the extraction status with the nested diagnostics rather than summing both levels together. If `Persistence.MaterializePayload` is high, the cost is likely in evidence canonicalization or parameter preparation before database writes. If `Persistence.WriteRelationships` is high relative to `relationshipCount`, inspect the family-level timings to see whether solution inclusion, node evidence support, metric evidence support, or metric target links dominate. For example, a metric-heavy snapshot may show modest `Persistence.WriteMetrics` time for metric node upserts but high `Persistence.WriteMetricEvidenceRelationships` or `Persistence.WriteMetricTargetRelationships` if most metrics also carry evidence and node targets. If `Persistence.Commit` dominates while sub-stage write timings look small, Neo4j transaction finalization, constraint maintenance, container I/O, or database resource pressure is a more likely starting point. These timings are diagnostic evidence, not optimization instructions by themselves; they identify where a contributor should focus a targeted performance review.

Partial diagnostics are useful when persistence fails. A writer can return the timings and counts collected before a controlled failure, and the orchestrator retains those diagnostics with the failed run while keeping the run status `Failed` and leaving `snapshotIdentity` absent. This makes slow or failing persistence more observable without weakening the main transaction rule: Archon still reports a completed extraction only after snapshot persistence succeeds.

The diagnostic path is deliberately defensive around operational edge cases. During persistence, the run lifecycle continues to report the top-level `Persistence` progress stage instead of writing a new lifecycle record for every sub-stage. This avoids flooding the run-history store while still letting the nested diagnostic timings explain the sub-stage sequence after the writer returns. If a writer has not reached diagnostic capture, or if an older writer does not provide diagnostics, the status response keeps `persistenceDiagnostics` empty while still reporting a normal top-level `Persistence` timing and a controlled completed or failed run state. That compatibility rule is important for mixed local development and test fixtures because the diagnostics section is additive rather than a required part of every run record.

Diagnostic collection must not hide the original persistence outcome. When Neo4j schema initialization, session creation, transaction execution, or another infrastructure operation fails, the adapter logs the detailed exception for operators and returns a safe application-owned persistence error with whatever timings and counts had already been collected. The returned diagnostics do not include raw Cypher, Bolt endpoints, driver exception text, connection strings, stack traces, credentials, or environment values. If diagnostic timing or count collection itself can only produce a non-fatal warning while persistence succeeds, that warning is appended through the existing run warning model and does not replace warnings already produced by the extraction pipeline. Contributors reading status output should therefore treat warning counts as accumulated lifecycle context, not as a persistence-only collection.

For troubleshooting, start with the run status and answer three questions in order. First, is the run still in `Persistence`, completed, or failed? The top-level progress and `timings` collection answer that lifecycle question. Second, is `persistenceDiagnostics` present? If it is absent, the run either has not reached persistence, was produced by an older or non-instrumented writer, or failed before diagnostic capture could start. Third, when diagnostics are present, is `completed` true? A false value means the timings and counts are partial evidence only; use the last completed sub-stage and the safe persistence error to decide where to investigate next, but do not infer that snapshot graph content became durable.

## Normalized properties and metadata JSON

The writer preserves the distinction between normalized graph properties and metadata. **Normalized properties** are fields the platform expects to query, compare, or validate directly, such as `stableKey`, `snapshotStableKey`, `nodeKind`, `evidenceKind`, `knowledgeKind`, `confidence`, `hasUnknownData`, and `fingerprint`. **Metadata JSON** is reserved for deterministic extension data that does not belong in those first-class fields.

For example, a project node's `nodeKind` is stored as a Neo4j property because later queries may filter all `Project` nodes. Extractor-specific details that are not part of the shared graph contract remain in `metadataJson`.

Semantic extraction uses the same rule. A compiler-backed C# type declaration is persisted as an `ArchonNode` whose first-class properties include the snapshot stable key, semantic declaration stable key, `Type` node kind, display name, qualified name, language, owning project stable key, confidence, unknown-state fields, evidence key, and fingerprint. Roslyn-specific details such as semantic declaration kind, source language enum value, metadata name, project context, relationship discovery source, and confidence category remain in deterministic metadata JSON. A semantic `CALLS` or `DEPENDS_ON` relationship is persisted as an `ArchonRelationship` node with the shared edge kind and endpoint stable keys rather than as a Roslyn-specific Neo4j label. This keeps the Neo4j adapter generic: it maps supplied graph contracts and does not load Roslyn, inspect syntax trees, or decide semantic meaning.

## Evidence deduplication

Evidence persistence is snapshot-scoped and deduplicated. **Evidence deduplication** means equivalent evidence payloads submitted more than once in the same snapshot collapse to one canonical `ArchonEvidence` node. The canonical identity includes the snapshot stable key and evidence content fields but intentionally excludes the evidence stable key itself.

Node, relationship, finding, and metric support relationships are remapped to canonical evidence records. Because snapshot stable key is part of the deduplication identity, equivalent evidence in a different snapshot remains separate. This preserves historical snapshot isolation while avoiding duplicate evidence records within one snapshot.

## Architecture relationships and the relationship-node pattern

Architecture relationships are persisted through the `ArchonRelationship` label. An **architecture relationship** is the domain fact that one architecture node relates to another: a project references a package, a service calls an endpoint, a component uses a view model, or a repository artifact depends on configuration.

Archon uses a **relationship-node pattern**. Direct Neo4j relationships are useful for simple traversal, but Archon relationships are evidence-backed records with their own stable identity. Neo4j does not let a relationship have outgoing relationships to evidence nodes in the same way a node can. Archon therefore stores each edge as an `ArchonRelationship` node, connects it to the source architecture node with `RELATIONSHIP_SOURCE`, connects it to the target architecture node with `RELATIONSHIP_TARGET`, and connects it to primary evidence with `SUPPORTED_BY_EVIDENCE` when evidence is supplied.

For example, a project-to-package dependency is stored as an `ArchonRelationship` node whose `edgeKind` might be `REFERENCES` or `USES_PACKAGE`. The relationship node points to the project through `RELATIONSHIP_SOURCE`, points to the package through `RELATIONSHIP_TARGET`, and points to project-file evidence through `SUPPORTED_BY_EVIDENCE`. Multiple facts can connect the same source and target because merge identity is the relationship stable key within the snapshot, not the endpoint pair.

The same relationship-node pattern is used for semantic relationships. A method call discovered by Roslyn becomes an `ArchonRelationship` node with `edgeKind` `CALLS`, a source stable key for the calling method declaration, a target stable key for the called method or symbol reference, and a `SUPPORTED_BY_EVIDENCE` link to compiler-symbol source evidence. When semantic extraction can only partially resolve the endpoint, the relationship still carries first-class confidence and unknown-state properties. This allows later queries to distinguish high-confidence compiler-resolved calls from partially resolved or metadata-only relationships without parsing metadata JSON.

## Rules and findings

Rule and finding persistence adds a durable analysis-result layer to the graph. A **rule catalog entry** is a versioned definition identified by `ruleCode` plus `ruleVersion`, such as `ARCHON001` at version `1.0.0`. Rule catalog entries are global `ArchonRule` nodes rather than snapshot-scoped copies. When a rule changes from version `1.0.0` to `2.0.0`, Archon can keep both versions and findings from older snapshots can still point to the exact rule version that classified them.

The current WP012 rule catalog store upserts validated rules through the application-layer `IRuleCatalogStore` port. An **upsert** creates the `ArchonRule` node when the rule code/version pair is absent and updates queryable properties when that exact version already exists. The Neo4j statement uses `MERGE (rule:ArchonRule { ruleCode: $ruleCode, ruleVersion: $ruleVersion })`, so idempotent reloads of the same rule do not create duplicates, while a new version of the same rule code coexists beside the older version. The write stores the rule name, category, severity, default status, enabled flag, description, definition JSON, source URLs JSON, built-in flag, owner scope, and metadata JSON as properties on the versioned catalog node.

Rule catalog persistence is intentionally non-destructive. Disabled rules remain persisted with their `enabled` property set to `false` because disabled catalog history may still be needed to explain old findings or review rule-authoring decisions. A later extraction run that omits a previously persisted rule file does not delete the existing `ArchonRule` node. This behavior is different from guarded graph recreation: recreation is an explicit destructive maintenance operation, while routine catalog loading only upserts the currently loaded validated rules.

A **finding** is a snapshot-scoped concern stored as an `ArchonFinding` node. It preserves the finding stable key, rule code, rule version, severity, status, title, description, knowledge classification, confidence, unknown-state fields, first-seen and latest-seen snapshot keys, suppression reason, suppressed-by actor, affected node stable keys, evidence stable keys, a cross-snapshot history key, deterministic metadata JSON, and fingerprint. The finding stable key remains scoped to the snapshot so each extraction run can store its own durable record; the history key deliberately crosses snapshot scope so equivalent findings can be recognized over time without using Neo4j internal IDs.

Finding links make provenance and evidence explicit. Every persisted finding receives `CLASSIFIED_BY_RULE` to the matching global rule version when that rule exists. A finding can carry one or more affected architecture node stable keys and one or more evidence stable keys; the current Neo4j store creates `PRIMARY_NODE` links to matching snapshot-scoped `ArchonNode` records and `SUPPORTED_BY_EVIDENCE` links to matching snapshot-scoped `ArchonEvidence` records. Those links are created by matching stable properties, not by reading Neo4j internal IDs. The finding node also stores the link stable-key arrays as properties so later query APIs can still return controlled evidence and node references without requiring consumers to issue arbitrary Cypher.

Finding persistence is non-destructive in the same spirit as rule catalog persistence. Upserting the same snapshot stable key and finding stable key updates the finding properties and links; omitting a finding from a later write does not delete older records. When a finding history key appears in a later snapshot, the application layer can carry the first-seen snapshot forward and update the latest-seen snapshot to the current run. That first/latest seen behavior is historical fidelity for analysis results: a contributor can see both when Archon first observed a concern and where it was most recently observed.

Suppression is stored as a lifecycle overlay rather than a destructive delete. A suppression targets a finding history key together with rule code, rule version, and primary node stable key. The persisted suppression stores a reason, suppressed-by actor, and deterministic metadata JSON. When matching findings are upserted or when a suppression is applied after findings already exist, the finding remains present but its status becomes `Suppressed` and the suppression fields are populated. This lets later hotlist and history APIs hide or filter suppressed concerns while still preserving the record for audit, review, and historical explanation.

The current Neo4j query adapter adds a read-only hotlist and rule catalog query seam over these persisted records. The adapter uses static, parameterized Cypher for approved filters only: rule code, version, category, severity, enabled state, built-in state, owner scope, snapshot stable key, finding status, project stable key, affected node stable key, and bounded paging values. It never accepts caller-provided Cypher fragments and does not use Neo4j internal IDs as public identities. Rule results are ordered by rule code and version. Finding results are ordered deterministically by severity, rule code, and finding stable key, and history records are read by finding history key in snapshot-stable-key order. The public behavior of that query surface is described in [hotlist and findings](hotlist-and-findings.md).

## Metrics and generated summaries

A **metric** is a durable `ArchonMetric` node that stores a computed value for a graph, snapshot, project, architecture node, architecture relationship, or modernization scope. Metrics carry metric kind, scope kind, optional node and relationship target stable keys, optional primary evidence, a developer-facing name, numeric value, text value, unit, confidence, unknown-state fields, deterministic metadata JSON, and fingerprint. Persisting metrics lets later diff, API, MCP, report, and hotlist packages retrieve stable historical values instead of recomputing them during every read.

The current metric persistence slice stores the snapshot metric `SnapshotNodeCount`, project-scoped metrics such as `ProjectPackageCount`, `ProjectEndpointCount`, and `ProjectTargetFrameworkRisk`, node-scoped graph metrics such as `GraphFanIn`, `GraphFanOut`, `GraphDegreeCentrality`, `GraphDependencyDepth`, `GraphTransitiveDependencyCount`, `GraphNeighbourhoodSize`, and `GraphCycleParticipation`, and modernization metrics such as `ModernizationLegacyTechnologyCount`, `ModernizationSecuritySensitiveFindingCount`, `ModernizationOutOfSupportTargetCount`, `ModernizationFrameworkOnlyDependencyCount`, `ModernizationDataAccessSpread`, and `ModernizationSharedTableUsageCount` as snapshot-owned outputs. The writer validates that every supplied metric belongs to the snapshot being persisted, writes the metric by snapshot stable key and metric stable key, and creates support relationships when metric evidence or node targets are present. Snapshot-level metrics do not require a node target, while project, repository, solution, and graph metrics target their scoped node through `nodeStableKey`. Metric confidence and unknown state are persisted as first-class properties rather than as metadata, because readers and future diff logic need to distinguish known calculated values from values calculated under incomplete-input conditions.

Metric reads use the same controlled-query principle as hotlist reads. The query adapter exposes bounded, deterministic metric pages for one snapshot stable key with optional metric-kind, scope-kind, and node-target filters. The public parameter is currently named `projectStableKey` because project metrics introduced the filter, but persistence applies it to `metric.nodeStableKey`, so it also filters graph node metrics. It uses static parameterized Cypher and returns stable DTOs rather than raw Neo4j nodes or database-local IDs. The public endpoint surface includes the query-string form `GET /snapshot-metrics?snapshotStableKey=...`, which is the safest option for stable keys containing `://` separators, and a route form for clients whose snapshot identities do not require slash-preserving query encoding.

Dependency cycle reads are derived from persisted snapshot graph facts rather than stored as a separate Neo4j node label in the current slice. This is deliberate: a cycle is a deterministic interpretation of architecture nodes and dependency relationship records, not a new source fact discovered by an extractor. The query API reads the assembled snapshot graph through the application query seam, follows only dependency-like edge kinds, canonicalizes duplicate rotations, and returns `cycle://` stable identities in DTOs. Future infrastructure adapters can optimize this read path, but they should preserve the same public semantics: stable node keys, stable edge keys, evidence references, confidence, unknown state, truncation metadata, and no Neo4j internal IDs.

Architecture-rule result reads are also derived from persisted snapshot graph facts in the current slice rather than stored as a separate Neo4j label. The application query service evaluates generic built-in checks from the completed snapshot's architecture nodes, relationship records, metrics, findings, runtime metadata, semantic metadata, and persisted rule definitions. The returned `architecture-rule://` identities are therefore stable public query results, not Neo4j internal IDs and not separate source facts. Future persistence optimization may cache these results, but it must preserve the same rule code, category, status, target stable key, contribution references, confidence, unknown-state semantics, metadata sanitization, and fingerprint behavior.

Snapshot diff reads are calculated from persisted snapshot facts rather than stored as separate Neo4j diff records in the current slice. The comparison reads the two completed snapshots requested by stable key, validates that both snapshots belong to the same repository comparison scope, and compares architecture nodes, architecture relationship records, findings, and metrics. Matching uses the public `stableKey` values of those records, and change detection uses their normalized `fingerprint` values. Neo4j internal IDs therefore remain irrelevant to diff semantics: recreating the database can change store-local identities without changing the public diff result when stable keys and fingerprints are the same.

This query-derived design also avoids creating historical diff artifacts for every possible snapshot pair. A snapshot can be compared with different previous snapshots depending on the user's review question, so materializing every pair would be wasteful and would require cleanup rules that are not part of the current persistence foundation. Future infrastructure adapters can optimize retrieval or cache common comparisons, but they must preserve the same public behavior: repository compatibility validation, stable-key matching, fingerprint classification into added, removed, changed, and unchanged records, evidence references, unknown-state propagation, changed-field summaries where practical, bounded detail rows, and truncation metadata.

A **generated summary** is a durable `ArchonGeneratedSummary` node containing generated narrative or report-ready content. It stores summary kind, optional target stable key, format, title, content, deterministic metadata JSON, and fingerprint. Generated summaries always link to the owning snapshot through `SUMMARIZES_SNAPSHOT`; when a summary has a target stable key, it links to the target graph record through `PRIMARY_NODE` or `PRIMARY_RELATIONSHIP`.

## Integrated persistence mental model

WP003 provides persistence of already-assembled graph contracts. It does not decide how extraction finds facts, how rules are loaded from disk, how rules evaluate findings, how summaries are generated, how metrics are computed, or how API and MCP consumers query the graph. Those responsibilities belong to later work packages.

When reviewing or troubleshooting a WP003 graph, start with stable identities and support paths rather than Neo4j internal IDs. Locate repositories, solutions, snapshots, architecture nodes, relationship nodes, evidence records, findings, metrics, and summaries by stable key and, where relevant, snapshot stable key. Locate rules by rule code plus version. Compare fingerprints for diff-oriented investigations. Traverse support relationships for explainability: `CLASSIFIED_BY_RULE`, `SUPPORTED_BY_EVIDENCE`, `RELATIONSHIP_SOURCE`, `RELATIONSHIP_TARGET`, `PRIMARY_NODE`, `PRIMARY_RELATIONSHIP`, and `SUMMARIZES_SNAPSHOT`.
