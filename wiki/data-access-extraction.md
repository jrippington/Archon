# Data Access Extraction

Data access extraction is Archon's static-analysis view of how an analyzed .NET repository describes and uses databases. In the current WP009 slice, the implemented behavior covers LINQ to SQL `.dbml` model files, generated LINQ to SQL designer source, source-code usage of generated LINQ to SQL contexts, Entity Framework 6 source artifacts, Entity Framework Core source artifacts, ADO.NET command or raw SQL usage in source code, and typed DataSet `.xsd` model artifacts with generated-source and usage correlation. A `.dbml` file is an XML model artifact used by LINQ to SQL designers to describe a `DataContext`, entity types, database tables, columns, associations, and stored-procedure wrapper methods. A typed DataSet `.xsd` file is an XML schema artifact produced by Visual Studio's legacy DataSet designer; it describes a generated `DataSet` class, generated `DataTable` classes, generated `TableAdapter` classes, query methods, SQL command text, and stored-procedure wrappers. Generated designer files express the same model through C# source. Entity Framework, often shortened to EF, is an object-relational mapper that uses a `DbContext` or legacy `ObjectContext` to describe mapped entity classes, database tables, columns, relationships, migrations, provider setup, and query or save usage. ADO.NET is the lower-level .NET data-access API family around `DbConnection`, `DbCommand`, provider-specific command types such as `SqlCommand`, and data containers such as `DataSet`. Archon reads those artifacts as repository evidence; it does not connect to the database named by the model, does not execute generated designer code, does not apply migrations, does not open ADO.NET connections, and does not call the target application's data-access layer.

This page is intentionally separate from [graph domain model](graph-domain-model.md) and [API extraction workflow](api-extraction-workflow.md). The graph page explains the general vocabulary of nodes, edges, evidence, confidence, unknown state, stable keys, and fingerprints. The API workflow page explains how stages run after a `POST /extractions` request. This page explains the current data-access extraction concept and the LINQ to SQL DBML, generated-designer, source-usage, EF6, EF Core, ADO.NET, typed DataSet, raw SQL, stored-procedure, and dynamic SQL behavior contributors need to understand when extending WP009.

Reader path: [Home](home.md) -> [API extraction workflow](api-extraction-workflow.md) -> Data access extraction -> [Validation and test workflows](validation-and-test-workflows.md).

## Current scope

The current data-access extraction stage is named `wp009-data-access-dbml`. The name preserves the first WP009 vertical-slice identifier, but the stage now delegates LINQ to SQL, Entity Framework, ADO.NET/raw SQL, and typed DataSet recognition to the data-access category inside the consolidated `src/Archon.Extractors` project. An **extractor category** is a cohesive source folder and namespace below the consolidated extractor assembly, such as `src/Archon.Extractors/DataAccess` with namespace `Archon.Extractors.DataAccess`; it is not a separate project. The consolidated assembly is the single production output built from `src/Archon.Extractors/Archon.Extractors.csproj`, and the matching tests live under `test/Archon.Extractors.Tests/DataAccess` in the consolidated test project. It runs after the project, Roslyn semantic, configuration/dependency-injection, and runtime extraction stages in the API-triggered pipeline. The stage delegates DBML parsing, generated designer recognition, LINQ to SQL source usage recognition, EF6 source recognition, EF Core source recognition, ADO.NET source usage recognition, typed DataSet XSD parsing, generated typed DataSet source correlation, and typed DataSet usage recognition to the extractor category and merges graph-ready output into the shared application accumulator. This means LINQ to SQL, Entity Framework, ADO.NET, and typed DataSet model or usage facts participate in the same snapshot as repository, solution, project, package, semantic, configuration, dependency-injection, and runtime facts.

The implemented scope is deliberately evidence-first. Archon discovers repository-contained files whose names end in `.dbml`, excluding generated build-output paths such as `obj`, and parses them as XML model artifacts. It extracts the LINQ to SQL `DataContext` name from the `Database` element's `Class` attribute when present, the database name from the `Database` element's `Name` attribute when present, safe connection identifiers from the `Connection` element, table names from `Table` elements, entity names from `Type` elements, column names and column metadata from `Column` elements, association metadata from `Association` elements, and stored-procedure facts from `Function` elements. The API stage also loads C# semantic documents from the submitted solution boundary so the extractor can inspect generated designer source and calling code without running MSBuild targets or executing the analyzed application.

Generated designer extraction recognizes classes that inherit from `System.Data.Linq.DataContext`, entity classes decorated with `TableAttribute`, mapped properties decorated with `ColumnAttribute`, association properties decorated with `AssociationAttribute`, `Table<TEntity>` DataContext properties, and stored-procedure wrapper methods decorated with `FunctionAttribute`. When designer facts correspond to DBML facts, they reuse the DBML stable keys and replace the earlier graph node metadata with a richer `DbmlAndDesignerSource` detection mode. This is how the snapshot avoids double-counting the same `NorthwindDataContext`, `Customer`, `dbo.Customers`, `CustomerID`, or `dbo.GetCustomerOrders` concept merely because it appears in both XML and generated C#.

Entity Framework extraction recognizes EF6 contexts that derive from `System.Data.Entity.DbContext`, legacy EF `ObjectContext` types from `System.Data.Entity.Core.Objects`, EF Core contexts that derive from `Microsoft.EntityFrameworkCore.DbContext`, and `DbSet<TEntity>` properties that expose mapped entities. It also recognizes source-level table and column mapping attributes, common Fluent API mapping chains inside `OnModelCreating`, EF6 `DbMigration` classes, EF Core `Migration` classes, provider configuration calls such as `UseSqlServer`, `UseSqlite`, `UseNpgsql`, and EF6 `SetProviderServices`, save calls such as `SaveChanges` and `SaveChangesAsync`, and raw SQL APIs such as `SqlQuery`, `ExecuteSqlCommand`, `FromSql`, `FromSqlRaw`, `FromSqlInterpolated`, `ExecuteSql`, and `ExecuteSqlRaw`. EF extraction is intentionally static. It reads compiler syntax and semantic facts from submitted solution documents; it does not load a real EF model, execute `OnModelCreating`, evaluate migration builders, instantiate contexts, or open database connections.

Source usage extraction recognizes direct `System.Data.Linq.DataContext` construction, generated context usage, `GetTable<T>()`, generated `Table<T>` property reads, `InsertOnSubmit`, `DeleteOnSubmit`, `Attach`, `SubmitChanges`, `ExecuteQuery<T>()`, `ExecuteCommand()`, and generated stored-procedure wrapper calls. EF usage extraction recognizes context construction or context parameters, `DbSet` query member access, `DbSet` mutation calls, `SaveChanges`, `SaveChangesAsync`, EF6 and EF Core raw SQL APIs, and migration SQL that creates stored procedures. ADO.NET usage extraction recognizes `SqlConnection`, `SqlCommand`, `SqlDataReader`, `SqlDataAdapter`, `DbCommand`, `OleDbCommand`, `OleDbDataAdapter`, `OdbcCommand`, `DataSet`, `DataTable`, command text assignments, `CommandType.StoredProcedure`, `ExecuteReader`, `ExecuteNonQuery`, `ExecuteScalar`, and adapter `Fill` calls where source evidence is available. Typed DataSet extraction recognizes repository-contained `.xsd` files marked as typed DataSet models, DataTable declarations, generated TableAdapter declarations, `DbSource` query definitions, `CommandType="StoredProcedure"` procedure wrappers, generated DataSet and TableAdapter source classes, and application methods that call generated TableAdapter query or stored-procedure methods. Usage relationships are method-scoped: a source `Method` node points to the DataContext, DbContext, table, stored procedure, or raw SQL node that the method uses. Read and write intent is represented through existing data-access edge kinds and metadata hints. The current slice still does not analyze live database schemas, query endpoints, MCP tools, Discovery UI pages, direct Neo4j writes, database connectivity, or markdown export. The extractor produces snapshot contributions only.

## Graph shape produced from LINQ to SQL artifacts

A LINQ to SQL model contributes standard architecture graph nodes rather than a DBML-specific parallel model. The DBML `Database` element or generated `DataContext` class contributes a `LinqToSqlDataContext` node. Each model entity contributes an `Entity` node. Each deterministic database table contributes a `DatabaseTable` node. Each deterministic column under a known table contributes a `DatabaseColumn` node. Each DBML function or generated `FunctionAttribute` wrapper with a deterministic database object name contributes a `StoredProcedure` node. Source methods that use those artifacts contribute ordinary `Method` nodes so query consumers can navigate from application code to database dependencies.

Relationships also use existing controlled edge kinds. The DataContext points to each entity through `MAPS_ENTITY`. An entity points to its table through `MAPS_TABLE`. A table points to its columns through `MAPS_COLUMN`, and the current slice also emits an entity-to-column `MAPS_COLUMN` relationship so consumers can navigate either through the table or directly from the model entity. The DataContext points to stored procedures through `CALLS_STORED_PROCEDURE`, representing the generated wrapper method that LINQ to SQL exposes for the function. Association metadata is preserved as metadata-backed `MAPS_ENTITY` evidence on the owning entity.

Usage relationships add the method-level view. A method that constructs or uses a generated context emits `USES_LINQ_TO_SQL_CONTEXT`. A method that reads through `Table<T>`, a generated table property, `GetTable<T>()`, or `ExecuteQuery<T>()` emits `READS_TABLE` when a table target can be resolved. A method that calls `InsertOnSubmit`, `DeleteOnSubmit`, `Attach`, `SubmitChanges`, or `ExecuteCommand()` emits `WRITES_TABLE` when a table target can be resolved. A method that calls a generated stored-procedure wrapper emits `CALLS_STORED_PROCEDURE`. A method that uses `ExecuteQuery<T>()` or `ExecuteCommand()` emits `EXECUTES_RAW_SQL` to a `SqlScript` node that stores a bounded redacted SQL preview and hash when the SQL text is literal, or explicit unknown state when the SQL text is computed.

EF graph facts use the same normalized graph vocabulary rather than a separate EF model. An EF6 or EF Core context contributes a `DbContext` node. An EF6 `ObjectContext` also contributes a `DbContext` node with `contextKind` metadata of `ObjectContext`, because the graph vocabulary currently treats EF context concepts through the shared context node kind. A `DbSet<TEntity>` property, mapping attribute, or Fluent API `Entity<TEntity>()` call contributes an `Entity` node for the CLR entity type. Explicit table mapping such as `[Table("Customers", Schema = "sales")]` or `.ToTable("Customers", "sales")` contributes a `DatabaseTable` node with high confidence. Convention-only table names inferred from a `DbSet` property are retained with lower confidence and explicit unknown metadata so consumers can distinguish a proven database table name from EF convention behavior. Column mappings from `[Column]`, `.Property(...).HasColumnName(...)`, or EF Core shadow-property mapping contribute `DatabaseColumn` nodes. A shadow property is an EF Core model property that does not have a CLR property on the entity type; Archon records it with unknown state because a contributor cannot navigate to a normal entity property declaration for that column.

EF relationships follow the same data-access edge vocabulary. A context points to mapped entities through `MAPS_ENTITY`; entities and contexts point to tables through `MAPS_TABLE`; tables and entities point to columns through `MAPS_COLUMN`; methods point to EF contexts through `USES_DB_CONTEXT`; query or raw SQL calls produce `READS_TABLE` and `EXECUTES_RAW_SQL` where evidence supports them; mutation and save calls produce `WRITES_TABLE`; and migration SQL that statically creates a stored procedure can produce a `StoredProcedure` node connected from the generated migration artifact through `CALLS_STORED_PROCEDURE`. EF migration classes are represented as `GeneratedArtifact` nodes because a migration is source evidence for schema-changing operations, not a runtime context or table by itself.

ADO.NET graph facts are context-free because a command can be created without a higher-level ORM model. A source method that executes a command contributes a `Method` node, a `SqlScript` node for the raw command evidence, and an `EXECUTES_RAW_SQL` relationship between them. If the command text is statically available after redaction, the SQL script metadata stores a bounded `sqlPreview` and `sqlTextHash`; if the command text is concatenated with runtime values, interpolated, supplied through an unknown parameter, or absent, Archon records explicit unknown state rather than reconstructing a query. Simple leading SQL shapes produce conservative affected-table hints. `SELECT` and data adapter `Fill` calls can produce `READS_TABLE`; `INSERT`, `UPDATE`, `DELETE`, `MERGE`, and data-definition language such as `CREATE TABLE` can produce `WRITES_TABLE`. ADO.NET commands marked with `CommandType.StoredProcedure` contribute `StoredProcedure` nodes and `CALLS_STORED_PROCEDURE` relationships when the procedure name is statically available. This is intentionally not a full SQL parser: it recognizes common table tokens such as `FROM`, `INTO`, `UPDATE`, `MERGE`, `USING`, and `TABLE`, then preserves uncertainty when more complex SQL would require unsafe interpretation.

Typed DataSet graph facts reuse the same graph vocabulary as the other WP009 slices. A typed DataSet root from an `.xsd` file contributes an `Entity` node with `dataAccessTechnology` and `framework` metadata set to `TypedDataSet`, because the current graph vocabulary treats data-access subtypes as metadata rather than new node kinds. Each deterministic typed DataTable contributes an `Entity` node for the generated DataTable class and a `DatabaseTable` node for the mapped database table. Columns below a known table contribute `DatabaseColumn` nodes. The typed DataSet root points to generated DataTable entities through `MAPS_ENTITY`; generated DataTable entities point to database tables through `MAPS_TABLE`; tables and DataTable entities point to columns through `MAPS_COLUMN`. TableAdapters are represented as `GeneratedArtifact` nodes because they are generated source/model artifacts that wrap data-access commands rather than database objects themselves.

TableAdapter command definitions produce raw SQL, table, and stored-procedure facts. Text queries contribute `SqlScript` nodes with redacted previews and SQL hashes, then emit `EXECUTES_RAW_SQL` from the TableAdapter artifact. Simple static SQL can also emit `READS_TABLE` or `WRITES_TABLE` from the TableAdapter artifact to a `DatabaseTable` node. Stored procedure commands contribute `StoredProcedure` nodes and `CALLS_STORED_PROCEDURE` relationships. Generated source correlation links generated typed DataSet and TableAdapter source classes back to the XSD-derived model facts through `REFERENCES` relationships when names and file relationships are deterministic. Consumer source usage links ordinary `Method` nodes to database tables or stored procedures when a method calls a generated TableAdapter query or stored-procedure wrapper. Partial XSD artifacts still emit available model identity with explicit unknown state, while malformed XSD files become non-blocking warnings.

The stable keys for current DBML facts include the repository-relative DBML model path and the model-local identity. For example, a DataContext declared in `Data/Northwind.dbml` can have a stable key shaped like `linqtosql://Data/Northwind.dbml#NorthwindDataContext`. A table can have a key shaped like `dbtable://Data/Northwind.dbml#dbo.Customers`, and a column can have a key shaped like `dbcolumn://Data/Northwind.dbml#dbo.Customers.CustomerID`. Including the model path is important because DBML files are model artifacts rather than compiled project symbols in this slice; two legacy projects can contain same-named tables or contexts, and the model file is the evidence boundary that distinguishes them before later correlation work exists. EF stable keys are project-scoped instead. For example, an EF Core context can have a key shaped like `dbcontext://src/Sales.Data/Sales.Data.csproj#Sales.Data.SalesContext`, and a table can have a key shaped like `dbtable://src/Sales.Data/Sales.Data.csproj#sales.Customers`. Project scoping matches the WP009 rule that EF context identity comes from the project key plus fully qualified context type name.

## Evidence, confidence, and unknowns

Every emitted DBML graph fact is backed by `Dbml` evidence. Typed DataSet XSD facts currently use the same XML-artifact evidence kind with metadata that identifies `TypedDataSetXsd` detection mode, because the graph vocabulary does not yet define a separate XSD evidence kind. Generated designer facts are backed by `DesignerGeneratedCode` or `SourceCode` evidence depending on the current extraction slice and artifact type. Source usage facts, including EF model, migration, provider, ADO.NET command, typed DataSet generated source, typed DataSet usage, raw SQL, and usage facts, are backed by `SourceCode` evidence. Evidence records include the repository-relative file path, one-based XML or source line information when available, a short redacted snippet preview, a snippet hash, and detection metadata such as `DbmlXmlModel`, `TypedDataSetXsd`, `DesignerGeneratedCode`, `GeneratedSource`, `SourceMapping`, `MigrationSource`, or `SourceUsage`. The snippet preview helps a contributor find the model element or call site quickly, but it is intentionally bounded and redacted. The snippet hash is the deterministic comparison value for the preview payload; it is not a full source archive.

Confidence is high when DBML metadata directly declares the fact. For example, a `Table Name="dbo.Customers"` element is certain evidence for a database table mapping in the model. Unknown state is explicit when useful partial facts exist but some identity cannot be proven. A valid DBML file with a `Database` element but no `Class` attribute still proves that a LINQ to SQL model exists, but it does not prove the generated DataContext class name. In that case Archon emits a `LinqToSqlDataContext` node with medium confidence and an unknown reason explaining that the DBML `Database` element does not declare a DataContext class name. This is preferable to dropping the model or inventing a class name that would look certain downstream.

Malformed DBML and typed DataSet XSD files are handled as non-fatal extraction warnings. A malformed XML file cannot provide reliable element locations or model facts, so Archon records a warning and continues with other artifacts. Source usage extraction also records explicit unknowns for unresolved model targets, such as `GetTable<T>()` where `T` is not mapped to a known table, convention-only EF table names, EF Core shadow properties, computed raw SQL where the literal command text cannot be determined statically, ADO.NET command executions whose command text is missing or supplied through unresolved parameters, and typed DataSet tables whose XSD metadata proves a model exists but does not provide deterministic table identity. This degraded behavior follows the broader extraction rule that one bad or incomplete artifact should not prevent unrelated architecture facts from being extracted when the problem can be isolated safely.

## Secret-safe connection handling

DBML files, typed DataSet XSD files, EF source, and ADO.NET command source can contain connection metadata. Some models reference an application settings property such as `NorthwindConnectionString` or a typed DataSet `ConnectionStringProperty`; others can contain raw connection strings with user names or passwords. EF constructors, provider configuration calls, ADO.NET connection constructors, command constructors, and TableAdapter XSD command metadata can also contain `name=ConnectionKey` references, inline provider connection strings, or SQL literals that look like secrets. Archon preserves safe identifiers such as `SettingsPropertyName`, typed DataSet connection-string property names, provider name, provider configuration API, connection mode, and `name=` connection-string keys. It deliberately does not persist raw connection-string values. Evidence previews are redacted before they are hashed or stored, and metadata records only that a raw connection string was present and redacted when applicable.

This distinction matters for contributor review. A configuration key or settings property name is architecture information because it helps later configuration extraction correlate model dependencies. A password or database credential is not architecture information and must not appear in graph metadata, warning text, API status responses, test output, or wiki examples. When adding new data-access extractors, apply the same rule before graph records are created rather than relying on a later API sanitization pass.

## API pipeline behavior

The API extraction composition registers `wp009-data-access-dbml` after `wp008-aspnet-core-minimal-api`. The stage receives the accepted repository root and explicit solution list through the same `ExtractionStageContext` used by earlier stages. DBML discovery is repository-root based because `.dbml` files are model artifacts that may not be compile items in SDK-style projects. Designer and usage source analysis is solution-bound: the stage loads C# semantic documents from the submitted solution files and passes those documents to the data-access extractor. The stage still runs only inside an accepted API extraction request; it is not an arbitrary standalone repository scanner in the product surface.

The final WP009 pass now also performs cross-slice correlation after data-access facts have been merged into the same accumulator as the project, semantic, configuration, dependency-injection, and runtime stages. A cross-slice correlation is a relationship that is not emitted by a single extractor in isolation, but becomes deterministic once two stages have produced stable graph identities. When a data-access node carries a safe `connectionStringKey`, such as `MainDb`, and the configuration stage has already emitted a matching `ConfigurationKey` node, Archon adds a `USES_CONFIG` relationship from the data-access context or command fact to the configuration key. This relationship carries `correlationKind` metadata of `DataAccessConnectionStringKey` and never copies the configuration value. When source contains an Entity Framework `AddDbContext<TContext>(...)` registration and WP009 has emitted a matching `DbContext` node, Archon adds a `USES_DB_CONTEXT` relationship from the registered context type identity to the context node with `DependencyInjectionDbContextRegistration` metadata. When a runtime method emitted by WP008 directly calls a method that WP009 has already identified as data-access usage, Archon adds a `DEPENDS_ON` relationship from the runtime method node to the data-access method node with `RuntimeDataAccessMethod` metadata. These correlations make downstream graph traversal possible without changing the original extractor facts or introducing direct Neo4j writes.

The stage creates a snapshot-scoped LINQ to SQL extraction request, invokes the data-access extractor, merges the returned `ExtractedArchitectureSnapshot` into the shared accumulator, and then runs the final correlation pass against that shared accumulator. It does not write to Neo4j directly. Persistence remains behind `IArchitectureSnapshotWriter`, and API status reports completion only after the assembled snapshot has been handed to the configured writer and accepted.

## Contributor extension guidance

When extending data-access extraction, preserve the current layering. New data-access implementation files belong under `src/Archon.Extractors/DataAccess`, and matching tests belong under `test/Archon.Extractors.Tests/DataAccess`. Contributors should not create a new `Archon.Extractors.DataAccess` production project or `Archon.Extractors.DataAccess.Tests` test project. Extractor categories should produce graph-ready domain/application contracts without depending on API hosts, Neo4j drivers, MCP tools, UI projects, or live database clients. API extraction stages should remain thin orchestration adapters: load or pass accepted context, call extractor categories through the consolidated extractor assembly, merge snapshots, log credential-safe progress, and return a pipeline result.

New data-access facts should reuse existing node kinds and edge kinds unless the domain vocabulary is genuinely missing a normalized concept. Metadata should use stable lower-camel-case names and must not hide normalized graph properties such as stable keys, relationship kinds, evidence kinds, confidence, or unknown state. If a future extractor cannot determine a table, stored procedure, provider, raw SQL target, or generated wrapper target, prefer explicit unknown state with a reason over silent omission or a guessed relationship.

## Validation

Use the data-access extractor tests when changing DBML parsing, generated designer extraction, EF extraction, ADO.NET extraction, typed DataSet extraction, raw SQL classification, or source usage behavior:

```powershell
dotnet test .\test\Archon.Extractors.Tests\Archon.Extractors.Tests.csproj --filter FullyQualifiedName~Archon.Extractors.Tests.DataAccess
dotnet test .\test\Archon.Extractors.Tests\Archon.Extractors.Tests.csproj --filter TypedDataSet
```

Use the API extraction tests when changing stage registration or API-triggered snapshot handoff:

```powershell
dotnet test .\test\Archon.Api.Extraction.Tests\Archon.Api.Extraction.Tests.csproj --filter DataAccess
```

The `DataAccess` API test filter now covers the original DBML snapshot-handoff test and the final integrated correlation test. The integrated test creates a self-contained repository fixture with legacy configuration, Entity Framework context registration, a worker runtime method, EF context usage, and ADO.NET command usage. Passing this test proves that WP009 runs after WP007 and WP008, can correlate connection-string keys, `AddDbContext` registration, runtime method calls, and method-level data-access usage through the public API orchestration path, and still redacts secret-like values from data-access evidence.

Run the integrated build gate after focused tests pass:

```powershell
dotnet build .\Archon.slnx --no-restore
```

These validations do not start the Aspire AppHost, do not require Neo4j credentials, do not connect to target databases, do not apply EF migrations, and do not execute analyzed repository code. A successful API test proves that data-access extraction uses the accepted API workflow and persists through the application-layer snapshot writer seam rather than through direct extractor persistence.
