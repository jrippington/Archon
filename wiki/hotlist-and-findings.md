# Controlled Analysis Queries

The hotlist is the controlled product-facing view over persisted WP012 findings. A **finding** is a snapshot-owned analysis result produced by a versioned rule, and the hotlist turns those records into bounded API responses that API clients and future MCP tools can consume without reading Neo4j directly. This page assumes familiarity with [rule catalog and rule engine](rule-catalog-and-rule-engine.md), because hotlist records are meaningful only when the reader understands rule identity, finding stable keys, history keys, confidence, unknown state, and suppression.

The same controlled-query model now includes dashboard summary reads, project catalogue and project detail reads, bounded graph traversal reads, symbol search/detail/usage reads, runtime endpoint/controller/entry-point/worker reads, fact reads for data access, configuration, integrations, and UI technologies, evidence drill-down reads, snapshot metric reads, dependency cycle reads, architecture hotspot reads, architecture-rule result reads, snapshot diff reads, cross-domain search reads, and controlled management and operations reads or commands. A **dashboard summary** is a compact non-visual aggregate over one repository, optional solution, and selected or latest snapshot. It gives API and future MCP consumers the high-level counts, top hotspots, latest-change summary, warning, and unknown-state information needed to start a review without loading arbitrary graph records. A **project catalogue** is a bounded list of project architecture nodes with stable identities, search, filters, deterministic sorting, pagination, aggregate dependency counts, risk indicators, and evidence references. A **project detail** response expands one stable project identity or one unambiguous project name into responsibilities, direct references, dependents, packages, endpoints, data-access indicators, configuration keys, integrations, findings, evidence references, and a scoped graph summary. A **bounded graph traversal** is a controlled walk over approved graph edge kinds from one stable node identity; it returns only stable node and edge DTOs, evidence references, depth and result limits, and truncation metadata rather than arbitrary graph query output. A **symbol query** is a controlled read over persisted Roslyn semantic facts such as namespace, type, method, property, and field nodes. It lets clients find symbols, inspect one symbol's source context and relationships, and list incoming or outgoing usages without turning the API into a source-code export surface. A **runtime query** is a controlled read over persisted runtime facts such as HTTP endpoints, controllers, handlers, application entry points, hosted services, background services, queue or topic consumers, and scheduled jobs. It lets clients inspect executable behavior without launching a Discovery UI, executing the target application, or exporting raw runtime metadata. A **fact query** is a controlled read over persisted non-runtime architecture facts such as persistence technologies, safe configuration usage, external integrations, and backend UI-technology facts. It lets clients inspect modernization-relevant facts without exposing secrets, live endpoints, raw SQL bodies, or UI assets. An **evidence drill-down** is a controlled lookup from a stable evidence key, or from a related node, edge, finding, metric, or rule identity, to source-location explanation data. It exposes repository-relative file path, line range, symbol context, bounded snippet preview, confidence, classification, unknown reason, and related stable records without reading source files or expanding snippets beyond persisted evidence context. A **metric** is a snapshot-owned calculated value such as `SnapshotNodeCount`; it is useful for dashboards, future diff views, and automated review because callers can ask for a stable historical value instead of recomputing facts during every read. A **dependency cycle** is a directed path through dependency-like architecture edges that returns to its starting node, such as one project referencing another project that eventually references the first project again. A **hotspot** is a deterministic triage result that combines metrics, findings, graph facts, and cycle participation into an explainable architecture-review target. An **architecture-rule result** is a bounded query result from a generic built-in rule check over graph, metric, finding, runtime, semantic, and fact-query data. A **snapshot diff** is a bounded comparison between two persisted snapshots that reports architecture drift across nodes, edges, findings, and metrics. A **cross-domain search** is a bounded lookup across supported result families such as projects, symbols, runtime endpoints, facts, evidence, findings, and metrics; it returns stable identities, confidence, unknown state, evidence references, related nodes, and deterministic follow-up affordances instead of raw graph queries. A **controlled management operation** is an allowlisted write or operational read whose request shape is defined by Archon, such as repository registration, solution registration, metadata update, retention, rule enablement, maintenance, health, or readiness. It is not a general-purpose graph editor or database administration endpoint.

## Controlled query surface

The current query API exposes dashboard summary, project catalogue, project detail, direct dependency, direct dependent, transitive dependency, transitive dependent, dependency path, graph neighbourhood, symbol search, symbol detail, symbol usage, runtime endpoint, runtime controller/handler, runtime entry-point, runtime worker, data-access fact, configuration usage, integration fact, UI-technology fact, evidence detail, related evidence, rule catalog, hotlist, finding detail, finding history, suppression, snapshot metric, snapshot cycle, snapshot hotspot, snapshot architecture-rule result, snapshot diff, latest-to-previous snapshot diff, cross-domain search, repository registration, solution registration, constrained metadata update, snapshot lifecycle, retention, extraction run history, rule enablement, controlled maintenance, health, and readiness endpoints through the API host modules. These endpoints deliberately do not expose arbitrary Cypher, unrestricted graph-query execution, raw graph property maps, runtime reflection execution, target-application startup, configuration values, credentials, connection strings, unrestricted SQL text, unbounded source-code export, UI rendering behavior, shell execution, arbitrary filesystem mutation, code modification, unrestricted graph mutation, or database administration commands. A caller supplies only approved filters, page bounds, route identities, traversal bounds, edge-kind filters, symbol identities, usage direction values, runtime identities, worker classification filters, fact-family filters, safe configuration or integration filters, UI-technology filters, evidence stable keys, related stable keys, diff scope and classification filters, search result-kind filters, suppression fields, management target kinds, approved metadata fields, retention boundaries, rule identity, or allowlisted maintenance operation names, and the application layer translates those inputs into stable DTOs. A **DTO**, or data transfer object, is the public response shape that protects clients from infrastructure-specific implementation details.

The API host also exposes this implemented surface through development-time API documentation. A **Scalar API reference** is the browser-based documentation UI backed by the ASP.NET Core OpenAPI document at `/openapi/v1.json`; in Archon it is available at `/scalar/v1` only when the host runs in the Development environment. Scalar is intentionally a contributor and API-consumer aid, not a product Discovery UI. It helps contributors inspect operation names, route groups, summaries, descriptions, request shapes, response schemas, validation responses, and safe server-error contracts while keeping the route implementation itself as the source of truth. Swagger UI is not part of the repository standard and should not be introduced as a parallel documentation surface.

When contributors add or revise controlled query or management endpoints, the route metadata must remain as deliberate as the runtime contract. Each route should carry a stable operation name, a grouping tag, a concise summary, and a fuller description that explains the bounded query or controlled operation in caller terms. Response metadata should identify the successful DTO or envelope, validation-problem responses, not-found or conflict responses where applicable, and safe server-error responses for route families that shape those errors. This metadata is not decorative: future MCP clients and automation workflows depend on the same consistency that humans see in Scalar. If a route returns a paged response, its documentation should make the page shape visible. If a route returns a non-paged envelope, its documentation should make the envelope and truncation metadata visible. If a route is a management operation, the documentation should reinforce the safety boundary rather than implying arbitrary mutation is available.

Dashboard summary is available through `GET /dashboard-summary?repositoryStableKey=...`. The repository stable key is required so latest snapshot resolution is bounded to one repository rather than scanning every persisted repository. Callers may also pass `solutionStableKey` to scope the response to a known solution and `snapshotStableKey` to request either an exact `snapshot://...` identity or the literal selector `latest`. When `snapshotStableKey` is omitted, the endpoint behaves like `latest`: it resolves the most recent matching snapshot by completion time, then started time, then stable key so repeated requests are deterministic. The endpoint returns one common non-paged response envelope. A **response envelope** is the outer object that carries the endpoint data plus cross-cutting metadata such as applied scope, resolved snapshot, paging state, truncation state, warnings, unknowns, and request trace information. In the dashboard case, the data payload contains count summaries, compact top-hotspot rows, and compact latest-change rows.

A **snapshot selector** is the request value that chooses the snapshot state behind a query. Exact selectors use stable snapshot keys and latest selectors use deterministic current-state resolution within the requested repository and optional solution scope. A **stable key** remains the durable public identity, such as `repository://...`, `solution://...`, `snapshot://...`, `project://...`, or `hotspot://...`; clients should never expect Neo4j internal IDs in the response. The dashboard summary intentionally treats missing optional inputs as visible information. If no persisted metrics or findings exist, `topHotspots` is empty and the envelope carries a warning plus an unknown entry for that field. If no previous snapshot exists for comparison, `latestChanges` is empty and the envelope again carries warning and unknown metadata. This is different from silently omitting a property: a missing optional section tells a dashboard or MCP client that Archon could not determine that summary from persisted facts, not that the value is known to be zero.

Project catalogue reads are available through `GET /projects?repositoryStableKey=...`. Repository scope is required for the same reason as dashboard summary: the latest selector must resolve inside one bounded repository rather than across every persisted graph. Callers may add `solutionStableKey` and may choose either an exact `snapshot://...` identity or `latest`/`current` through `snapshotStableKey`. The catalogue supports bounded `skip` and `take`, search over public project identity fields, exact filters such as `language`, `projectType`, `targetFramework`, `applicationType`, `hasDataAccess`, and `hasRisk`, plus deterministic sort fields such as `name`, `path`, `language`, `projectType`, `targetFramework`, `dependencyCount`, `packageCount`, `endpointCount`, `hotlistCount`, and `risk`. A catalogue row includes the project stable key, display name, repository-relative path when known, language, project type, target framework, SDK-style status, outgoing dependency count, incoming dependent count, package count, endpoint count, data-access indicators, hotlist count, risk indicators, evidence stable keys, confidence, and unknown-state fields. The row is intentionally a discovery contract: it tells a client enough to render or filter a project inventory and then follow the stable key to the detail endpoint without exporting the whole graph.

Project detail reads are available through `GET /projects/detail?repositoryStableKey=...&projectStableKey=...` and through `GET /projects/{projectStableKey}` when a client prefers route-based stable-key lookup. The query-parameter form is often safer because stable keys contain `://` and path separators. A caller that does not know the stable key can pass `projectName`, but name lookup must resolve to exactly one project. If two projects share the same display name, the endpoint returns a conflict response with stable disambiguation options instead of choosing arbitrarily. This is important because a project display name is a convenience label while the `project://...` key is the durable identity. A detail response includes the catalogue summary, inferred responsibilities, safe evidence references, entry points, direct references, dependents, packages, application type, endpoints, workers, data-access indicators, configuration keys, integrations, hotlist finding stable keys, scoped graph summary, warnings, unknowns, and sanitized metadata. A **scoped graph summary** is a compact aggregate over the selected project and its directly owned or directly related facts; it is not a substitute for later bounded graph traversal endpoints.

For example, a dashboard or MCP client can first request `/projects?repositoryStableKey=repository%3A%2F%2Fcustomer-estate&snapshotStableKey=latest&projectType=Api&sort=hotlistCount&descending=true&take=20`. The envelope identifies the resolved snapshot and returns the first twenty API projects ordered by hotlist count with stable project keys. The client can then request `/projects/detail?repositoryStableKey=repository%3A%2F%2Fcustomer-estate&snapshotStableKey=latest&projectStableKey=project%3A%2F%2Fsrc%2FCustomer.Api%2FCustomer.Api.csproj`. The detail response can show that the project exposes endpoint nodes, references a domain project, uses data-access indicators, and has finding and evidence stable keys. It still does not expose source snippets, Neo4j IDs, raw metadata maps, arbitrary relationship expansion, or query text; those remain behind controlled DTOs and later bounded traversal routes.

Bounded graph traversal reads are available through query-parameter routes because node stable keys commonly contain `://` and slash-like path segments. `GET /dependencies/direct` returns depth-one outgoing dependency-like edges from `nodeStableKey`; `GET /dependents/direct` returns depth-one incoming edges for immediate consumers of the same node. `GET /dependencies/transitive` and `GET /dependents/transitive` apply the same directions over a caller-supplied `depth`, defaulting to a bounded transitive depth when omitted. `GET /graph-neighbourhood` returns the neighbourhood around one node and defaults to depth `1` and direction `Both`; callers can set `direction=Outgoing`, `direction=Incoming`, or `direction=Both` and can narrow the traversal with `edgeKinds=REFERENCES` or other controlled edge-kind values. A **neighbourhood** is the bounded set of adjacent or reachable nodes and edges around a selected node under the requested direction and depth, not an export of the full persisted graph.

Traversal responses are non-paged envelopes because each request is already bounded by depth and `take`. The `data` payload carries the traversal mode, start node stable key, normalized direction, applied depth, applied edge kinds, stable node DTOs, stable edge DTOs, and truncation state. A **dependent** is a node that has an incoming dependency edge to the selected node; for example, if `Customer.Api` references `Customer.Domain`, then `Customer.Api` is a dependent of `Customer.Domain`. A **dependency path** is an ordered sequence of stable nodes and stable edges that explains how one source node reaches one target node by following outgoing dependency-like edges. `GET /dependency-path` returns `pathFound=true` with nodes and edges in path order when a bounded path exists. When both nodes exist but no path is found within the requested depth and edge-kind bounds, the endpoint returns `pathFound=false`, `unavailable=false`, and a safe no-path reason. When the selected snapshot contains no persisted graph edges, the endpoint returns `pathFound=false`, `unavailable=true`, an explicit unknown entry, and an unavailable-data reason so clients do not confuse missing graph support with a proven absence of relationship.

For example, a client investigating why an API project is risky might request `/dependencies/direct?repositoryStableKey=repository%3A%2F%2Fcustomer-estate&snapshotStableKey=latest&nodeStableKey=project%3A%2F%2Fsrc%2FCustomer.Api%2FCustomer.Api.csproj&edgeKinds=REFERENCES&take=50`. The response returns stable edge identities such as `edge://...`, source and target stable node keys, the relationship kind, confidence, unknown-state fields, and evidence stable keys for reference declarations where available. If a broader review is needed, the client can request `/graph-neighbourhood?...&direction=Both&depth=1` to see immediate incoming and outgoing dependency pressure. If the response says `truncation.truncated=true`, the client should narrow the request by edge kind, lower the depth, or accept that the returned subgraph is an intentionally bounded view. The endpoint does not return source snippets, raw metadata maps, Cypher text, Neo4j relationship IDs, or every reachable fact in a dense estate.

Symbol reads are available through query-parameter routes because symbol stable keys commonly contain `://` and slash-like segments derived from compiler identity. `GET /symbols` returns a bounded page of semantic symbol rows. It accepts repository, optional solution, and snapshot selectors, then supports `searchText`, `projectStableKey`, `kind`, `namespaceName`, `containingType`, `language`, deterministic `sort`, `descending`, `skip`, and `take`. The supported symbol kinds are the persisted Roslyn semantic node kinds: `Namespace`, `Type`, `Method`, `Property`, and `Field`. A **fully qualified name** is the compiler-style name that includes enough namespace and containing-type context to distinguish symbols that share the same short display name. The search response includes the symbol stable key, display name, fully qualified name, kind, containing project stable key, namespace, containing type, language, bounded source context, evidence stable keys, confidence, and unknown-state fields. Source context is intentionally small: it can include repository-relative file path, line range, and a bounded snippet preview, but it does not expose full source files or arbitrary evidence expansion.

`GET /symbols/detail` returns one symbol by `symbolStableKey` or by exact `searchText` when the caller does not yet have a stable key. Stable-key lookup is preferred because display names and fully qualified names can still be ambiguous across overloads, generated code, partial declarations, or multi-language snapshots. The detail response expands the search summary with safe evidence references and direct semantic relationships, such as `CALLS`, `REFERENCES`, `IMPLEMENTS`, `INHERITS`, or `HANDLES`. An **unresolved symbol** is a semantic fact where Roslyn or the graph projection could not prove the complete target identity from available compilation references. Archon keeps that uncertainty visible through unknown-state metadata instead of pretending the symbol is complete or dropping the row. `GET /symbols/usages` lists incoming or outgoing usage relationships for one `symbolStableKey`. Incoming usage answers “who references or calls this symbol?” while outgoing usage answers “what does this symbol reference or call?” Usage rows include source and target stable keys, source and target display names when available, evidence stable keys, file path, line range, bounded snippet preview, confidence, and unknown-state fields. If no persisted usage edges are available for a valid symbol, the response is still a successful bounded page with an explicit unknown entry so clients do not confuse missing extraction coverage with a proven absence of references.

For example, a client can search `/symbols?repositoryStableKey=repository%3A%2F%2Fcustomer-estate&snapshotStableKey=latest&kind=Method&searchText=CalculateRisk&take=20`, choose the returned `symbol://...` stable key, then request `/symbols/detail?repositoryStableKey=repository%3A%2F%2Fcustomer-estate&snapshotStableKey=latest&symbolStableKey=...` to inspect direct semantic relationships. To understand callers, the client can request `/symbols/usages?repositoryStableKey=repository%3A%2F%2Fcustomer-estate&snapshotStableKey=latest&symbolStableKey=...&direction=Incoming&take=50`. The usage response may show a line range and short preview such as `return service.CalculateRisk(input);`, but the preview is bounded and treated as untrusted display text. Contributors should continue to treat evidence and snippets as sensitive by default: expose stable evidence references and small previews for explanation, not full source code, configuration values, secrets, or arbitrary graph metadata.

Runtime reads are available through query-parameter routes because runtime stable keys frequently contain `://` separators and path-like project segments. `GET /runtime/endpoints` returns a bounded page of HTTP endpoint facts and accepts repository, optional solution, and snapshot selectors plus filters for `httpMethod`, `route`, `projectStableKey`, `controllerOrHandler`, `authorization`, deterministic `sort`, `descending`, `skip`, and `take`. Endpoint rows include method, route, owning project stable key, controller or handler names, action or implementation method, request and response DTO names when extracted, authorization attributes, services used, data-access indicators, safe configuration key names, evidence stable keys, confidence, and unknown-state fields. The endpoint response is intended for discovery and triage: it can explain that `GET /orders/{id}` is handled by `OrdersController.GetOrder`, uses a DbContext indicator, and reads a safe configuration key name, but it does not return source files, controller bodies, authorization secrets, dependency-injection internals, or raw graph metadata.

`GET /runtime/controllers` returns one controller or handler detail by `stableKey` or exact `name`. A **controller or handler** is a runtime implementation node that owns or handles endpoints, messages, schedules, or related runtime work. Stable-key lookup is preferred because display names can repeat across projects or generated partial classes. The detail response includes associated endpoints, services used, data-access indicators, configuration keys, safe evidence references, sanitized metadata, confidence, and unknown-state fields. `GET /runtime/entry-points` returns API, worker, console, or service-host style bootstrap records. An **entry point** is the static project or runtime artifact that starts the application process or host loop, such as a `Program.Main`, an API project bootstrap, a worker host, or a service-host configuration artifact. Entry-point rows connect the project to hosted services, exposed endpoint stable keys, safe configuration keys, and evidence keys so automation can understand runtime shape before choosing deeper endpoint or worker reads.

`GET /runtime/workers` returns hosted-service, background-service, queue-consumer, topic-consumer, and scheduled-job facts. A **hosted service** is a .NET background component registered with the host lifetime, and a **background service** is the common long-running hosted-service pattern based on `BackgroundService`. A **queue consumer** or **topic consumer** represents message-driven runtime behavior; it records safe queue or topic names, transport hints, subscription names when known, handler stable keys, evidence stable keys, and explicit unknowns when extraction could only infer part of the target. A **scheduled job** represents timer- or cron-like runtime behavior and reports a safe schedule description when extracted. Worker rows aggregate project identity, entry-point identity, hosted and background services, consumers, scheduled jobs, data-access indicators, integrations, configuration keys, evidence, confidence, and unknowns. If a queue name was inferred from configuration or a schedule was only partially proven, the worker envelope promotes that unknown so clients do not mistake partial extraction for complete runtime coverage.

For example, a client investigating message-driven risk can request `/runtime/workers?repositoryStableKey=repository%3A%2F%2Fcustomer-estate&snapshotStableKey=latest&workerKind=BackgroundService&queueOrTopic=orders&take=20`. The response can show a stable hosted-service key, the owning worker project, the `orders-incoming` queue consumer, a safe transport hint such as `AzureServiceBus`, related data-access and integration indicators, and evidence stable keys. If the same worker also has a timer method, a caller can add `scheduledJob=Nightly` or inspect returned scheduled-job rows with their safe schedule descriptions. The route family deliberately remains backend-only: it adds no Discovery UI pages, no components, no frontend assets, and no runtime reflection over the target application.

Fact reads are available through four query-parameter routes that use the same repository, optional solution, and snapshot selector pattern as dashboard, project, symbol, and runtime reads. `GET /data-access` returns data-access facts for LINQ to SQL, EF Classic or EF6, EF Core, ADO.NET, typed DataSet, raw SQL, stored procedure, entity, table, and usage-site records when those facts were extracted. A **DataContext** is a LINQ to SQL object model root, while a **DbContext** is the Entity Framework unit-of-work and mapping root; the endpoint can report either as a stable graph fact with related entity, table, stored procedure, usage-site, operation, evidence, confidence, and unknown-state metadata. The operation list can include safe method-style indicators such as `SubmitChanges`, `ExecuteQuery`, `ExecuteCommand`, `Read`, `Write`, `RawSql`, or `StoredProcedure`. Those indicators explain the shape of persistence behavior, but the endpoint does not echo raw connection strings, credentials, unbounded SQL bodies, or database-local identifiers. Callers can filter by `family`, `projectStableKey`, `usageSite`, `entity`, `table`, `storedProcedure`, `skip`, and `take`.

`GET /configuration` returns secret-safe configuration key usage. A **configuration provider** is the source family that supplies settings, such as JSON files, environment variables, user secrets, or another provider recorded by extraction. Configuration rows expose the key name, owning project stable key, consumer stable keys, provider names, optional environment name, source evidence file paths, a `valueAvailable` flag, a `secretLike` flag, evidence stable keys, confidence, unknown-state fields, and sanitized metadata. The important boundary is that `valueAvailable=true` means extraction saw or inferred that a value existed, not that the public API will return it. Values, passwords, tokens, connection strings, and credential-bearing metadata remain omitted from the response. A client that needs to understand exposure can see that `ConnectionStrings:Main` was used by a consumer and that the key is secret-like, but it cannot retrieve the connection string through this route.

`GET /integrations` returns secret-safe external integration facts for external services, queues, topics, OpenAPI documents, and other graph nodes that represent calls outside the project boundary. An **external integration** is a dependency on a system or transport outside the local code unit, such as an HTTP service, broker queue, topic, storage endpoint, email service, payment provider, or generated service client. A **protocol** is the communication family or transport hint, such as HTTP, gRPC, Azure Service Bus, SMTP, or another extractor-provided value. Integration rows can include integration kind, safe endpoint host or service name, protocol, client type, related configuration key names, consumer stable keys, evidence stable keys, confidence, unknown-state fields, and sanitized metadata. If an extractor captured a URL such as `https://user:password@example.invalid/api?token=...`, the query surface reduces it to a safe host when possible and omits credentials, paths, query strings, and token-like values.

`GET /ui-technologies` returns backend UI-technology facts for Blazor, Razor, Windows Forms, WPF, WinUI, .NET MAUI, Avalonia, and related UI graph concepts. A **UI-technology fact** is a persisted static fact about a UI application, component, page, view, route, layout, control, resource, style, binding, command, or view model. The endpoint reports technology, fact kind, name, project stable key, safe route or view path, related stable keys, evidence stable keys, confidence, unknown-state fields, and sanitized metadata. It is intentionally not a Discovery UI feature: it does not render Blazor components, load XAML, instantiate Windows Forms controls, start a UI thread, or add frontend assets to Archon. It simply lets API and future MCP consumers inspect already-persisted UI extraction facts through the same bounded query contract used by other fact families.

For example, a modernization assistant can request `/data-access?repositoryStableKey=repository%3A%2F%2Fcustomer-estate&snapshotStableKey=latest&family=EFCore&table=Orders&take=20` to find EF Core persistence facts related to an Orders table. It can then request `/configuration?repositoryStableKey=...&configurationKey=ConnectionStrings&take=20` to determine which projects consume connection-string keys without seeing the values, `/integrations?repositoryStableKey=...&endpointHost=billing.example.invalid&take=20` to see safe integration metadata, and `/ui-technologies?repositoryStableKey=...&technology=Blazor&route=orders&take=20` to inspect backend UI route facts. Each response uses stable keys and bounded paging so the assistant can continue deterministically without asking for arbitrary graph access or exposing secrets.

Evidence drill-down reads are available through `GET /evidence/detail?repositoryStableKey=...&evidenceStableKey=...` and `GET /evidence/related?repositoryStableKey=...&relatedStableKey=...`. The detail endpoint resolves one stable evidence identity inside the same repository, optional solution, and snapshot selector pattern used by the other WP014 query endpoints. It returns the repository-relative file path, optional line range, optional symbol and containing-symbol names, snippet hash, bounded snippet preview, confidence, classification, unknown reason, related finding context, related rule context, related graph records, sanitized metadata, and the snapshot stable key that owns the evidence. A **snippet preview** is not a source-code export. It is the short preview text already persisted with the evidence record, bounded by the API and treated as untrusted display text. The endpoint does not open the repository file, read more lines from disk, follow includes, or expand a preview beyond persisted evidence context.

The related-evidence endpoint starts from a stable node, edge, finding, metric, or rule identity and returns a bounded page of evidence detail rows connected through explicit primary or supporting evidence relationships. The optional `relatedKind` parameter can narrow lookup to `Node`, `Edge`, `Finding`, `Metric`, or `Rule`; if omitted, the service searches the supported record families by stable key. This shape lets a client follow from a project catalogue row, symbol usage row, runtime endpoint row, finding, metric, hotspot, architecture-rule result, or future MCP output into evidence without needing Neo4j relationship IDs. If no related evidence exists, the API returns a validation problem rather than inventing a source location or pretending that absence is proof of no evidence.

Evidence responses keep source text and secret handling conservative. Snippet previews are bounded to the configured evidence preview limit, and truncation metadata makes that boundary visible. If a preview or metadata value looks secret-like, for example because it contains password, token, API key, credential, or connection-string markers, the public response redacts the preview or omits the metadata field. That redaction is a final API-boundary safeguard, not a reason for extractors to persist secrets. Contributors should continue to redact sensitive source and configuration values before persistence, then rely on evidence drill-down to show enough location context for review: file path, line range, symbol, snippet hash, confidence, classification, unknown reason, and the stable records that point to the evidence.

The rule catalog endpoints are `GET /rules` and `GET /rules/{ruleCode}/{version}`. The list endpoint supports exact filters for rule code, version, category, severity, enabled state, built-in state, and owner scope. The detail endpoint returns one exact rule code/version pair. Rule identity remains the pair of rule code and version, so an older finding can still point to the precise version that classified it even after a newer rule version exists.

The hotlist endpoint is `GET /hotlist`. It lists persisted findings with approved filters for snapshot stable key, category, severity, status, project stable key, affected node stable key, critical-only selection, legacy data-access indicators, out-of-support indicators, security-sensitive indicators, framework-only indicators, technology, and rule code. The indicator filters are deliberately named API parameters such as `legacyDataAccess=true` or `securitySensitive=true`; they are not arbitrary metadata predicates. A **suppression** is a lifecycle overlay that can move a finding out of the active review path while preserving the underlying record, so status filters such as `Open`, `Suppressed`, `Resolved`, or `Acknowledged` should be used when a client needs one lifecycle state. Results include rule code and version, title, summary, severity, status, confidence, optional category, affected-node references, evidence references, and unknown-state information. Evidence is returned as references rather than as raw snippets, because evidence snippets can contain source text or configuration fragments that must not be exposed accidentally through summary lists.

A typical Work Item 8 analysis-output review starts with the rule catalog and then narrows the hotlist. A client can request `/rules?ruleCode=ARCHON-SECURITY-CRITICAL&version=2.1.0&category=SecuritySensitive&severity=Critical&enabled=true` to prove which versioned rule is active, then request `/hotlist?snapshotStableKey=...&criticalOnly=true&securitySensitive=true&ruleCode=ARCHON-SECURITY-CRITICAL&status=Open&take=20` to retrieve only currently active critical findings from that rule. For a legacy data-access modernization review, the same shape can use `/hotlist?snapshotStableKey=...&legacyDataAccess=true&technology=LINQ%20to%20SQL&status=Open`. The response still returns stable finding keys, affected-node references, and evidence references; it does not expose Neo4j IDs, raw rule-storage records, source snippets, or arbitrary metadata matching.

Finding detail is available through `GET /findings/{snapshotStableKey}/{findingStableKey}` and the query-parameter form `GET /findings/detail?snapshotStableKey=...&findingStableKey=...`. The query-parameter form exists because stable keys commonly contain slash-like separators such as `snapshot://...` or `finding://...`, and HTTP path decoding can make those values awkward for some clients. Both forms resolve the same application query. Finding history is available through `GET /findings/history/{historyKey}` and the query-parameter form `GET /finding-history?historyKey=...` for the same route-safety reason.

Snapshot metrics are available through `GET /snapshot-metrics?snapshotStableKey=...` and the route form `GET /snapshots/{snapshotStableKey}/metrics`. The query-parameter form is preferred when a snapshot stable key contains `://` or other slash-like separators. Metric list filters are intentionally small: callers can supply one snapshot stable key, optional metric kind, optional scope kind, optional project stable key, and bounded paging values. The project stable-key filter matches the metric `nodeStableKey`, which is how project-scoped metrics identify their target project and how graph node-scoped metrics identify their target architecture node. The response returns stable public identities, metric kind, scope kind, optional target and evidence references, numeric or text value, unit, confidence, unknown-state fields, sanitized metadata, and fingerprint. It does not return Neo4j internal IDs or accept raw graph predicates.

Snapshot dependency cycles are available through `GET /snapshot-cycles?snapshotStableKey=...`. The endpoint accepts one required snapshot stable key, an optional `nodeStableKey` filter, and bounded paging values. It returns cycle DTOs with the cycle stable key, stable node path, stable edge path, evidence stable keys, confidence, unknown-state fields, truncation state, sanitized metadata, and fingerprint. The node path repeats the first node as the final value so clients can display the closure directly. The edge path has one edge stable key per hop. The endpoint uses the query-parameter form because snapshot and node stable keys frequently contain `://` separators that are safer to pass as encoded query values than as path segments.

Snapshot hotspots are available through `GET /snapshot-hotspots?snapshotStableKey=...`. The endpoint accepts one required snapshot stable key, optional `targetStableKey` and `category` filters, and bounded paging values. It returns hotspot DTOs with the hotspot stable key, category, target stable key, target kind, display name, score, rank, contributing metric stable keys, contributing finding stable keys, evidence stable keys, confidence, unknown-state fields, sanitized metadata, and fingerprint. Hotspot reads are derived from persisted snapshot facts in the application layer; clients cannot submit scoring expressions or traversal predicates.

Snapshot architecture-rule results are available through `GET /snapshot-architecture-rules?snapshotStableKey=...`. The endpoint accepts one required snapshot stable key, optional `category` or `ruleCategory` filter, optional `status` filter, optional `targetStableKey` filter, and bounded paging values. It returns architecture-rule DTOs with the result stable key, rule code, rule name, category, status, target stable key, target kind, display name, description, contributing metric stable keys, contributing edge stable keys, contributing finding stable keys, evidence stable keys, confidence, unknown-state fields, sanitized metadata, and fingerprint. The `ruleCategory` parameter is an alias for `category` so clients can choose the wording that best distinguishes rule-category filtering from other category filters. The endpoint derives results from persisted snapshot facts in the application layer; clients cannot submit custom rule expressions or change built-in rule policy through URL parameters.

Snapshot diff is available through `GET /snapshot-diff?currentSnapshotStableKey=...&previousSnapshotStableKey=...`. The endpoint requires two snapshot stable keys and validates that both snapshots exist and belong to the same repository comparison scope. Optional `domains` filters can select `Nodes`, `Edges`, `Findings`, or `Metrics`; optional `changeKinds` filters can select `Added`, `Removed`, `Changed`, or `Unchanged`. Both filter parameters accept comma-separated values or repeated query values. `includeUnchangedDetails=true` is required when a caller wants unchanged detail rows; unchanged counts are still returned in summaries by default. The endpoint also accepts bounded `skip` and `take` values for deterministic continuation. It returns summary counts, detail rows with stable keys and fingerprints, evidence references, unknown-state fields, changed-field summaries where practical, and truncation metadata.

Latest-to-previous diff is available through `GET /snapshot-diff/latest?repositoryStableKey=...`. This route resolves the two newest comparable snapshots inside the requested repository and optional `solutionStableKey` scope, then runs the same stable-key and fingerprint comparison used by explicit diff. It exists for dashboard and MCP clients that need the common “what changed since the last completed extraction?” question without first listing snapshots or reading Neo4j directly. If fewer than two comparable snapshots exist, the endpoint returns a validation problem instead of fabricating an empty diff. Both explicit and latest diff support additional exact filters for `projectStableKey`, `targetStableKey`, `recordKind`, and finding `severity`. The project filter matches owning or related project context where the compared domain can supply it. The target filter matches target node identities, edge endpoints, finding affected nodes, or metric targets. The record-kind filter matches the public kind field, such as a node kind, edge kind, rule code, or metric kind. These are controlled filters, not arbitrary graph predicates, and they are intentionally designed to satisfy broad API and future MCP triage flows without exposing Cypher.

Cross-domain search is available through `GET /search?repositoryStableKey=...&searchText=...`. The route resolves an exact snapshot or deterministic `latest`/`current` snapshot inside one repository and optional solution scope, then searches supported public fields across project nodes, semantic symbols, runtime records, architecture facts, evidence records, findings, and metrics. The optional `resultKinds` filter accepts the controlled values `Project`, `Symbol`, `RuntimeEndpoint`, `Fact`, `Evidence`, `Finding`, and `Metric`; it also accepts comma-separated or repeated values. Search is deliberately simple and bounded. It is not full-text source search, an AI retrieval index, a graph traversal language, or a way to run arbitrary predicates. It matches stable keys, display text, qualified names, safe summary fields, evidence paths or previews already persisted by extraction, finding rule and title data, and metric names or kinds. Source snippets remain untrusted display content, and search never expands snippets beyond persisted evidence previews.

A search result contains a result kind, stable key, display text, summary, snapshot stable key, confidence, evidence stable keys, related node stable keys, unknown-state fields, and one or more deterministic follow-up affordances. A **follow-up affordance** is a machine-readable next query suggestion, such as a route and parameter set for opening a project detail, symbol detail, evidence detail, finding detail, metric list, runtime endpoint list, or graph neighbourhood. Follow-up affordances are important for WP015 MCP readiness because a tool can continue from search into a more specific controlled endpoint while still using stable keys and approved parameters. The search endpoint therefore verifies the intended architecture boundary: planned MCP search can depend on the HTTP query surface instead of direct Neo4j access.

## Dashboard summary reads

A typical dashboard flow starts after an extraction run has completed and the caller knows the repository stable key from the extraction request or run status. Request `/dashboard-summary?repositoryStableKey=repository%3A%2F%2Fcustomer-estate&snapshotStableKey=latest` to resolve the newest matching snapshot. If a caller is reviewing one submitted solution, add `solutionStableKey=solution%3A%2F%2Fcustomer-estate%2FCustomer.slnx`. If a caller is comparing a historical run, pass the exact snapshot stable key instead of `latest`.

The response envelope starts by explaining the applied scope and snapshot. For example, `scope.repositoryStableKey` tells the client which repository was used, `snapshot.snapshotStableKey` tells the client which persisted graph state produced the counts, and `snapshot.resolvedAsLatest` distinguishes a convenience latest request from an exact historical selection. The `page` metadata says the endpoint is not paged because the dashboard returns one aggregate object. The `truncation` metadata is still present because nested sections such as top hotspots are intentionally bounded even though the endpoint itself is not a page.

The data section is intentionally compact. `counts.projectCount`, `counts.apiCount`, `counts.workerCount`, `counts.endpointCount`, `counts.dataContextCount`, and `counts.hotlistFindingCount` summarize established graph facts in the selected snapshot. `topHotspots` contains stable `hotspot://` identities and target stable keys so a client can drill into the full hotspot endpoint later. `latestChanges` contains compact domain and change-kind counts against the previous scoped snapshot when one exists. The dashboard endpoint does not expose raw evidence snippets, raw graph property maps, Cypher text, or store-local identifiers.

The most important operational detail is that the dashboard summary is honest about incomplete optional data. A first snapshot has no previous snapshot to diff, so `latestChanges` is an unknown section rather than an empty section with no explanation. A snapshot without metrics or findings cannot calculate top hotspots, so `topHotspots` is also reported as unknown. This explicit unknown pattern lets a human dashboard and an automated MCP client make the same safe decision: show the available counts, but avoid implying that the unavailable sections were calculated and found empty.

## Paging, ordering, and response limits

Symbol search, symbol usage, runtime endpoint, runtime entry-point, runtime worker, data-access fact, configuration usage, integration fact, and UI-technology fact reads use a default page size of fifty records and a maximum page size of two hundred records because semantic, runtime, and architecture-fact estates can be dense and evidence previews require a tighter public response boundary. For those endpoints, `skip` must be greater than or equal to zero, and `take` must be inside the endpoint's supported range. Invalid paging values return deterministic validation-problem responses rather than being silently clamped.

This difference is part of the safety boundary. Query APIs should be useful for dashboards, triage views, bounded traversal views, metric summaries, and future MCP consumers without becoming unbounded graph export mechanisms. A bounded response gives a caller enough records to continue deterministically, while validation-problem responses teach automated consumers how to fix requests that fall outside the supported bounds. Traversal endpoints add a second boundary in addition to list paging: traversal depth must be within the supported maximum, `take` must stay within the configured edge-result maximum, and edge-kind filters must be drawn from the controlled graph vocabulary. Invalid depth, result-size, direction, or edge-kind values return validation-problem responses rather than being silently expanded.

Snapshot diff details are ordered by domain, change kind, and record stable key after filters and unchanged-detail rules are applied. Cross-domain search results are ordered by result kind, display text, and stable key so a broad query returns repeatable pages even when several result families match the same text. Deterministic ordering makes paging repeatable for tests and consumers, and it avoids returning data in incidental database order. When adding a new filter or sort path, keep the ordering stable and update targeted tests before relying on the behavior in clients.

WP013 and WP014 validation errors are deliberately field-like and stable. Missing snapshot identity on list endpoints is reported against the relevant snapshot stable-key parameter. Invalid list paging is reported with `skip` or `take`. Snapshot diff aggregates request problems into named error groups such as `CurrentSnapshotRequired`, `PreviousSnapshotRequired`, `CurrentSnapshotNotFound`, `PreviousSnapshotNotFound`, `IncompatibleRepository`, `RepositoryStableKeyRequired`, `RepositoryNotFound`, `SolutionNotFound`, `PreviousComparableSnapshotNotFound`, `UnsupportedDomain`, `UnsupportedChangeKind`, `SkipInvalid`, and `TakeInvalid`. Search aggregates request problems into named error groups such as `RepositoryStableKeyRequired`, `SnapshotSelectorInvalid`, `RepositoryNotFound`, `SolutionNotFound`, `SnapshotNotFound`, `SearchTextRequired`, `UnsupportedResultKind`, `SkipInvalid`, and `TakeInvalid`. The endpoints can therefore tell a caller that a comparison requested an unsupported change kind, that a search requested an unsupported result family, or that a required selector is missing, without exposing stack traces, database exceptions, source snippets, or graph query details.

## Finding detail and evidence references

A finding detail response expands the hotlist item with the full finding description, knowledge kind, primary node and evidence stable keys, first-seen and latest-seen snapshot keys, suppression reason and actor when present, sanitized metadata, and fingerprint. The response still does not require direct graph access. A client that needs to explain why a finding exists can show the rule identity, affected node stable keys, evidence reference stable keys, confidence, unknown reason, and history without issuing Cypher.

The metadata exposed by the query service is defensive. Metadata keys must already be stable lower camel case, and obvious secret-bearing names such as password, secret, token, and connection-string style fields are omitted from public query DTOs. This sanitizer is shared by project detail, rule detail, finding detail, metric, cycle, hotspot, and architecture-rule response shaping so the API boundary behaves consistently. It does not replace extractor-level redaction; it is a final API-boundary safeguard. Contributors should continue to redact secret-like source and configuration values before they become graph facts, then treat the query API sanitizer as another defense in depth.

Operational logging follows the same safety model. WP013 endpoint diagnostics use `ILogger` abstractions and log fixed endpoint names plus paging counts or truncation state. They intentionally do not log submitted stable keys, evidence stable keys, metadata, filter values, source snippets, repository paths, raw graph data, or secrets. A developer investigating an endpoint should be able to see that a bounded query was handled and how many records matched, but should use controlled API responses and persisted evidence references for detailed review rather than expecting logs to become a parallel graph export.

The integrated WP012 validation path proves this redaction boundary from the rule side through the query side. A representative security-sensitive rule matches a configuration location fact that says a secret-like value existed, but the graph facts, finding metadata, hotlist summary, finding detail metadata, extraction warnings, and suppression flow carry only safe location and unknown-state text. In practical terms, a finding can tell a reviewer that `app.config` contains a connection-string location and that the raw value was redacted; it must not echo the connection string itself in rule output, diagnostics, logs, metadata, or API responses. This is why security-sensitive rules should be written against location indicators such as `ConnectionStringLocation` rather than against credential literals.

## History and suppression

Finding history is based on the finding history key, not on Neo4j internal IDs. The history response returns first-seen and latest-seen snapshot stable keys plus compact historical finding records. Each historical record includes the snapshot stable key, finding stable key, status, severity, confidence, and fingerprint so a consumer can link back to the detail endpoint for the exact snapshot-owned record.

Suppression is exposed through `POST /findings/suppressions`. A suppression request must provide finding history key, rule code, rule version, primary node stable key, reason, and suppressed-by identity. The application validates these fields before persistence and returns validation problems for missing audit data. A successful suppression updates matching current findings to `Suppressed` and stores the suppression so later equivalent findings can inherit it. The underlying finding record is not deleted; suppression is an overlay that preserves auditability and historical fidelity.

A typical triage flow is therefore: list `/hotlist?snapshotStableKey=...&severity=High`, open one item through `/findings/detail`, review the rule through `/rules/{ruleCode}/{version}`, inspect history through `/finding-history?historyKey=...`, and, when policy allows, post a suppression with a clear reason and actor. At no point does the client need unrestricted graph access or raw evidence snippets.

## Metric reads

A typical metric flow is shorter but follows the same safety model: obtain the completed `snapshotIdentity` from `GET /extractions/{runId}`, then request `/snapshot-metrics?snapshotStableKey=...&metricKind=SnapshotNodeCount`. The response is a bounded page even when a filter normally matches one snapshot-level metric. To inspect one project, pass the project identity as `projectStableKey`, for example `/snapshot-metrics?snapshotStableKey=...&scopeKind=Project&projectStableKey=project%3A%2F%2Fsrc%2FCustomer.Api%2FCustomer.Api.csproj`. To inspect graph metrics for the same architecture node, use node scope and a graph metric kind such as `/snapshot-metrics?snapshotStableKey=...&scopeKind=Node&metricKind=GraphFanOut&projectStableKey=project%3A%2F%2Fsrc%2FCustomer.Api%2FCustomer.Api.csproj`. The parameter name remains `projectStableKey` for compatibility with the first project metric slice, but the filter is technically a node stable-key filter. The value field is typed as optional numeric plus optional text because some metrics are categorical rather than purely numeric. `SnapshotNodeCount` uses the numeric value and the unit `nodes`; `ProjectTargetFrameworkRisk` uses both a numeric risk score and a text risk category; graph metrics such as `GraphFanIn`, `GraphDependencyDepth`, and `GraphCycleParticipation` use numeric values with explicit unknown-state text when traversal or cycle detection is bounded by configured limits.

Modernization metrics use the same endpoint rather than a separate modernization-only route. For example, `/snapshot-metrics?snapshotStableKey=...&metricKind=ModernizationOutOfSupportTargetCount&scopeKind=Project&projectStableKey=project%3A%2F%2Fsrc%2FLegacyWeb%2FLegacyWeb.csproj` returns the out-of-support target count for one project when that metric was produced for the snapshot. Snapshot-level modernization reads omit `projectStableKey` and can filter by metric kinds such as `ModernizationLegacyTechnologyCount`, `ModernizationSecuritySensitiveFindingCount`, `ModernizationFrameworkOnlyDependencyCount`, `ModernizationDataAccessSpread`, or `ModernizationSharedTableUsageCount`. Repository and solution rollups also use `nodeStableKey` internally, so clients can pass their stable key through the same `projectStableKey` query parameter until a later query API revision introduces a more general target parameter name. Modernization metric metadata explains the calculation source, contributing project stable keys, contributing fact counts, and whether Archon used any inference; current behavior records `modernizationInference` as `None` because these values are derived from extracted facts and persisted findings rather than AI assumptions.

Metric metadata is sanitized before leaving the application layer just like finding metadata. Secret-bearing metadata keys are omitted from public DTOs, and normalized fields such as stable keys, scope, confidence, unknown state, and fingerprint remain first-class properties rather than metadata. This shape lets a dashboard show a metric value while still explaining whether the value was calculated with complete inputs.

## Bounded graph traversal reads

A typical traversal flow starts from a project catalogue or project detail response. The client follows a stable node identity, usually a `project://...` key, into a traversal endpoint rather than asking for arbitrary graph execution. Direct dependency reads answer “what does this node depend on immediately?” Direct dependent reads answer “what depends on this node immediately?” Transitive reads answer the same questions across multiple bounded hops, and neighbourhood reads combine incoming and outgoing direction for local graph context.

Traversal uses breadth-first expansion over approved edge kinds. Breadth-first means Archon inspects all matching one-hop relationships before moving to the next hop, which keeps the returned view close to the selected node and predictable under a depth limit. The endpoint returns the stable edges that matched the traversal plus the stable nodes needed to explain those edges. It does not return unrelated nodes, containment-only structure, or evidence snippets. Evidence appears as stable evidence keys so the client can follow later evidence-focused surfaces without turning traversal into a source-code export.

Depth and result limits are part of the contract. Depth controls how many hops Archon may walk from the start node. The result limit controls how many edge DTOs are serialized. If more matching edges exist than can be returned, truncation metadata and a warning make the partial response visible. This matters for dense estates where one shared library or integration node can have many dependents. A truncated response is still useful as a bounded view, but it is not a proof that no additional relationships exist.

Dependency path reads are intentionally different from traversal reads. A path query asks whether one source node can reach one target node by following outgoing dependency-like edges within the requested depth. A found path returns nodes and edges in display order. A no-path response means Archon had graph edges to inspect and did not find a bounded route between the two supplied nodes. An unavailable response means the selected snapshot did not contain graph edge support for path search, so the absence of a path must not be interpreted as architecture proof.

## Cycle reads

A typical cycle review flow starts from a completed extraction run's `snapshotIdentity`, then requests `/snapshot-cycles?snapshotStableKey=...`. To focus on one architecture node, pass `nodeStableKey`, for example `/snapshot-cycles?snapshotStableKey=...&nodeStableKey=project%3A%2F%2Fsrc%2FCustomer.Api%2FCustomer.Api.csproj`. The response does not expose a general traversal language. Instead, Archon applies the configured dependency edge-kind set, removes duplicate rotations of the same cycle, and returns bounded stable DTOs that are ready for UI, MCP, or report consumers.

Cycle stable keys use the `cycle://` prefix and are derived from the canonical node and edge path. A client should treat that key as the identity of the canonical cycle for the snapshot, while the `nodeStableKeys` and `edgeStableKeys` arrays explain the path. Evidence stable keys identify the source artifacts that explain individual edge hops when those edges have primary evidence. Cycle metadata records the canonical path, dependency edge kinds, traversal depth limit, result limit, and truncation state. The related `GraphCycleParticipation` metric uses detected cycles to count how many returned canonical cycles contain each node, so metric consumers can sort nodes by cycle pressure and then call `/snapshot-cycles` to inspect the path-level evidence.

## Hotspot reads

A typical hotspot flow starts after a completed extraction has produced a snapshot identity. Request `/snapshot-hotspots?snapshotStableKey=...` to retrieve the bounded triage list. To focus on one category, add `category=HighFanIn`, `category=DataAccessSpread`, or another stable hotspot category. To focus on one node or snapshot target, add `targetStableKey=...`. The query is intentionally exact-match and bounded; it is not a general graph query language and it does not let callers change scoring formulas through URL parameters.

Hotspot categories are explainable mappings from existing facts. High fan-in, high fan-out, dependency depth, transitive dependency count, and cycle participation come from graph node metrics. Shared-library pressure is also based on fan-in because a project or node with many incoming dependencies is likely to have broader change impact. Data-access spread and shared table usage come from modernization metrics. Hotlist finding concentration groups open findings by affected node and keeps the contributing finding and evidence stable keys so a reviewer can move from the hotspot to the underlying finding detail.

Scores are numeric and ranks are deterministic within each category. The current default thresholds are documented in the graph domain model: fan-in and fan-out require at least five, shared-library fan-in requires at least eight, data-access spread requires at least three projects, shared table usage requires at least two shared table identities, finding concentration requires at least three open findings, dependency depth requires at least four hops, transitive dependency count requires at least ten reachable nodes, and cycle participation requires at least one detected cycle. These defaults are conservative triage values rather than organization-specific policy. Future rule-catalog threshold integration can replace the threshold provider while preserving the same stable hotspot DTO shape.

Confidence and unknown state remain visible in hotspot responses. When several findings contribute to one hotspot, the current composition uses the lowest contributor confidence so the hotspot does not overstate certainty. Unknown-state reasons from contributing facts are preserved when present. Metadata explains threshold and score source, but public DTOs continue to sanitize secret-like metadata names just like finding, metric, and cycle responses.

## Architecture-rule reads

A typical architecture-rule flow starts from the completed extraction run's `snapshotIdentity`, then requests `/snapshot-architecture-rules?snapshotStableKey=...`. To focus on generic layering checks, add `category=ArchitectureLayering` or `ruleCategory=ArchitectureLayering`. To inspect only proven violations, add `status=Violation`; to inspect checks that need human review, add `status=ReviewRequired`; to inspect incomplete evidence, add `status=Unknown`. To focus on a single project or controller, pass its stable key as `targetStableKey`. The query remains exact-match and bounded so it is suitable for dashboards, MCP consumers, and triage tools without becoming an unrestricted rule engine endpoint.

Architecture-rule result statuses have different meanings. `Violation` means the current graph facts prove a generic boundary breach, such as a domain project referencing infrastructure. `ReviewRequired` means the facts indicate change risk rather than a hard violation, such as a shared library whose `GraphFanIn` metric crosses the review threshold. `Unknown` means the check is relevant but the evidence is incomplete. For example, a worker project can declare messaging-oriented runtime metadata, but if no `Queue` or `Topic` dependency edge is present, Archon reports an unknown worker-messaging result instead of guessing that the design is wrong.

The built-in checks intentionally stay generic. They cover source-brief layering and dependency patterns such as domain-to-infrastructure references, domain-to-web references, non-web references to web projects, direct LINQ to SQL use from application projects, direct DataContext use from controllers, worker projects whose expected queue/topic dependencies are absent from the graph, and high fan-in shared libraries that require review before change. Organization-specific exceptions are not hard-coded in the query endpoint. Policy-like choices live behind evaluation options or configured rule definitions, while the response preserves contribution references so a reviewer can inspect the exact edge, metric, finding, or evidence that caused the result.

## Snapshot diff and cross-domain search reads

A typical diff flow starts with two completed extraction runs for the same repository. Use the later run's `snapshotIdentity` as `currentSnapshotStableKey` and the earlier run's `snapshotIdentity` as `previousSnapshotStableKey`, then request `/snapshot-diff?currentSnapshotStableKey=...&previousSnapshotStableKey=...`. The endpoint compares four domains: `Nodes`, `Edges`, `Findings`, and `Metrics`. To inspect only metric changes, add `domains=Metrics`. To inspect newly introduced and removed graph records together, use `changeKinds=Added,Removed`. To page through a large response, use `skip` and `take`; the `truncation` object reports the total matching detail rows, the returned count, the applied bounds, and whether rows were omitted before or after the page.

Diff classification uses stable keys first and fingerprints second. Stable keys are the logical identity of records across snapshots, while fingerprints summarize diff-relevant content. If a stable key appears only in the current snapshot, the record is `Added`. If it appears only in the previous snapshot, it is `Removed`. If the same stable key appears in both snapshots with different fingerprints, it is `Changed`. If both stable key and fingerprint match, it is `Unchanged`. This means a changed metric value for an existing metric identity is a changed metric row, not a removal plus an addition. The same principle applies to project nodes, dependency edges, and findings.

Unchanged records are intentionally summarized differently from changed records. Summary counts always include unchanged totals so drift dashboards can show how much of each domain stayed stable. Detail rows for unchanged records are omitted unless the caller sets `includeUnchangedDetails=true`. This default keeps responses useful for triage and future MCP consumption because large repositories often have far more unchanged records than drift records. When unchanged details are requested, they are still ordered and bounded by the same deterministic detail-row rules as other change kinds.

The current changed-field summary is explanatory rather than a replacement for record-level fingerprints. For changed rows, the response always includes `fingerprint` in the changed-field list and can add known public fields such as display name, kind, evidence stable keys, or unknown-state changes when those values differ. The underlying comparison remains stable-key/fingerprint based, so contributors should treat changed-field names as a guide to likely causes, then inspect the relevant graph fact, finding, metric, or evidence record for full context.

When a client needs the most common drift view, it can request `/snapshot-diff/latest?repositoryStableKey=repository%3A%2F%2Fcustomer-estate&domains=Findings&changeKinds=Added,Changed&severity=Critical&take=20`. That request finds the newest two comparable snapshots in the repository, compares them, then narrows output to new or changed critical findings. A more project-focused review can add `projectStableKey` or `targetStableKey`. These filters are useful for automation because they let a future MCP tool ask a precise question such as “what critical findings were introduced for this project since the previous extraction?” and receive stable finding keys, evidence keys, target node keys, and fingerprints without any direct database connection.

Search reads complement diff reads. A typical discovery flow starts with `/search?repositoryStableKey=repository%3A%2F%2Fcustomer-estate&snapshotStableKey=latest&searchText=Orders&resultKinds=Project,Symbol,RuntimeEndpoint,Fact,Evidence,Finding,Metric&take=20`. A human or MCP client can inspect the returned result kind and follow-up affordances. A project result points toward project detail, a symbol result points toward symbol detail, an evidence result points toward evidence detail, a finding result points toward finding detail, and a metric result points toward the metric list route. The affordance is deliberately a route plus stable parameters rather than executable code or prompt text. This keeps follow-up behavior deterministic, auditable, and safe for automation.

Search is not expected to prove completeness across every possible source-code phrase. It is a bounded navigation surface over already persisted architecture facts. If search returns no rows for a valid snapshot, the response is successful and includes an explicit unknown entry for `searchResults` so callers can distinguish “nothing matched the controlled search fields” from “the API failed” or “direct Neo4j access is needed.” Contributors adding a new result family should preserve this boundary: add stable result kinds, safe public fields, bounded paging, evidence references where available, explicit unknowns for incomplete data, and deterministic follow-up affordances into existing controlled endpoints.

## Controlled management and operations

Controlled management endpoints live under `/management`, with local monitoring probes at `/health` and `/ready`. They are intentionally narrow. Repository registration through `POST /management/repositories` records repository identity, name, root metadata, optional source-control metadata, approved metadata fields, and audit-ready metadata. It does not start extraction, scan the repository, create snapshots, mutate arbitrary graph records, or accept raw persistence commands. Solution registration through `POST /management/solutions` associates a repository-relative `.sln` or `.slnx` path with a registered repository stable key. The path policy mirrors the extraction boundary: a solution path must stay inside the repository scope and must not be an absolute path or `..` traversal shape.

Metadata management uses `PATCH /management/metadata` and is deliberately an overlay rather than an unrestricted property editor. A **metadata allowlist** is the set of field names that management callers may set, such as owner, description, environment, tags, and business unit. Requests that try to set raw graph fields, query text, database commands, or unapproved operational payloads are rejected with validation problems before state changes. This keeps metadata useful for operational annotation while preserving the distinction between normalized graph facts and management annotations.

Snapshot lifecycle and retention are separate concepts. `GET /management/snapshots` lists lifecycle rows by repository, optional solution, status, date range, and commit SHA when those fields are available. A **snapshot lifecycle row** is the operational view of a snapshot header: stable snapshot key, repository key, optional solution key, status, branch or commit metadata, timestamps, and diagnostic counts. `POST /management/retention` validates retention boundaries before reporting or applying candidates. A **retention boundary** is the explicit scope and rule that decides which snapshots are candidates, such as a repository stable key, optional solution stable key, `keepLatest`, and `deleteBeforeUtc`. A dry run reports candidates without deletion. A non-dry-run operation still remains limited to candidate snapshot identities inside the requested lifecycle scope; it is not an arbitrary delete endpoint.

Extraction run history is available through `GET /management/runs`. The response exposes run identity, status, timestamps, progress stage and message, warning and error counts, submitted solution paths, metadata keys, and produced snapshot identity when available. It intentionally exposes metadata keys rather than metadata values because run metadata can contain operational context that should remain out of public responses. Rule enablement uses `PUT /management/rules/enablement` to record an enablement overlay for one rule code and version. That overlay can affect later rule/finding query interpretation when a host wires it into rule evaluation or query composition, but it does not edit rule JSON files on disk and does not rewrite historical rule definitions.

Controlled maintenance uses `POST /management/maintenance` and accepts only allowlisted operation names such as rebuilding read models, compacting management state, or validating the rule cache. The endpoint returns explicit outcome, warnings, errors, and audit metadata. It rejects raw Cypher, SQL, shell commands, filesystem paths intended for mutation, and code-modification requests. Health and readiness are designed for local development and automation. `/health` answers whether the management module itself can respond. `/ready` reports sanitized dependency names and states, such as snapshot lifecycle, extraction run history, and rule catalog readiness, without returning connection strings, credentials, endpoint URLs, or driver exceptions.

For example, a local operator can register `repository://customer-estate`, register `solution://customer-estate/Customer.slnx`, then call `/management/snapshots?repositoryStableKey=repository%3A%2F%2Fcustomer-estate&status=Completed` to inspect completed snapshots. Before cleanup, the operator should call `/management/retention` with `dryRun=true`, `keepLatest=2`, and a `deleteBeforeUtc` boundary. The response lists candidate stable snapshot keys and audit metadata. Only after that bounded preview should the caller choose a non-dry-run request. At no point does the flow require direct Neo4j access, arbitrary delete commands, or shell execution.

The same triage flow is what the current end-to-end application test validates without launching the Aspire AppHost. It loads copied-output JSON rules, upserts versioned catalog entries, evaluates enabled rules over established graph facts, constructs deterministic findings, persists them in the application finding store, queries the hotlist and detail/history DTOs, posts a suppression command, and then re-reads the finding detail to confirm the status changed to `Suppressed`. That test is intentionally application-layer focused: it proves the behavior contract without starting a product UI, introducing MCP resources, exporting markdown, computing snapshot diffs, or running automatic remediation.

## Current boundaries

The query and management APIs are the minimum product surface for dashboard summary, project catalogue, project detail, bounded dependency traversal, dependency path, graph neighbourhood, symbol search/detail/usage, runtime endpoint/controller/entry-point/worker, data-access fact, configuration usage, integration fact, UI-technology fact, evidence drill-down, related-evidence lookup, rule catalog, finding, snapshot metric, snapshot cycle, snapshot hotspot, snapshot architecture-rule result, snapshot diff, latest-to-previous snapshot diff, cross-domain search reads, repository and solution registration, constrained metadata management, snapshot lifecycle, retention, extraction run history, rule enablement, controlled maintenance, health, and readiness. They do not introduce MCP graph tools, markdown export, automatic remediation, a Discovery UI, arbitrary graph traversal, arbitrary source-code export, configuration value export, credential inspection, organization-specific rule-authoring UI, target-application runtime reflection, UI rendering, arbitrary graph or database mutation, arbitrary deletion, shell execution, code modification, or a general-purpose Neo4j browser. Endpoint security remains limited to the host security model currently available in the repository; this slice adds controlled validation, authorization seams in route boundaries, audit-ready metadata, and response shaping, not a new authentication or authorization subsystem.
