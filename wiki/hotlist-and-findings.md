# Controlled Analysis Queries

The hotlist is the controlled product-facing view over persisted WP012 findings. A **finding** is a snapshot-owned analysis result produced by a versioned rule, and the hotlist turns those records into bounded API responses that API clients and future MCP tools can consume without reading Neo4j directly. This page assumes familiarity with [rule catalog and rule engine](rule-catalog-and-rule-engine.md), because hotlist records are meaningful only when the reader understands rule identity, finding stable keys, history keys, confidence, unknown state, and suppression.

The same controlled-query model now includes snapshot metric reads, dependency cycle reads, architecture hotspot reads, architecture-rule result reads, and snapshot diff reads. A **metric** is a snapshot-owned calculated value such as `SnapshotNodeCount`; it is useful for dashboards, future diff views, and automated review because callers can ask for a stable historical value instead of recomputing facts during every read. A **dependency cycle** is a directed path through dependency-like architecture edges that returns to its starting node, such as one project referencing another project that eventually references the first project again. A **hotspot** is a deterministic triage result that combines metrics, findings, graph facts, and cycle participation into an explainable architecture-review target. An **architecture-rule result** is a bounded query result from a generic built-in rule check over graph, metric, finding, runtime, and semantic facts. A **snapshot diff** is a bounded comparison between two persisted snapshots that reports architecture drift across nodes, edges, findings, and metrics.

## Controlled query surface

The current query API exposes rule catalog, hotlist, finding detail, finding history, suppression, snapshot metric, snapshot cycle, snapshot hotspot, snapshot architecture-rule result, and snapshot diff endpoints through the API host. These endpoints deliberately do not expose arbitrary Cypher, unrestricted graph-query execution, or raw graph property maps. A caller supplies only approved filters, page bounds, route identities, or suppression fields, and the application layer translates those inputs into stable DTOs. A **DTO**, or data transfer object, is the public response shape that protects clients from infrastructure-specific implementation details.

The rule catalog endpoints are `GET /rules` and `GET /rules/{ruleCode}/{version}`. The list endpoint supports exact filters for rule code, version, category, severity, enabled state, built-in state, and owner scope. The detail endpoint returns one exact rule code/version pair. Rule identity remains the pair of rule code and version, so an older finding can still point to the precise version that classified it even after a newer rule version exists.

The hotlist endpoint is `GET /hotlist`. It lists persisted findings with approved filters for snapshot stable key, category, severity, status, project stable key, and affected node stable key. Results include rule code and version, title, summary, severity, status, confidence, optional category, affected-node references, evidence references, and unknown-state information. Evidence is returned as references rather than as raw snippets, because evidence snippets can contain source text or configuration fragments that must not be exposed accidentally through summary lists.

Finding detail is available through `GET /findings/{snapshotStableKey}/{findingStableKey}` and the query-parameter form `GET /findings/detail?snapshotStableKey=...&findingStableKey=...`. The query-parameter form exists because stable keys commonly contain slash-like separators such as `snapshot://...` or `finding://...`, and HTTP path decoding can make those values awkward for some clients. Both forms resolve the same application query. Finding history is available through `GET /findings/history/{historyKey}` and the query-parameter form `GET /finding-history?historyKey=...` for the same route-safety reason.

Snapshot metrics are available through `GET /snapshot-metrics?snapshotStableKey=...` and the route form `GET /snapshots/{snapshotStableKey}/metrics`. The query-parameter form is preferred when a snapshot stable key contains `://` or other slash-like separators. Metric list filters are intentionally small: callers can supply one snapshot stable key, optional metric kind, optional scope kind, optional project stable key, and bounded paging values. The project stable-key filter matches the metric `nodeStableKey`, which is how project-scoped metrics identify their target project and how graph node-scoped metrics identify their target architecture node. The response returns stable public identities, metric kind, scope kind, optional target and evidence references, numeric or text value, unit, confidence, unknown-state fields, sanitized metadata, and fingerprint. It does not return Neo4j internal IDs or accept raw graph predicates.

Snapshot dependency cycles are available through `GET /snapshot-cycles?snapshotStableKey=...`. The endpoint accepts one required snapshot stable key, an optional `nodeStableKey` filter, and bounded paging values. It returns cycle DTOs with the cycle stable key, stable node path, stable edge path, evidence stable keys, confidence, unknown-state fields, truncation state, sanitized metadata, and fingerprint. The node path repeats the first node as the final value so clients can display the closure directly. The edge path has one edge stable key per hop. The endpoint uses the query-parameter form because snapshot and node stable keys frequently contain `://` separators that are safer to pass as encoded query values than as path segments.

Snapshot hotspots are available through `GET /snapshot-hotspots?snapshotStableKey=...`. The endpoint accepts one required snapshot stable key, optional `targetStableKey` and `category` filters, and bounded paging values. It returns hotspot DTOs with the hotspot stable key, category, target stable key, target kind, display name, score, rank, contributing metric stable keys, contributing finding stable keys, evidence stable keys, confidence, unknown-state fields, sanitized metadata, and fingerprint. Hotspot reads are derived from persisted snapshot facts in the application layer; clients cannot submit scoring expressions or traversal predicates.

Snapshot architecture-rule results are available through `GET /snapshot-architecture-rules?snapshotStableKey=...`. The endpoint accepts one required snapshot stable key, optional `category` or `ruleCategory` filter, optional `status` filter, optional `targetStableKey` filter, and bounded paging values. It returns architecture-rule DTOs with the result stable key, rule code, rule name, category, status, target stable key, target kind, display name, description, contributing metric stable keys, contributing edge stable keys, contributing finding stable keys, evidence stable keys, confidence, unknown-state fields, sanitized metadata, and fingerprint. The `ruleCategory` parameter is an alias for `category` so clients can choose the wording that best distinguishes rule-category filtering from other category filters. The endpoint derives results from persisted snapshot facts in the application layer; clients cannot submit custom rule expressions or change built-in rule policy through URL parameters.

Snapshot diff is available through `GET /snapshot-diff?currentSnapshotStableKey=...&previousSnapshotStableKey=...`. The endpoint requires two snapshot stable keys and validates that both snapshots exist and belong to the same repository comparison scope. Optional `domains` filters can select `Nodes`, `Edges`, `Findings`, or `Metrics`; optional `changeKinds` filters can select `Added`, `Removed`, `Changed`, or `Unchanged`. Both filter parameters accept comma-separated values or repeated query values. `includeUnchangedDetails=true` is required when a caller wants unchanged detail rows; unchanged counts are still returned in summaries by default. The endpoint also accepts bounded `skip` and `take` values for deterministic continuation. It returns summary counts, detail rows with stable keys and fingerprints, evidence references, unknown-state fields, changed-field summaries where practical, and truncation metadata.

## Paging, ordering, and response limits

Every list endpoint uses bounded paging. The rule catalog and hotlist endpoints remain aligned with the WP012 query contract: they normalize negative `skip` values to zero, apply a default page size of fifty records, and clamp oversized `take` values to the current maximum of two hundred records. The WP013 endpoints are stricter because they are intended to be consumed by later MCP tools and other automation that should repair malformed requests instead of guessing what the server did. Snapshot metric, cycle, hotspot, architecture-rule result, and snapshot diff reads use a default page size of one hundred records and a maximum page size of five hundred records. For those endpoints, `skip` must be greater than or equal to zero, and `take` must be between one and five hundred. Invalid paging values return deterministic validation-problem responses rather than being silently clamped.

This difference is part of the safety boundary. Query APIs should be useful for dashboards, triage views, metric summaries, and future MCP consumers without becoming unbounded graph export mechanisms. A bounded response gives a caller enough records to continue deterministically, while validation-problem responses teach automated consumers how to fix requests that fall outside the supported bounds.

Ordering is deterministic. Rules are ordered by rule code and version. Findings are ordered by severity, rule code, and finding stable key in the current query implementation. Metrics are ordered by metric kind, scope kind, and metric stable key. Cycles are ordered by canonical stable path and cycle stable key after duplicate rotations have been removed. Hotspots are ordered by category, category-local rank, target stable key, and hotspot stable key. Architecture-rule results are ordered by category, rule code, status, target stable key, and result stable key. Snapshot diff details are ordered by domain, change kind, and record stable key after filters and unchanged-detail rules are applied. Deterministic ordering makes paging repeatable for tests and consumers, and it avoids returning data in incidental database order. When adding a new filter or sort path, keep the ordering stable and update targeted tests before relying on the behavior in clients.

WP013 validation errors are deliberately field-like and stable. Missing snapshot identity on list endpoints is reported against the relevant snapshot stable-key parameter. Invalid list paging is reported with `skip` or `take`. Snapshot diff aggregates request problems into named error groups such as `CurrentSnapshotRequired`, `PreviousSnapshotRequired`, `CurrentSnapshotNotFound`, `PreviousSnapshotNotFound`, `IncompatibleRepository`, `UnsupportedDomain`, `UnsupportedChangeKind`, `SkipInvalid`, and `TakeInvalid`. The endpoint can therefore tell a caller that a comparison requested an unsupported change kind and also that one of the snapshots is missing, without exposing stack traces, database exceptions, or graph query details.

## Finding detail and evidence references

A finding detail response expands the hotlist item with the full finding description, knowledge kind, primary node and evidence stable keys, first-seen and latest-seen snapshot keys, suppression reason and actor when present, sanitized metadata, and fingerprint. The response still does not require direct graph access. A client that needs to explain why a finding exists can show the rule identity, affected node stable keys, evidence reference stable keys, confidence, unknown reason, and history without issuing Cypher.

The metadata exposed by the query service is defensive. Metadata keys must already be stable lower camel case, and obvious secret-bearing names such as password, secret, token, and connection-string style fields are omitted from public query DTOs. This sanitizer is shared by rule detail, finding detail, metric, cycle, hotspot, and architecture-rule response shaping so the API boundary behaves consistently. It does not replace extractor-level redaction; it is a final API-boundary safeguard. Contributors should continue to redact secret-like source and configuration values before they become graph facts, then treat the query API sanitizer as another defense in depth.

Operational logging follows the same safety model. WP013 endpoint diagnostics use `ILogger` abstractions and log fixed endpoint names plus paging counts or truncation state. They intentionally do not log submitted stable keys, evidence stable keys, metadata, filter values, source snippets, repository paths, raw graph data, or secrets. A developer investigating an endpoint should be able to see that a bounded query was handled and how many records matched, but should use controlled API responses and persisted evidence references for detailed review rather than expecting logs to become a parallel graph export.

The integrated WP012 validation path proves this redaction boundary from the rule side through the query side. A representative security-sensitive rule matches a configuration location fact that says a secret-like value existed, but the graph facts, finding metadata, hotlist summary, finding detail metadata, extraction warnings, and suppression flow carry only safe location and unknown-state text. In practical terms, a finding can tell a reviewer that `app.config` contains a connection-string location and that the raw value was redacted; it must not echo the connection string itself in rule output, diagnostics, logs, metadata, or API responses. This is why security-sensitive rules should be written against location indicators such as `ConnectionStringLocation` rather than against credential literals.

## History and suppression

Finding history is based on the finding history key, not on Neo4j internal IDs. The history response returns first-seen and latest-seen snapshot stable keys plus compact historical finding records. Each historical record includes the snapshot stable key, finding stable key, status, severity, confidence, and fingerprint so a consumer can link back to the detail endpoint for the exact snapshot-owned record.

Suppression is exposed through `POST /findings/suppressions`. A suppression request must provide finding history key, rule code, rule version, primary node stable key, reason, and suppressed-by identity. The application validates these fields before persistence and returns validation problems for missing audit data. A successful suppression updates matching current findings to `Suppressed` and stores the suppression so later equivalent findings can inherit it. The underlying finding record is not deleted; suppression is an overlay that preserves auditability and historical fidelity.

A typical triage flow is therefore: list `/hotlist?snapshotStableKey=...&severity=High`, open one item through `/findings/detail`, review the rule through `/rules/{ruleCode}/{version}`, inspect history through `/finding-history?historyKey=...`, and, when policy allows, post a suppression with a clear reason and actor. At no point does the client need unrestricted graph access or raw evidence snippets.

## Metric reads

A typical metric flow is shorter but follows the same safety model: obtain the completed `snapshotIdentity` from `GET /extractions/{runId}`, then request `/snapshot-metrics?snapshotStableKey=...&metricKind=SnapshotNodeCount`. The response is a bounded page even when a filter normally matches one snapshot-level metric. To inspect one project, pass the project identity as `projectStableKey`, for example `/snapshot-metrics?snapshotStableKey=...&scopeKind=Project&projectStableKey=project%3A%2F%2Fsrc%2FCustomer.Api%2FCustomer.Api.csproj`. To inspect graph metrics for the same architecture node, use node scope and a graph metric kind such as `/snapshot-metrics?snapshotStableKey=...&scopeKind=Node&metricKind=GraphFanOut&projectStableKey=project%3A%2F%2Fsrc%2FCustomer.Api%2FCustomer.Api.csproj`. The parameter name remains `projectStableKey` for compatibility with the first project metric slice, but the filter is technically a node stable-key filter. The value field is typed as optional numeric plus optional text because some metrics are categorical rather than purely numeric. `SnapshotNodeCount` uses the numeric value and the unit `nodes`; `ProjectTargetFrameworkRisk` uses both a numeric risk score and a text risk category; graph metrics such as `GraphFanIn`, `GraphDependencyDepth`, and `GraphCycleParticipation` use numeric values with explicit unknown-state text when traversal or cycle detection is bounded by configured limits.

Modernization metrics use the same endpoint rather than a separate modernization-only route. For example, `/snapshot-metrics?snapshotStableKey=...&metricKind=ModernizationOutOfSupportTargetCount&scopeKind=Project&projectStableKey=project%3A%2F%2Fsrc%2FLegacyWeb%2FLegacyWeb.csproj` returns the out-of-support target count for one project when that metric was produced for the snapshot. Snapshot-level modernization reads omit `projectStableKey` and can filter by metric kinds such as `ModernizationLegacyTechnologyCount`, `ModernizationSecuritySensitiveFindingCount`, `ModernizationFrameworkOnlyDependencyCount`, `ModernizationDataAccessSpread`, or `ModernizationSharedTableUsageCount`. Repository and solution rollups also use `nodeStableKey` internally, so clients can pass their stable key through the same `projectStableKey` query parameter until a later query API revision introduces a more general target parameter name. Modernization metric metadata explains the calculation source, contributing project stable keys, contributing fact counts, and whether Archon used any inference; current behavior records `modernizationInference` as `None` because these values are derived from extracted facts and persisted findings rather than AI assumptions.

Metric metadata is sanitized before leaving the application layer just like finding metadata. Secret-bearing metadata keys are omitted from public DTOs, and normalized fields such as stable keys, scope, confidence, unknown state, and fingerprint remain first-class properties rather than metadata. This shape lets a dashboard show a metric value while still explaining whether the value was calculated with complete inputs.

## Cycle reads

A typical cycle review flow starts from a completed extraction run's `snapshotIdentity`, then requests `/snapshot-cycles?snapshotStableKey=...`. To focus on one architecture node, pass `nodeStableKey`, for example `/snapshot-cycles?snapshotStableKey=...&nodeStableKey=project%3A%2F%2Fsrc%2FCustomer.Api%2FCustomer.Api.csproj`. The response does not expose a general traversal language. Instead, Archon applies the configured dependency edge-kind set, removes duplicate rotations of the same cycle, and returns bounded stable DTOs that are ready for UI, MCP, or report consumers.

Cycle stable keys use the `cycle://` prefix and are derived from the canonical node and edge path. A client should treat that key as the identity of the canonical cycle for the snapshot, while the `nodeStableKeys` and `edgeStableKeys` arrays explain the path. Evidence stable keys identify the source artifacts that explain individual edge hops when those edges have primary evidence. Cycle metadata records the canonical path, dependency edge kinds, traversal depth limit, result limit, and truncation state. The related `GraphCycleParticipation` metric uses detected cycles to count how many returned canonical cycles contain each node, so metric consumers can sort nodes by cycle pressure and then call `/snapshot-cycles` to inspect the path-level evidence.

## Hotspot reads

A typical hotspot flow starts after a completed extraction has produced a snapshot identity. Request `/snapshot-hotspots?snapshotStableKey=...` to retrieve the bounded triage list. To focus on one category, add `category=HighFanIn`, `category=DataAccessSpread`, or another stable hotspot category. To focus on one node or snapshot target, add `targetStableKey=...`. The query is intentionally exact-match and bounded; it is not a general graph query language and it does not let callers change scoring formulas through URL parameters.

Hotspot categories are explainable mappings from existing facts. High fan-in, high fan-out, dependency depth, transitive dependency count, and cycle participation come from graph node metrics. Shared-library pressure is also based on fan-in because a project or node with many incoming dependencies is likely to have broader change impact. Data-access spread and shared table usage come from modernization metrics. Hotlist finding concentration groups open findings by affected node and keeps the contributing finding and evidence stable keys so a reviewer can move from the hotspot to the underlying finding detail.

Scores are numeric and ranks are deterministic within each category. The current default thresholds are documented in the graph domain model: fan-in and fan-out require at least five, shared-library fan-in requires at least eight, data-access spread requires at least three projects, shared table usage requires at least two shared table identities, finding concentration requires at least three open findings, dependency depth requires at least four hops, transitive dependency count requires at least ten reachable nodes, and cycle participation requires at least one detected cycle. These defaults are conservative triage values rather than organization-specific policy. Future rule-catalog threshold integration can replace the threshold provider while preserving the same stable hotspot DTO shape.

Confidence and unknown state remain visible in hotspot responses. When several findings contribute to one hotspot, the current composition uses the lowest contributor confidence so the hotspot does not overstate certainty. Unknown-state reasons from contributing facts are preserved when present. Metadata explains threshold and score source, but public DTOs continue to sanitize secret-like metadata names just like finding, metric, and cycle responses.

## Architecture-rule reads

A typical architecture-rule flow starts from the completed extraction run's `snapshotIdentity`, then requests `/snapshot-architecture-rules?snapshotStableKey=...`. To focus on generic layering checks, add `category=ArchitectureLayering` or `ruleCategory=ArchitectureLayering`. To inspect only proven violations, add `status=Violation`; to inspect checks that need human review, add `status=ReviewRequired`; to inspect incomplete evidence, add `status=Unknown`. To focus on a single project or controller, pass its stable key as `targetStableKey`. The query remains exact-match and bounded so it is suitable for dashboards, MCP consumers, and triage tools without becoming an unrestricted rule engine endpoint.

Architecture-rule result statuses have different meanings. `Violation` means the current graph facts prove a generic boundary breach, such as a domain project referencing infrastructure. `ReviewRequired` means the facts indicate change risk rather than a hard violation, such as a shared library whose `GraphFanIn` metric crosses the review threshold. `Unknown` means the check is relevant but the evidence is incomplete. For example, a worker project can declare messaging-oriented runtime metadata, but if no `Queue` or `Topic` dependency edge is present, Archon reports an unknown worker-messaging result instead of guessing that the design is wrong.

The built-in checks intentionally stay generic. They cover source-brief layering and dependency patterns such as domain-to-infrastructure references, domain-to-web references, non-web references to web projects, direct LINQ to SQL use from application projects, direct DataContext use from controllers, worker projects whose expected queue/topic dependencies are absent from the graph, and high fan-in shared libraries that require review before change. Organization-specific exceptions are not hard-coded in the query endpoint. Policy-like choices live behind evaluation options or configured rule definitions, while the response preserves contribution references so a reviewer can inspect the exact edge, metric, finding, or evidence that caused the result.

## Snapshot diff reads

A typical diff flow starts with two completed extraction runs for the same repository. Use the later run's `snapshotIdentity` as `currentSnapshotStableKey` and the earlier run's `snapshotIdentity` as `previousSnapshotStableKey`, then request `/snapshot-diff?currentSnapshotStableKey=...&previousSnapshotStableKey=...`. The endpoint compares four domains: `Nodes`, `Edges`, `Findings`, and `Metrics`. To inspect only metric changes, add `domains=Metrics`. To inspect newly introduced and removed graph records together, use `changeKinds=Added,Removed`. To page through a large response, use `skip` and `take`; the `truncation` object reports the total matching detail rows, the returned count, the applied bounds, and whether rows were omitted before or after the page.

Diff classification uses stable keys first and fingerprints second. Stable keys are the logical identity of records across snapshots, while fingerprints summarize diff-relevant content. If a stable key appears only in the current snapshot, the record is `Added`. If it appears only in the previous snapshot, it is `Removed`. If the same stable key appears in both snapshots with different fingerprints, it is `Changed`. If both stable key and fingerprint match, it is `Unchanged`. This means a changed metric value for an existing metric identity is a changed metric row, not a removal plus an addition. The same principle applies to project nodes, dependency edges, and findings.

Unchanged records are intentionally summarized differently from changed records. Summary counts always include unchanged totals so drift dashboards can show how much of each domain stayed stable. Detail rows for unchanged records are omitted unless the caller sets `includeUnchangedDetails=true`. This default keeps responses useful for triage and future MCP consumption because large repositories often have far more unchanged records than drift records. When unchanged details are requested, they are still ordered and bounded by the same deterministic detail-row rules as other change kinds.

The current changed-field summary is explanatory rather than a replacement for record-level fingerprints. For changed rows, the response always includes `fingerprint` in the changed-field list and can add known public fields such as display name, kind, evidence stable keys, or unknown-state changes when those values differ. The underlying comparison remains stable-key/fingerprint based, so contributors should treat changed-field names as a guide to likely causes, then inspect the relevant graph fact, finding, metric, or evidence record for full context.

The same triage flow is what the current end-to-end application test validates without launching the Aspire AppHost. It loads copied-output JSON rules, upserts versioned catalog entries, evaluates enabled rules over established graph facts, constructs deterministic findings, persists them in the application finding store, queries the hotlist and detail/history DTOs, posts a suppression command, and then re-reads the finding detail to confirm the status changed to `Suppressed`. That test is intentionally application-layer focused: it proves the behavior contract without starting a product UI, introducing MCP resources, exporting markdown, computing snapshot diffs, or running automatic remediation.

## Current boundaries

The query API is the minimum product surface for rule catalog, finding, snapshot metric, snapshot cycle, snapshot hotspot, snapshot architecture-rule result, and snapshot diff reads. It does not introduce MCP graph tools, markdown export, automatic remediation, a Discovery UI, arbitrary graph traversal, organization-specific rule-authoring UI, or a general-purpose Neo4j browser. Endpoint security remains limited to the host security model currently available in the repository; this slice adds controlled validation and response shaping, not a new authentication or authorization subsystem.
