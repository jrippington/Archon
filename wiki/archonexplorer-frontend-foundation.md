# ArchonExplorer Frontend Foundation

ArchonExplorer is the browser-facing user interface foundation for Archon. In the current implementation, it exists as a standalone Vite, React, and TypeScript application in `src/ArchonExplorer`, renders a visible desktop-style workbench foundation shell with local activity navigation, contextual primary sidebar placeholders, persisted layout preferences, a controllable bottom panel, a keyboard-driven command palette, a shell notification placement seam, a tabbed work area, shell-state recovery rules, focused Playwright browser validation, and safe placeholder boundaries, exposes the shared ArchonApi route catalog, includes the typed request executor and safe error model, provides the first typed operational API client, defines stable TanStack Query keys and extraction polling helpers, provides deterministic runtime test doubles, shows safe API connectivity state in the shell status bar, includes a safe notification runtime for transient operation messages, includes the API-backed Extraction Center history, start-submission, selected-run monitoring, background run monitor, command palette, duplicate-request, and produced-snapshot placeholder handoff surface, and is composed by the Aspire AppHost as a local Vite resource. A **frontend foundation** is the smallest runnable browser application structure that later product work can extend without replacing the package manager, bootstrap path, provider model, component-system seam, configuration seam, shell frame, local workbench-state seam, preference-persistence seam, command-palette seam, notification-placement seam, browser-validation seam, route-construction seam, request-execution seam, operational-client seam, server-state seam, polling seam, test-double seam, connectivity-state seam, notification seam, diagnostic-safety model, or local distributed-application hosting path. This page describes the current frontend, shell, route catalog, request transport foundation, operational client, query-key convention, extraction polling support, runtime test doubles, safe connectivity status path, notification runtime, safe error shaping, browser validation, and Aspire-hosted development foundation. Detailed current Extraction Center behavior now lives on [ArchonExplorer Extraction Center](archonexplorer-extraction-center.md); full snapshot context activation, snapshot administration, and analytical feature screens remain intentionally out of scope.

The foundation is intentionally separate from the ASP.NET Core API and MCP hosts. ArchonExplorer is not an ASP.NET Core-hosted SPA template and is not a Next.js application. It is an npm-managed Vite application that can be restored, typechecked, and built from its own project directory. The AppHost composes that application for local development, but the source of browser behavior remains the frontend folder. That separation keeps browser runtime concerns in `src/ArchonExplorer` while the .NET hosts continue to own API, MCP, persistence, and local composition behavior.

## Current application shape

The current frontend project lives under `src/ArchonExplorer` and uses npm as its package manager. The package manifest exposes three scripts:

```powershell
cd .\src\ArchonExplorer
npm install
npm run typecheck
npm run build
```

`npm install` restores the frontend dependency graph and maintains `package-lock.json`, which is the deterministic npm lockfile for this application. `npm run typecheck` runs the TypeScript build in type-checking mode without emitting browser assets. `npm run build` runs the same TypeScript project references and then asks Vite to produce a production build in the local `dist` output folder. The generated `dist` folder is a build artifact, not contributor-authored source.

The source layout keeps bootstrap, runtime providers, configuration, and styling concerns easy to find:

```text
src/ArchonExplorer/
  index.html
  package.json
  package-lock.json
  tsconfig.json
  tsconfig.app.json
  tsconfig.node.json
  vite.config.ts
  src/
	main.tsx
	App.tsx
	index.css
	api/
	config/
	providers/
	test-e2e/
```

`index.html` supplies the Vite HTML entry point and the `root` element that React mounts into. `src/main.tsx` is the browser bootstrap path. It locates the required root element, enables React `StrictMode`, and wraps the application in the centralized provider tree. `src/App.tsx` reads safe API configuration state and composes the visible workbench shell without calling an API. The shell implementation lives under `src/components/workbench`, reusable component primitives live under `src/components/ui`, shared helpers live under `src/lib`, and browser-side ArchonApi runtime foundations live under `src/api`.

The focused browser-validation setup also belongs to the frontend project. `playwright.config.ts` sits beside the Vite configuration, starts the local Vite server for browser journeys, and points Playwright at `src/test-e2e`. Keeping this configuration local matters because Playwright validates the browser shell rather than the .NET hosts. Reports and test results are local validation artifacts, not wiki or source-of-truth documentation, and they should not be moved to the repository root.

## ArchonApi route catalog

The current frontend includes an **ArchonApi route catalog** in `src/ArchonExplorer/src/api/archonApiRoutes.ts`. A route catalog is a single source of truth for HTTP path construction. Instead of letting each future feature type strings such as `/extractions`, `/management/snapshots`, or `/dashboard-summary` by hand, ArchonExplorer groups the current ArchonApi paths by API area and exports documented constants or route builders. This is intentionally modest infrastructure: it does not execute `fetch`, parse JSON, create query keys, or render a feature screen. It makes later client code safer by removing the need to rediscover route spelling and path-parameter encoding rules in every feature package.

The catalog mirrors the current API host rather than a generated OpenAPI client or a roadmap-only endpoint list. It includes operational routes such as `/health` and `/ready`, extraction routes such as `/extractions` and `/extractions/{runId}`, management routes such as `/management/snapshots` and `/management/runs`, and the implemented controlled-query groups for dashboard summary, projects, graph traversal, symbols, runtime facts, architecture facts, evidence, rules, findings, metrics, cycles, hotspots, architecture-rule results, snapshot diff, and search. Query-string construction deliberately stays out of literal path constants. Later runtime slices can add typed query objects and request execution around these base paths without changing the route identities.

The no-common-`/api` route convention is part of the contract. ArchonApi maps public routes directly at the application root, so the browser catalog must use `/health`, `/extractions`, and `/projects` instead of `/api/health`, `/api/extractions`, or `/api/projects`. This matters because a browser-only prefix would create a contract that the server does not expose and could hide route drift until feature work begins. The route tests therefore sample constants and builder outputs to prove that no exported route equals `/api` or starts with `/api/`.

A **route builder** is a function that inserts caller-supplied values into a route path after encoding them as path segments. The catalog uses builders for values such as extraction run identifiers, snapshot stable keys, project stable keys, rule identities, finding stable keys, and finding history keys. A **stable key** is a durable public identity and often looks URI-like, for example `snapshot://repository/solution/current`. URI-like values can contain slash characters, hash characters, or other delimiters. The catalog uses `encodeURIComponent` through a small local helper so a stable key remains one logical route value rather than being split into accidental path segments.

For example, a later snapshot administration feature should build a delete-one path through the catalog:

```typescript
archonApiRoutes.management.snapshotByStableKey('snapshot://repository/solution/current')
```

That expression produces a path shaped like `/management/snapshots/snapshot%3A%2F%2Frepository%2Fsolution%2Fcurrent`, preserving the stable key as a single encoded route value. The same principle applies to catch-all backend routes such as `/projects/{*projectStableKey}` and `/findings/history/{*historyKey}`. The backend may accept catch-all segments, but the frontend still encodes stable keys so route construction is deterministic and safe before query execution exists.

## API client foundation and request execution

The current frontend now includes the first browser-side **API client foundation** under `src/ArchonExplorer/src/api`. An API client foundation is the shared boundary that every later feature should use when it needs to communicate with ArchonApi. It is deliberately smaller than a full feature client: it does not render an Extraction Center, Snapshot Admin, project catalogue, search page, graph view, evidence panel, findings workbench, or notification center. Instead, it centralizes the low-level rules that those future features would otherwise duplicate: how to read the configured API base URL, how to combine that base URL with a route-catalog path, how to serialize typed query parameters, how to send JSON request bodies, how to parse JSON success responses, how to treat empty responses, how to honor cancellation, and how to convert failures into safe frontend errors.

The **request executor** is the transport helper in `src/api/request.ts`. A request executor is a small wrapper around browser-native `fetch` that returns a typed success-or-failure result rather than throwing raw browser or server diagnostics into components. It reads the same `VITE_ARCHON_API_BASE_URL` configuration seam described later on this page. If the base URL is absent, the executor returns a normalized `configuration` error and does not call `fetch`. If the base URL is present, it builds an absolute URL from the configured base, a route-catalog path such as `/health` or `/management/snapshots`, and a typed query object. Undefined and null query values are omitted; array values repeat the same key so ASP.NET Core can bind ordinary repeated query parameters. Request bodies are serialized as JSON and receive `Content-Type: application/json`; every request asks for `application/json` responses.

Successful JSON responses are parsed by the executor and returned as typed data. Empty success responses, such as a `204 No Content` result, are represented as successful responses with `undefined` data. The executor intentionally treats non-JSON success content and malformed JSON as `unexpectedResponse` failures. That may look strict, but it is the safe foundation for a workbench that will later render operational and architecture data. Feature code should not silently accept ambiguous text, HTML error pages, proxy diagnostics, or partially parsed data when the route contract says JSON.

Cancellation is also part of the foundation. Callers may pass an `AbortSignal`, which is the browser-native cancellation object used by `fetch` and by server-state libraries such as TanStack Query. The executor forwards that signal into the request and returns a normalized `cancelled` error if the caller aborts. It also supports timeout-compatible cancellation through a `timeoutMs` option. Timeout cancellation returns a separate `timeout` category, which lets later UI code distinguish a user navigation or unmount from a request that hung longer than the feature allowed. The executor does not add automatic retry behavior, and destructive operations such as snapshot deletion should continue to avoid transport-level automatic retry unless a later approved design proves the retry is safe.

Typed request and response contracts live in `src/api/archonApiTypes.ts`. They cover the operational shapes that later WP004, WP005, and WP006 consumers need first: health and readiness responses, extraction start requests, extraction run status and history responses, snapshot lifecycle rows, delete-one and delete-all snapshot responses, ASP.NET Core problem details, validation-problem details, safe query error envelopes, snapshot selectors, and the normalized frontend error model. These types are not a generated OpenAPI client. They are hand-authored contracts that align with the current ArchonApi shapes while leaving feature-specific query DTO expansion to the work packages that implement those screens.

## Safe diagnostics and error model

**Safe diagnostic shaping** is the process of converting raw failure evidence into messages and metadata that can be shown in the browser without exposing secrets or implementation details. ArchonExplorer performs this shaping in `src/api/errors.ts`. The error model classifies failures into stable categories: `configuration`, `network`, `timeout`, `validation`, `notFound`, `conflict`, `server`, `unexpectedResponse`, `cancelled`, and `unknown`. A feature can use that category to decide whether to show a setup message, a retry affordance, a form validation summary, a not-found state, or a general unavailable state without parsing backend exception text.

The safe error object is intentionally conservative. User-visible messages must not contain raw stack traces, connection strings, environment variable values, credentials, bearer tokens, API keys, raw Cypher, Neo4j internals, driver-specific diagnostics, or arbitrary backend exception text. The frontend therefore fails closed: if a candidate message is empty, too long, or contains unsafe fragments such as `Password=`, `ConnectionString`, `StackTrace`, `System.`, `Neo4j`, `Cypher`, `Bearer`, or stack-trace-like text, it is replaced with a category-specific fallback. This rule applies even when a response appears to be a normal problem-details object. The browser cannot prove that arbitrary server text is safe, so it preserves only the metadata that has passed the safety gate.

A **validation problem** is the ASP.NET Core shape that reports request validation failures as an `errors` dictionary. ArchonExplorer converts that dictionary into field-level or form-level validation issues. Each field name or stable validation code is preserved only after safety checks, and each message is sanitized independently. This means one unsafe validation message does not force the UI to discard every other safe message in the same response. Safe query error envelopes receive similar treatment: the documented `code`, safe `message`, and optional trace identifier are preserved when they pass the redaction gate, then the HTTP status maps the failure into a frontend category such as `conflict`, `notFound`, or `server`.

Consider a future extraction form that submits an empty repository root. ArchonApi may return a validation problem with an error bucket such as `RepositoryRootDirectory` and a safe message saying that the repository root is required. The request executor parses the JSON response, the error shaper recognizes the validation-problem shape, and the component receives a normalized `validation` error with a field issue for `RepositoryRootDirectory`. If a server regression accidentally included `System.InvalidOperationException at ... Password=...` in another validation message, that one message would be replaced with the generic validation fallback before any UI rendered it. The user sees actionable form feedback, while secrets and implementation details stay out of browser state.

## Safe presentation and notification runtime

The current foundation includes a **notification runtime** in `src/providers/NotificationProvider.tsx`. A notification runtime is the application-level provider, hook, helper API, and viewport that lets feature code create transient success, information, warning, or error messages in one consistent place. A **transient notification** is short-lived feedback about a completed or changing operation, such as an extraction start, an extraction completion, an extraction failure summary, snapshot deletion, or API availability change. ArchonExplorer composes the provider through `ApplicationProviders`, so later feature routes and mutation callbacks can publish operation feedback without creating a second toast stack or importing another component library.

The runtime is safe by default. It accepts only controlled notification categories, frontend-authored operation text, normalized API errors, and optional safe metadata such as a stable code or trace identifier. Both operation helpers and direct notifications pass user-visible strings through the same diagnostic sanitizer used by the API client foundation. That means a message containing stack-trace fragments, connection strings, credentials, raw Cypher, Neo4j internals, bearer tokens, API keys, framework exception names, or other unsafe backend detail is replaced with safe fallback copy before it reaches React state. The provider stores only sanitized presentation payloads. It does not store raw thrown values, response bodies, request URLs, configured base URLs, dependency-specific readiness details, or backend diagnostic objects in the notification queue.

The public hook is `useNotifications`. It exposes general `notify` and category-specific helpers for success, information, warning, and normalized-error notifications. Feature code should prefer the specific helpers because they make intent obvious and keep copy near the operation. For example, a future snapshot administration mutation can call the success helper with an operation name such as `Snapshot deleted` after the API confirms deletion. If deletion fails, it should pass the `NormalizedArchonApiError` from the API client foundation to the error helper rather than passing the caught exception or HTTP response body. The resulting notification can display safe user copy and, when present, safe support metadata such as `ARCHON_SNAPSHOT_ACTIVE` or a trace identifier.

Notifications are not a replacement for durable error UI. A validation problem from a form should usually appear near the affected fields or in a persistent page-level summary. A long-lived dependency outage should usually remain visible in page or shell state until the condition changes. The notification runtime therefore carries a `requiresPersistentDisplay` flag for errors that also need page-level representation. This is a reminder to feature authors, not a hidden page renderer. A toast can be dismissed, can disappear from a user's attention before the user has acted, and may not contain all retry context needed for keyboard, screen-reader, or later troubleshooting workflows. A transient notification can supplement those surfaces by announcing that something happened, but it must not be the only representation for persistent page-level failures.

The viewport uses the same shadcn/ui-compatible local styling approach as the rest of the frontend foundation. It is rendered as a fixed application notification region with an accessible label and polite live-region behavior; error notifications use alert urgency while routine success, information, and warning notifications use status semantics. Dismissal is explicit through the local button primitive. The styles use existing theme tokens and local class names rather than marketing-style visual treatments, custom theme colors, or a separate toast package. This keeps notification behavior aligned with the desktop workbench shell and preserves the repository rule that UI styling should remain plain, toolkit-like, and token-based unless a later work item explicitly changes that direction.

Consider a future extraction start flow. The page submits through the typed operational client. If the API accepts the run, the page can publish an informational notification such as `Extraction started` while the page or status area retains the run identifier and polling state. If the run later completes, a success notification can announce completion. If the request fails with a normalized `network` or `server` error, the error helper can produce safe notification text while the page-level extraction surface keeps retry, cancellation, or setup guidance visible. At no point should the feature put raw response text, stack traces, Neo4j driver messages, dependency names, or configured URLs into the notification body.

## Operational API client and connectivity state

The current frontend now includes a typed **operational API client** in `src/api/archonApiClient.ts`. An operational API client is the hand-authored wrapper layer above the route catalog and request executor for near-term operational routes. It does not create product screens, own visual workflows, or replace later feature clients. Its purpose is narrower and foundational: it gives later Extraction Center, Snapshot Admin, dashboard, and diagnostics slices one documented place to call health, readiness, extraction, and snapshot lifecycle operations without spelling routes, HTTP methods, JSON body contracts, cancellation options, or destructive-operation retry intent in components.

The client exposes health and readiness reads through `/health` and `/ready`; extraction operations through `POST /extractions`, `GET /extractions/{runId}`, and `GET /extractions`; snapshot lifecycle reads through `GET /management/snapshots`; destructive snapshot cleanup through `DELETE /management/snapshots/{snapshotStableKey}` and `POST /management/snapshots/delete-all`; and management run history through `GET /management/runs`. All methods delegate path selection to the ArchonApi route catalog and request execution to the request executor. This means route values such as run identifiers and snapshot stable keys still receive the same path-segment encoding described earlier, and query objects still flow through the centralized query serializer instead of becoming hand-built strings.

Destructive snapshot methods carry an explicit no-automatic-retry intent. This matters because a retry policy that is harmless for a health check or list request can be unsafe for a mutation that deletes data. The delete-one method requires a caller-selected snapshot stable key, and the delete-all method accepts the backend confirmation contract rather than hiding the confirmation phrase in the client. Later UI features remain responsible for user confirmation, permission checks, and visible destructive-operation workflows; the foundation only prevents future generic retry helpers from accidentally treating snapshot deletion like an ordinary idempotent read.

ArchonExplorer also includes an **API connectivity state** model in `src/api/connectivity.ts` and a React hook in `src/hooks/useApiConnectivity.ts`. API connectivity state is the safe, machine-readable and user-facing summary of what the browser currently knows about ArchonApi availability. It distinguishes `unconfigured`, `configured`, `checking`, `reachable`, `notReady`, `unreachable`, and `unknown`. `Configured` means only that a base URL exists; it is not proof that the API can be reached. `Checking` means the browser is actively probing the API through TanStack Query. `Reachable` means both the health check and readiness check have completed successfully. `Not ready` means the API responded to health but readiness failed or reported unavailable dependencies. `Unreachable` means the configured endpoint could not be reached or timed out. `Unknown` is the conservative bucket for unexpected response shapes or failures that should not be interpreted more specifically in the shell.

A **health check** is a lightweight operational read that answers whether the API process can respond safely. A **readiness check** is a stronger operational read that answers whether dependencies required for useful work are available. ArchonExplorer intentionally checks health before readiness. If health fails with a network or timeout error, the shell reports the API as unreachable and does not run a second probe that would add noise. If health succeeds but readiness fails with a server-side or dependency-like failure, the shell reports that the API is reachable but dependencies are not ready. The status bar presents only controlled labels such as `Checking API connectivity`, `API reachable and ready`, `API reachable; dependencies not ready`, or `API unreachable`. It does not print the configured base URL, dependency names, response bodies, exception text, stack traces, connection strings, Neo4j diagnostics, raw Cypher, tokens, or other unsafe details.

The status bar remains a minimal runtime surface rather than a diagnostics screen. It consumes `useApiConnectivity` so contributors can observe the setup path while running the shell, but it does not add Extraction Center, Snapshot Admin, global search, graph rendering, evidence inspection, findings workbench, or lenses. A typical local sequence is therefore: start the frontend with `npm run dev`, let the status bar show `API base URL not configured` when no `VITE_ARCHON_API_BASE_URL` exists, or run through the Aspire AppHost so that the frontend receives the local ArchonApi endpoint and the status bar can probe `/health` and `/ready`. If the API is not running, the shell should report an unreachable state using safe text. If the API is running but a dependency such as snapshot lifecycle readiness is unavailable, the shell should report not-ready without exposing the dependency failure internals. This gives later contributors a visible proof that the runtime foundation works while preserving the WP002 boundary against implementing feature screens prematurely.

## TanStack Query keys, extraction polling, and runtime test doubles

ArchonExplorer now has a shared **server state** convention for ArchonApi responses. Server state is data that belongs to the server and is cached in the browser only as a copy, such as health and readiness results, extraction run status, extraction run history, snapshot lifecycle rows, dashboard summaries, search results, project catalogues, graph neighbourhoods, and finding lists. The current frontend uses TanStack Query as the server-state provider, and `src/api/queryKeys.ts` defines stable **query keys** for the server-state families that WP002 knows about. A query key is the structured cache identity that tells TanStack Query whether two reads represent the same server data. The key includes the ArchonApi family, such as `extraction`, `snapshots`, or `search`, plus the scope values that change the returned data, such as repository stable key, solution stable key, snapshot selector, run identifier, filters, pagination, and search text.

The query-key module exists so later feature packages do not invent incompatible literal arrays. For example, extraction run polling uses a key shaped like `['archonApi', 'extraction', 'runs', runId]`, while extraction history uses the extraction history family plus a normalized filter object. Snapshot lifecycle lists use a list-family prefix plus repository, solution, status, date, commit, and take filters. Representative later areas such as dashboard summary, search results, project catalogue, graph neighbourhood, and finding lists already have key builders so contributors can follow the same vocabulary when those screens arrive. The object segments are normalized by removing undefined filters and sorting nested object keys. That normalization is not a replacement for TanStack Query's own hashing; it makes tests, invalidation, and code review easier because equivalent filter objects look equivalent in source and assertion output.

The same module exposes invalidation selectors for extraction and snapshot workflows. Cache invalidation means telling TanStack Query that cached server state may be stale after some operation. Starting or completing an extraction can affect a single run-status query and also the recent history list, so `getExtractionInvalidationKeys` returns the extraction family, history-family, and optional exact run key. Deleting one snapshot or deleting all snapshots can affect snapshot lifecycle lists and explicit snapshot-scoped state, so `getSnapshotInvalidationKeys` returns the snapshot family, list-family, and optional exact snapshot key. Destructive mutations are still excluded from automatic retry behavior. A retry that is acceptable for an idempotent read can be unsafe for snapshot deletion, and the current runtime keeps destructive retry decisions out of generic query-key or polling helpers.

Extraction run status now has a dedicated **polling helper** in `src/api/polling.ts`. A polling helper is a small runtime utility that lets the browser check asynchronous server work repeatedly without creating a tight request loop or scattering stop-condition rules throughout components. The helper recognizes terminal statuses, meaning status values after which no further polling should be scheduled. The current terminal set includes completed, failed, canceled or cancelled, unavailable, and unknown. Active statuses such as running continue polling, while terminal statuses stop the loop. The helper also calculates bounded polling intervals with a simple linear backoff, clamps unsafe caller values, honors `AbortSignal` cancellation, and reports a `stalled` state when an operation exceeds the configured attempt or elapsed-time bounds.

A typical extraction polling scenario works in three stages. First, a later feature starts an extraction through the typed operational client and receives a run identifier. Second, the feature asks TanStack Query to read `GET /extractions/{runId}` using the extraction run query key. Third, the polling helper looks at each status response. If the API says `Running`, the helper returns a safe continuation decision and the next bounded interval. If the API says `Completed`, `Failed`, `Canceled`, `Unavailable`, or `Unknown`, the helper returns a non-continuing state. If the component unmounts or navigation changes the query input, the caller's cancellation signal stops the workflow. If the API never reaches a terminal state within the configured bounds, the helper reports `stalled` using controlled frontend terminology rather than exposing backend internals. `src/hooks/useExtractionRunPolling.ts` demonstrates this pattern through TanStack Query without rendering an Extraction Center screen.

The runtime also includes deterministic **test doubles** in `src/api/testDoubles.ts`. A test double is a safe replacement for a real dependency used by tests. The current ArchonApi client test double returns typed health, readiness, extraction status, extraction history, snapshot lifecycle, delete-one snapshot, and delete-all snapshot responses without running ArchonApi. It records the operation, HTTP method, and route-catalog path for each call so tests can assert behavior without duplicating route strings. Its snapshot deletion methods mutate seeded in-memory rows deterministically and enforce the delete-all confirmation phrase. Its missing-run behavior returns a normalized safe not-found result rather than raw diagnostics. These doubles are intended for component and journey tests that need runtime realism before a live backend or feature screen is involved; they are not a mock server, not a generated API client, and not a substitute for API contract tests.

## Extraction Center history, start-submission, and selected-run monitoring surface

The current frontend includes the first API-backed workbench feature surface: the **Extraction Center**. The Extraction Center is the page area that submits explicit extraction requests, reads compact extraction run summaries from ArchonApi, polls one selected run for status, keeps accepted or selected runs visible in the bottom-panel background monitor, duplicates safely available prior request values into the form, and presents produced-snapshot handoff boundaries inside the existing desktop shell. The current surface lets contributors and users open the Extraction Center activity, focus an `Extraction Center` tab in the tabbed work area, submit a start request through `POST /extractions`, see the accepted run identity returned by the API, review recent extraction history from `GET /extractions`, select a history row, monitor one selected run through `GET /extractions/{runId}`, keep that run visible while another workbench activity is selected, acknowledge terminal monitored runs, run Extraction Center commands from the command palette, duplicate a selected run request without auto-submitting it, and activate an honest produced-snapshot placeholder notification when a completed run exposes `snapshotIdentity`. Detailed workflow guidance lives on [ArchonExplorer Extraction Center](archonexplorer-extraction-center.md).

The feature deliberately consumes the typed operational API client instead of calling `fetch` from React components. The hook in `src/hooks/useExtractionHistory.ts` builds the extraction history query key through `src/api/queryKeys.ts`, forwards TanStack Query cancellation to `ArchonApiClient.getExtractionHistory`, and converts normalized API failures into a safe page-level error. The mutation hook in `src/hooks/useStartExtraction.ts` calls `ArchonApiClient.startExtraction`, converts normalized failures into a safe mutation error, and invalidates extraction history and exact run-status cache keys after an accepted response. That means route spelling, query serialization, base URL handling, response parsing, cancellation, mutation request execution, cache refresh, and diagnostic redaction remain owned by shared runtime seams. Feature code should preserve that layering: if a later Extraction Center component needs a new extraction API call, add or reuse a typed client method and query/mutation hook rather than constructing URLs inside the component.

The visible surface lives under `src/components/extraction-center`. It renders a start form, an accepted-run summary, and the history states that a contributor should expect from the history endpoint: initial loading, empty history, background refetching, safe unavailable/error, and populated history. The **extraction start form** is the browser-owned interaction state for values that have not yet become server state. It asks for a repository root directory, one or more **explicit solution paths**, optional branch name, optional commit SHA, optional requested-by text, and optional newline-delimited metadata entries. An explicit solution path is a user-supplied solution file path that Archon should extract; it is not a directory to scan and not a wildcard. Relative solution paths resolve against the submitted repository root, and the browser performs only convenience validation for obvious missing values or malformed metadata text. The API remains authoritative for path existence, `.sln` extension checks, duplicate detection, and repository-boundary validation.

When a start request is accepted, the page shows an **accepted run** summary and also selects that run for detailed polling. An accepted run is the API-visible lifecycle record created by `POST /extractions` after server validation succeeds. The summary shows the run identifier, status, started timestamp, current progress stage and message, warning count, error count, and snapshot identity when one already exists. Warning and error details are not fabricated when the API supplies only counts. Populated history rows continue to show run identifier, lifecycle status as text, started timestamp, completed timestamp when present, repository root, solution count, warning count, error count, and snapshot identity when present. The row action is now an enabled `View details` control that selects that run for the polling-backed detail surface without navigating away from the desktop shell.

The **selected run detail** region is the durable page-level monitor for one extraction run. Selecting a history row or receiving an accepted start response sets only a local selected run identifier. The run status response itself remains server state owned by TanStack Query and `useExtractionRunPolling`; the component does not copy the status into local shell state or call `fetch` directly. The polling hook uses the exact extraction run query key, passes cancellation through to the typed operational client, and schedules bounded refetch intervals only while the latest status is active. Terminal statuses stop automatic polling. ArchonExplorer treats completed, failed, canceled or cancelled, unavailable, and unknown as terminal states; queued and running remain active states. A failed status request renders a normalized safe not-found or unavailable state, while a selected but not-yet-loaded run renders a loading state. The page therefore distinguishes empty selection, loading, background refetching, failed request, run-not-found, unavailable, active, and terminal states without leaking transport details.

The selected-run monitor displays the run identifier, lifecycle status, submitted request summary, timestamps, progress stage, progress message, optional progress percentage, last-updated timestamp, warning count, error count, top-level timings, produced snapshot identity, and persistence diagnostics when ArchonApi returns them. A **produced snapshot** is the public stable snapshot identity retained by a completed run after the persistence handoff succeeds; the current detail surface displays that identity and provides an `Open produced snapshot` placeholder that publishes a safe notification, but it does not yet open a snapshot context or query graph data. The duplicate request action also belongs here because selected-run status contains the request summary needed to copy repository root, explicit solution paths, branch, commit, and requested-by values without scanning or auto-submitting. Metadata values are intentionally not duplicated because status exposes metadata keys only. Persistence diagnostics are shown only when the API includes the optional `persistenceDiagnostics` section. When present, the UI renders scoped persistence timings, count values, and the completion flag. When absent, the UI explains that diagnostics are unavailable for the selected run rather than treating the response as corrupt or fabricating values. Metadata values are not displayed from the submitted request summary; only metadata keys are shown.

Safe presentation remains the most important boundary for this first real feature surface. History errors and selected-run polling errors show normalized safe messages and retry or setup hints, not raw stack traces, configured URLs, connection strings, database driver details, raw Cypher, Neo4j internals, or arbitrary backend exception text. Submission failures preserve the entered form values and render safe field-level or form-level messages when the API returns validation problems. API setup problems are shown using the existing safe connectivity state; the form may state that the API base URL is not configured, but it does not print environment-variable names, configured endpoint values, or transport details. The history and detail surfaces may display public route text such as `GET /extractions` and `GET /extractions/{runId}` as contributor-facing contract vocabulary, but they must not introduce a common `/api` prefix or expose internal request URLs. Focused Vitest tests cover hook behavior, form mapping, request validation, accepted-run rendering, polling state mapping, selected-run detail rendering, persistence diagnostics, selectable history rows, and safe failure states with deterministic test doubles, while focused Playwright coverage opens the activity from the rail, verifies mocked populated and empty history states, submits a mocked extraction request through the browser accessibility tree, and verifies a selected run transitioning from running to completed.

## Workbench shell model

The current **workbench shell** is the stable desktop-style frame for ArchonExplorer. A shell is not the same thing as a finished product feature. It is the persistent structure around future features: the top application frame, activity rail, primary sidebar, tabbed work area, command/search affordance, command palette, notification host, status bar, theme affordance, and safe setup indicators. Establishing those regions early lets later work packages add extraction, snapshot, search, graph, finding, evidence, and settings behavior without replacing the reader's mental model or rewriting the bootstrap path.

The **activity rail** is the left-side navigation region that names major workbench areas. It now contains keyboard-reachable controls for Dashboard, Extraction Center, Snapshots, Search, Projects, Findings, Diagnostics, and Settings. Selecting most activities updates local shell state and changes the contextual sidebar while staying inside the same browser frame. Selecting Extraction Center additionally opens or focuses the API-backed `Extraction Center` tab so the main work area can render recent run history. It does not navigate to a separate browser page. The distinction matters because activity navigation is implemented shell behavior, Extraction Center history is the first data-backed feature slice, and extraction submission, snapshot administration, search results, project catalogues, finding review, and diagnostics remain future product behavior.

The **primary sidebar** is the contextual navigation region beside the work area. In the current shell, it renders activity-specific headings and lists, such as the current Extraction Center history entry plus future extraction queues, future snapshot selectors, future search filters, or future diagnostics checks. A sidebar placeholder must be honest: it may reserve a future navigation shape, but it must not fabricate counts, architecture facts, extraction runs, snapshot rows, graph data, project names, finding totals, dependency errors, or environment diagnostics. The sidebar uses prose and `Placeholder` labels so contributors can see what each future area will host without mistaking reserved navigation for implemented behavior.

`Extraction Center` tab is now a real feature tab that submits extraction start requests through a TanStack mutation, loads extraction history through TanStack Query, and polls selected run status through the shared extraction polling hook. Other activity tabs remain future placeholders until their work packages provide API-backed content.

**Local workbench state** is the browser-owned state that controls the shell itself. It tracks the active activity, open tabs, active tab, sidebar collapsed placeholder state, bottom-panel visibility state, command-palette visibility placeholder state, and safe layout sizing values. This is different from **server state**, which belongs to ArchonApi and is cached through TanStack Query. Local workbench state may know that the `Extraction Center` tab is open, but it must not store the extraction history rows themselves. It should not store secrets, raw diagnostics, API response bodies, architecture graph facts, extraction run histories, snapshot lists, or search results. Its responsibility is to make the shell interactive and recoverable while feature surfaces use query hooks for their server-backed data.

A **persisted layout preference** is the small browser-local record that remembers non-sensitive shell chrome choices between page loads. ArchonExplorer currently persists the selected activity, primary sidebar width percentage, bottom-panel height percentage, sidebar collapsed state, and bottom-panel visibility. The persisted document is versioned and validated before use. If the stored value is missing, invalid JSON, shaped for a future version, or outside supported size bounds, the shell recovers to default layout preferences instead of crashing or applying untrusted layout data. This storage is deliberately narrow: it excludes API base URLs, secrets, connection strings, raw diagnostics, response bodies, extraction runs, snapshots, graph records, evidence, findings, and architecture facts.

The shell uses simple **resizable panel** separators for the primary sidebar and bottom panel. A resizable panel is a shell region whose visible size can change while the overall workbench frame remains stable. The current implementation stores panel sizes as bounded percentages and exposes keyboard-operable separators with explicit accessible labels. It avoids adding a separate layout component library and keeps the visual treatment plain, desktop-IDE-like, and based on existing theme tokens. Pointer-drag behavior can be added later behind the same percentage state if a later work item needs it, but the current foundation already proves the persistence and accessibility seam.

The **bottom panel** is the lower contextual workbench region reserved for background work, extraction run feedback, and diagnostics. It can be shown or hidden from the shell header, resized through the layout separator, and persisted across reloads. In the current shell it contains a real Extraction Runs background monitor plus safe Background Work and Diagnostics placeholder sections. The Extraction Runs monitor reads status for tracked run identifiers through the typed client and TanStack Query; local feature state stores only run identifiers, acknowledgement flags, and last-notified status strings. It shows active and terminal run status in words, lets users open a run back in Extraction Center, and keeps terminal rows visible until acknowledgement. The diagnostics placeholder explicitly excludes stack traces, connection strings, environment variables, raw Cypher, Neo4j internals, and driver details. Durable errors and retry context still belong in the owning Extraction Center detail surface rather than only in a transient panel.

The **command/search affordance** sits in the top frame and now opens the **command palette** through the visible `Open command palette` button or the documented `Ctrl+K` keyboard shortcut. A command palette is a keyboard-oriented dialog that collects shell-level actions in one searchable list. In ArchonExplorer it is deliberately scoped to local shell behavior: it can switch activities, toggle or focus the bottom panel, focus the required `Workbench Start` tab, reset browser-local layout preferences, and guide the user toward major shell regions. It does not perform browser page navigation, query ArchonApi, inspect the graph, execute arbitrary Cypher, or display architecture search results.

A **shell command** is a named action that changes browser-local workbench state or provides safe transient feedback. Shell commands are grouped as Activities, Panels, Tabs, Layout, Focus, Extraction Center, and Future Search so the command surface is understandable without requiring contributors to inspect implementation code. Extraction Center commands open the feature, request focus on the new request form, request a history refresh, or focus the first visible tracked background run when one exists. They operate through local shell and feature intent state; TanStack Query still owns server-state refreshes. The future-search command is visible because the top-frame affordance still reserves the eventual search location, but it is explicitly labelled unavailable and its execution only publishes safe explanatory feedback. This boundary is important because search-shaped controls can easily imply product capability: the current shell can filter command labels, but global architecture search arrives in a later work package and no search result, graph record, snapshot row, evidence item, or architecture artefact is fabricated.

The command palette also establishes the shell's keyboard flow. Opening the palette moves focus into the command filter input. Pressing `Escape`, using the close button, or executing a command closes the palette and returns focus to the visible command-palette trigger when practical. That focus-return behavior gives keyboard users a stable recovery point in the top frame and keeps command execution inside the same desktop shell instead of relying on browser navigation side effects.

The shell now has focused **browser validation** for that keyboard flow and the current Extraction Center journeys. Browser validation means an automated browser opens the Vite-served application and interacts with the same accessibility tree a user-facing journey depends on. The current Playwright suite checks that the activity rail, primary sidebar, tabbed work area, status bar, command affordance, and notification host are discoverable through roles or accessible names; that `Ctrl+K` or `Meta+K` opens the command palette and places focus in the filter input; that activity switching updates sidebar and status context without page navigation; that bottom-panel visibility can change through both visible controls and shell commands; that status text includes non-color descriptions such as `bottom panel hidden` or `current unavailable`; that opening Extraction Center renders mocked populated or empty history safely through the `GET /extractions` path; that a valid mocked form submission posts to `POST /extractions`, preserves explicit solution paths in the request body, and renders the accepted run identity; that selecting a history row polls `GET /extractions/{runId}` from running to completed before rendering terminal output, produced snapshot identity, and persistence diagnostics; that duplicating a selected run copies safe request values into the form without submitting; and that the produced-snapshot placeholder action publishes safe feedback without calling graph, search, dashboard, lens, visualization, or snapshot-delete routes. This test suite does not prove snapshot administration, search results, graph rendering, or live backend availability, because those remain out of scope. It proves that the shell frame and current API-backed Extraction Center submission/history/detail/action surface are browser-usable before later work packages depend on them.

The `Workbench Start` tab identifies the product as `ArchonExplorer`, explains that the workbench frame is ready, and states that operational and investigation features are pending. The start tab deliberately names absent feature families: extraction runs, snapshots, graph data, search results, lenses, evidence inspection, and findings triage. Contributors should preserve this kind of honest absence when adding future placeholders. A placeholder may orient the user, but it must not look like a feature that has been implemented.

The **status bar** is the bottom frame region reserved for cross-cutting context. It currently reports active snapshot `current` as unavailable, safe API connectivity state from the operational health/readiness path, background work as not running with the bottom-panel visibility stated in words, and the selected workbench activity with no selected item. Those labels reserve future context without relying on color alone and without exposing raw environment variable names, configured API URLs, connection strings, stack traces, Neo4j identifiers, raw Cypher, driver details, dependency internals, or implementation diagnostics.

The **notification host** is the shell placement seam for safe transient messages. The application-level notification runtime still owns the live toast viewport, but the shell now includes a visible host marker that explains where shell-originated messages appear and why transient notifications do not replace persistent error surfaces. The current command palette uses this path for feedback such as layout reset confirmation or unavailable future-search explanation. Persistent errors, validation summaries, retry context, setup problems, and durable feature failures must remain visible in their owning workbench region even when a transient notification announces the same event.

The shell includes a simple light/dark **theme affordance**. Theme selection is implemented through a document-level `data-theme` attribute and CSS custom properties, also called CSS variables. The theme control is intentionally local and lightweight. It proves that the shell has a tokenized light/dark foundation, but it does not persist preferences, synchronize with operating-system theme settings, or introduce a settings store.

A typical contributor walkthrough for the current shell starts by running the frontend with `npm run dev` from `src/ArchonExplorer`. The browser opens into the `Workbench Start` tab with the Dashboard activity selected. Choose `Extraction Center` in the activity rail and observe that the primary sidebar changes to Extraction Center context while the central work area opens the `Extraction Center` tab. With a configured API, the page can submit a repository root and explicit solution paths through the typed start-extraction mutation, read recent run history through the typed history query, and select one run for polling-backed detail through the typed status query. Without a configured API, it shows safe setup feedback rather than a raw URL or exception, and form values remain local so users can correct or retry after configuration changes. Choose `Snapshots` in the activity rail and observe that the primary sidebar changes to snapshot placeholder copy while the shell remains inside the same browser frame. Press `Ctrl+K` or use `Open command palette`, filter for `bottom`, and run `Toggle Bottom Panel`; the bottom panel should open or close through local shell state and can show tracked Extraction Center runs when a run has been accepted or selected. Open the palette again, run `Reset Layout Preferences`, and observe safe transient feedback through the notification runtime. Run or inspect the future architecture search command and confirm that it explains the later-work-package boundary instead of showing results. Then use the separator keyboard controls to adjust reserved panel size, hide the panel, and reload the page. The shell should preserve safe layout choices or recover to defaults if browser-local storage was cleared or corrupted. Choose `Search` or `Diagnostics` and the same pattern repeats: the selected activity changes local shell context, but no graph renders, no raw diagnostics appear, and no future feature data is fabricated. This behavior proves the shell has stable activity, tab, layout, bottom-panel, command, notification, status, and current Extraction Center submission/history/detail/background-monitor/duplicate-request/produced-snapshot-placeholder seams without crossing into the later feature work packages that will supply full snapshot context activation, snapshot administration, search, graph, evidence, or findings workflows.

## Component-system foundation

ArchonExplorer now includes a shadcn/ui-compatible component-system seam. **shadcn/ui** is a copy-and-own component convention rather than a runtime component library in the same sense as a packaged design system. The repository records that convention in `components.json`, uses the `@` path alias for frontend imports, defines CSS custom properties compatible with shadcn token names, and provides minimal local primitives under `src/components/ui`.

The current primitives are intentionally small: `Button`, `Badge`, `Card`, and a local command primitive. They are enough to prove ordinary shell composition, variant-style styling, focus behavior, command-palette grouping, and reusable panel structure. They should not be treated as a license to add unrelated UI frameworks. Future shell, form, table, dialog, command, tab, menu, badge, tooltip, popover, or notification patterns should extend this local primitive approach unless a later work package explicitly chooses another dependency for a well-documented reason.

The CSS remains hand-authored for this slice, while `tailwind.config.ts` and `components.json` preserve shadcn-compatible metadata. This hybrid is deliberate. It avoids expanding the foundation slice into a full styling migration while still making later generated or hand-authored shadcn-style primitives line up with the same aliases and tokens.

## Safe unavailable states and accessibility

Unavailable states in ArchonExplorer must be safe and specific. Safe means that the user can understand what is missing without seeing internal implementation details. The current shell reports only whether API base URL configuration exists; it does not print the configured URL, raw `VITE_` key name, exception text, driver type names, Neo4j internal identifiers, stack traces, or other sensitive diagnostics. When later work packages add real API calls, error handling should continue that pattern by converting dependency failures into controlled, user-facing messages.

The shell also avoids conveying state by color alone. Disabled or unavailable actions include explanatory text and labels. The command/search affordance includes prose that separates local shell commands from future global architecture search. The command palette groups actions by purpose, uses text descriptions, moves focus into the palette on open, and provides a stable close path. The status bar states each status in words. Interactive controls use native buttons, accessible labels, disabled or `aria-disabled` attributes where appropriate, semantic landmarks, and visible focus outlines. These basics matter because later workbench areas will become keyboard-heavy investigation workflows; the foundation should already model accessible interaction rather than postpone it.

## Runtime provider seam

A **runtime provider seam** is the React boundary where application-wide services are attached once and then made available to every component below it. ArchonExplorer currently exposes this seam through `src/providers/ApplicationProviders.tsx`. The provider creates one TanStack Query `QueryClient` for the browser page lifetime, supplies it through `QueryClientProvider`, and nests the notification runtime so every later workbench surface can publish safe operation messages from the same application-level queue.

TanStack Query is present as the shared server-state provider for the browser runtime. The current connectivity hook uses it for the global health/readiness probe, and the extraction polling hook demonstrates how a later feature can use the shared query-key and polling conventions for one long-running operation. Feature-specific screens still remain deferred to later work packages. The provider keeps one cache and one policy surface for future controlled API client work, search results, snapshot lists, polling, and other server-backed state. The initial query defaults disable automatic retries and refetch-on-window-focus behavior so later features must make deliberate choices about user-visible loading and retry behavior; destructive operations continue to carry explicit no-retry intent through the operational client. The notification provider adds the complementary transient presentation seam, but it does not change TanStack Query cache behavior and does not make notifications the owner of persistent loading or error state.

## Aspire-hosted local development

The Aspire AppHost in `src/Archon` now declares ArchonExplorer as a **Vite resource**. A Vite resource is an Aspire-managed JavaScript application that runs the frontend development server as part of the local distributed application model. This means contributors can continue to run the frontend directly with `npm run dev`, but they can also launch the AppHost when they need to inspect the API, MCP host, Neo4j container, and browser shell together.

The AppHost uses the frontend project directory rather than copying UI code into the .NET host. It starts ArchonExplorer through the frontend package script named `dev`, waits for `ArchonApi` for local startup ordering, and passes the API HTTP endpoint to the frontend through the Vite-compatible `VITE_ARCHON_API_BASE_URL` environment value. The environment value is a development-time configuration seam, not a secret. It lets the shell report that API base URL configuration exists without hardcoding a localhost port into React source.

This composition preserves the ownership boundary. The AppHost may describe that ArchonExplorer exists, where it runs from, which API endpoint it should know about in local development, and which resource it should wait for. It must not contain React components, API client code, workbench state, routing behavior, graph visualization behavior, or user-interface feature logic. When future work packages add functional API calls, those calls should live behind frontend or application-layer seams rather than inside `src/Archon/Program.cs`.

Manual Aspire verification should be performed from the repository root when a contributor needs the full local distributed application:

```powershell
dotnet run --project .\src\Archon\Archon.csproj
```

After the Aspire dashboard opens, confirm that `neo4j`, `ArchonApi`, `ArchonMcp`, and `ArchonExplorer` appear as resources. Open the ArchonExplorer resource URL from the dashboard and confirm that the workbench shell renders with the same safe placeholder states described on this page. Stop the AppHost after verification. This is a manual smoke check because the AppHost is a long-running orchestration process and may require local container support for Neo4j.

## API base URL configuration seam

ArchonExplorer reads a development-time API base URL through the Vite environment key `VITE_ARCHON_API_BASE_URL`. A **Vite environment key** is a configuration value that Vite exposes to browser code only when the name is prefixed with `VITE_`. That prefix matters because browser code must not receive arbitrary process environment values, secrets, connection strings, credentials, or infrastructure diagnostics.

The current configuration adapter lives in `src/config/apiConfiguration.ts`. It trims the configured value and returns a safe object that distinguishes two setup states: configured and not configured. When the AppHost runs ArchonExplorer, it supplies this value from the `ArchonApi` HTTP endpoint. When the frontend is run directly through npm, a contributor may supply the same `VITE_ARCHON_API_BASE_URL` key manually or leave it unset. The adapter itself still does not validate connectivity and does not display the raw environment-variable name in the UI. The request executor consumes the same safe adapter and fails with a normalized configuration error when the value is absent. The connectivity hook is the layer that decides when to call `/health` and `/ready`, and its output remains safe status text rather than raw endpoint or dependency diagnostics.

When the value is absent, ArchonExplorer should still start. An unconfigured API base URL is an operational setup state, not a frontend crash. When the value is present, the UI can report that configuration exists, but this is not proof that the API is reachable or healthy. Contributors should preserve that distinction when adding later API calls.

## Current exclusions

The current frontend foundation implements the Extraction Center's API-backed recent-history, start-submission, selected-run detail polling, bottom-panel background extraction monitoring, command palette integration, duplicate-request, and produced-snapshot placeholder handoff slices. It does not yet implement full snapshot context activation, snapshot administration screens, search results, investigation tabs, graph views, lenses, evidence inspection, a notification center, authentication, authorization, persisted theme preferences, or settings behavior. The route catalog, request executor, operational client, query-key helpers, polling helpers, runtime test doubles, connectivity hook, and notification runtime should not be mistaken for those feature workflows: they centralize route construction, transport behavior, typed contracts, operational method boundaries, cache identity, polling decisions, deterministic test seams, safe connectivity status, safe transient operation messages, and safe error shaping only. Those omissions are part of the staged implementation plan rather than accidental missing features.

This means contributors should avoid adding feature calls, navigation behavior, server-state queries, graph rendering, notification-center behavior, or settings persistence to the shell as incidental cleanup. New behavior should follow the relevant work-package step so that documentation, validation, AppHost wiring, API-client wrappers, notification usage, and component-system decisions stay aligned.
