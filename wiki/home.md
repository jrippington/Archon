# Archon

Archon is a .NET architecture-intelligence platform whose foundation is being built around small, independently runnable hosts. The repository now provides the initial runtime slices and the first Neo4j persistence-foundation capabilities: the API host and MCP host start as ASP.NET Core processes, expose operational probe endpoints, and can be composed together through the Aspire AppHost, while `src/Archon.Infrastructure.Neo4j` provides validated Neo4j connection configuration, official driver lifecycle management, a readiness health check, idempotent graph schema initialization, explicitly guarded graph recreation for local development and tests, and snapshot persistence for repositories, solutions, snapshot headers, architecture nodes, architecture relationships, evidence, versioned rule catalog entries, findings, metrics, and generated summaries. The platform still does not expose extraction orchestration, query APIs, MCP tool, markdown export, or user-interface behavior.

The term **service defaults** means shared host configuration that every runtime process uses instead of copying the same setup into each executable project. Archon keeps those defaults in `src/Archon.ServiceDefaults`. The defaults currently configure health checks, OpenTelemetry-compatible logging/metrics/tracing, Aspire-style service discovery, and resilient `HttpClient` behavior. Keeping this cross-cutting setup in one project helps later work packages add real API and MCP features without drifting away from a consistent runtime foundation.

The current operational probe model uses two endpoints. The `/health` endpoint is the **readiness** probe: it runs the registered health checks and answers whether the process is ready to accept work. The `/alive` endpoint is the **liveness** probe: it uses a lightweight self-check to answer whether the process itself is responsive. This distinction matters because a process can be alive before every dependency is ready. The Neo4j infrastructure adapter now contributes a dependency-specific readiness check named `neo4j` when a host opts into `AddArchonNeo4j`; that check opens a read session and runs a tiny `RETURN 1 AS healthy` Cypher query. It proves connection configuration, authentication, network reachability, database selection, and query execution without creating graph schema or requiring any architecture data.

Developers can run the hosts independently while working on the foundation:

```powershell
dotnet run --project .\src\ArchonApi\ArchonApi.csproj
dotnet run --project .\src\ArchonMcp\ArchonMcp.csproj
```

After a host starts, browse or request `/health` and `/alive` on the assigned local ASP.NET Core URL. A successful response confirms the WP001 runtime foundation is working for that host. Stop manually run host processes after verification. Automated validation should use the test projects instead of launching the Aspire AppHost as a blocking process.

The **AppHost** is the Aspire project in `src/Archon`. Aspire uses an AppHost to describe a local distributed application: the project declares which services, containers, and dependencies should run together for a developer. Archon's AppHost is also the **composition root**. A composition root wires resources together but does not implement business behavior. In practical terms, `src/Archon/Program.cs` may say that Neo4j, `ArchonApi`, and `ArchonMcp` run together, but it must not contain extraction rules, API endpoint handlers, graph persistence code, or MCP tool logic.

The current AppHost composes Neo4j as a container resource named `neo4j`. Neo4j is a graph database; Archon will use it as the system of record for deterministic architecture facts. The AppHost establishes the local runtime seam, and the Neo4j infrastructure adapter now establishes the first code-level connection and schema seams. A **graph schema** is the set of database constraints and indexes that make later graph writes safe and queryable. A **constraint** is a rule enforced by Neo4j, such as “repository stable keys must be unique.” An **index** is a lookup structure that helps later queries find records efficiently by stable key, snapshot scope, kind, status, confidence, knowledge classification, or fingerprint. Because no dedicated `Aspire.Hosting.Neo4j` package is available in NuGet for this implementation, the AppHost uses Aspire's generic container support with the official `neo4j:latest` image. Neo4j starts in secured mode: the AppHost reads the `neo4j-username` and `neo4j-password` Aspire parameters from `src/Archon/appsettings.json` and uses them to set the container's `NEO4J_AUTH` environment value. The password parameter is marked as secret in the Aspire resource graph so the same parameter flow can move to user secrets or another secure provider without changing the composition contract. The AppHost also binds the Neo4j HTTP browser endpoint to `localhost:7474`, binds Bolt to `localhost:7687`, and advertises those host-reachable addresses to Neo4j so Browser can connect back to the same local instance.

Schema initialization is exposed through the application-layer `IArchitectureGraphInitializer` port and implemented by `Neo4jGraphInitializer` in the infrastructure project. This preserves Onion Architecture: application and host code can ask for graph initialization without depending on Neo4j driver types, while the infrastructure adapter owns the Cypher statements. Initialization is **idempotent**, meaning it can run repeatedly against the same database without failing merely because the expected constraints and indexes already exist. That property is important for local development, CI, and future startup flows because contributors should be able to verify or repair schema state without manually deleting the database.

Graph recreation is a separate maintenance workflow exposed through the application-layer `IArchitectureGraphRecreator` port and implemented by `Neo4jGraphRecreator`. **Graph recreation** means deleting Archon-owned graph records and then recreating the required constraints and indexes. It is destructive by design and exists only to support local development and automated integration tests where a clean Archon graph is needed quickly. It is not a schema migration, not a data repair operation, and not a production management endpoint. A migration changes stored data or schema from one version to another while preserving the intended information. Recreation intentionally discards Archon graph records, so it must never be used as a substitute for future migration planning.

The recreation guard is deliberately explicit. Callers must provide the exact confirmation phrase `DELETE ARCHON GRAPH DATA AND RECREATE SCHEMA` through `GraphRecreationRequest`; near misses, different casing, missing words, and trailing spaces are rejected before a write session is opened. This exact phrase is intentionally loud so a future local tool or integration test reads like an intentional destructive action rather than an ordinary Boolean option. Resolving `IArchitectureGraphRecreator` from dependency injection is not enough to erase data, and no API route, health check, snapshot writer, or startup hook invokes it in the current implementation.

When authorized, recreation deletes nodes carrying Archon-owned labels from the closed schema catalog: `ArchonRepository`, `ArchonSolution`, `ArchonSnapshot`, `ArchonNode`, `ArchonRelationship`, `ArchonEvidence`, `ArchonRule`, `ArchonFinding`, `ArchonMetric`, and `ArchonGeneratedSummary`. It uses `DETACH DELETE`, which removes relationships attached to the deleted nodes as part of the same clear operation. The label list comes from `Neo4jSchemaNames`; contributors must not extend this workflow with caller-provided labels or ad hoc dynamic Cypher. After clearing data, recreation runs the same idempotent initializer described above so the database still has the expected constraints and indexes for later persistence tests.

Snapshot persistence is exposed through the application-layer `IArchitectureSnapshotWriter` port and implemented by `Neo4jArchitectureSnapshotWriter`. **Snapshot persistence** means taking an assembled `ExtractedArchitectureSnapshot` from the application layer and writing its graph facts to Neo4j using stable logical identities. The current writer persists repositories, solutions, one snapshot header, architecture nodes, architecture relationship records, evidence nodes, versioned rule catalog entries, finding records, metric records, generated-summary records, snapshot-to-solution relationships, node-to-evidence support relationships, relationship endpoint relationships, relationship-to-evidence support relationships, finding-to-rule relationships, finding-to-primary-node relationships, finding-to-evidence support relationships, metric support relationships, and generated-summary target relationships.

The write order matters because graph records reference one another. Repositories and solutions are written first, then the snapshot header, then architecture nodes, then canonical evidence, then architecture relationship nodes, then global rule catalog entries, then snapshot-scoped findings, metrics, and generated summaries, and finally supporting relationships. The writer initializes schema before the write transaction and then uses a single Neo4j write transaction for the supported snapshot data. A **write transaction** is the unit of work Neo4j commits atomically; if the transaction fails, the writer does not return a successful completed result for partial graph data. This protects later orchestration from mistaking an incomplete snapshot for a valid one.

Stable keys remain the only logical identities used by the writer. Repository, solution, and snapshot records are merged by their global stable keys. Architecture nodes and evidence are merged by snapshot scope plus stable key. Neo4j internal IDs are never surfaced in persistence results, tests, API-facing values, or documentation examples because those IDs are local database implementation details. Fingerprints remain first-class properties so later diff and lookup work can ask whether a graph fact's diff-relevant content changed without reading metadata JSON.

Architecture relationships are persisted through the `ArchonRelationship` label. An **architecture relationship** is the domain fact that one architecture node relates to another: a project references a package, a service calls an endpoint, a component uses a view model, or a repository artifact depends on configuration. The persisted relationship node keeps `stableKey`, `snapshotStableKey`, `edgeKind`, `sourceNodeStableKey`, `targetNodeStableKey`, `isDirect`, `knowledgeKind`, `confidence`, unknown-state fields, `metadataJson`, `primaryEvidenceStableKey`, and `fingerprint` as first-class properties. This means later query, diff, and reporting work can filter by edge kind, compare fingerprints, inspect confidence, or detect unknown data without unpacking metadata JSON.

The relationship-node pattern is now part of the write path rather than only schema preparation. Direct Neo4j relationships are useful for simple graph traversal, but Archon relationships are evidence-backed records with their own stable identity. Neo4j does not let a relationship have outgoing relationships to evidence nodes in the same way a node can. Archon therefore stores each edge as an `ArchonRelationship` node, connects it to the source architecture node with `RELATIONSHIP_SOURCE`, connects it to the target architecture node with `RELATIONSHIP_TARGET`, and connects it to primary evidence with `SUPPORTED_BY_EVIDENCE` when evidence is supplied. A contributor reading the graph should think of this as “source node <- relationship fact -> target node,” with the relationship fact carrying the explainable metadata and evidence.

For example, a project-to-package dependency is stored as an `ArchonRelationship` node whose `edgeKind` might be `REFERENCES` or `USES_PACKAGE`. The relationship node points to the project through `RELATIONSHIP_SOURCE`, points to the package through `RELATIONSHIP_TARGET`, and points to the project-file evidence through `SUPPORTED_BY_EVIDENCE`. Multiple facts can connect the same source and target because the merge identity is the relationship stable key within the snapshot, not the endpoint pair. This matters when one source and target pair has both a generic dependency fact and a more specific package-use fact.

The writer preserves the distinction between normalized graph properties and metadata. **Normalized properties** are fields the platform expects to query, compare, or validate directly, such as `stableKey`, `snapshotStableKey`, `nodeKind`, `evidenceKind`, `knowledgeKind`, `confidence`, `hasUnknownData`, and `fingerprint`. **Metadata JSON** is reserved for deterministic extension data that does not belong in those first-class fields. For example, a project node's `nodeKind` is stored as a Neo4j property because later queries may filter all `Project` nodes, while extractor-specific details that are not part of the shared graph contract remain in `metadataJson`.

Evidence persistence is snapshot-scoped and deduplicated. **Evidence deduplication** means equivalent evidence payloads submitted more than once in the same snapshot collapse to one canonical `ArchonEvidence` node. The canonical identity includes the snapshot stable key and evidence content fields but intentionally excludes the evidence stable key itself, so two contributors can point at the same source evidence without creating duplicate evidence nodes. Node support relationships are remapped to the canonical evidence record. Because snapshot stable key is part of the deduplication identity, equivalent evidence in a different snapshot remains separate, which preserves historical snapshot isolation.

Rule and finding persistence adds the first durable analysis-result layer to the graph. A **rule catalog entry** is a versioned definition identified by `ruleCode` plus `ruleVersion`, such as `ARCHON001` at version `1.0.0`. Rule catalog entries are global `ArchonRule` nodes rather than snapshot-scoped copies. That design matters for history: when a rule changes from version `1.0.0` to `2.0.0`, Archon can keep both versions in the graph and findings from older snapshots can still point to the exact rule version that classified them. A newer rule version must not destructively overwrite the old one merely because it has the same rule code.

A **finding** is a snapshot-scoped concern stored as an `ArchonFinding` node. It preserves the finding stable key, rule code, rule version, severity, status, title, description, knowledge classification, confidence, unknown-state fields, first-seen and latest-seen snapshot keys, suppression reason, suppressed-by actor, deterministic metadata JSON, and fingerprint. **Severity** describes impact, such as `High` or `Info`. **Status** describes lifecycle state, such as `Open`, `Suppressed`, or `Resolved`. **Suppression fields** record why a finding is intentionally hidden or accepted and who or what made that decision; they are first-class properties because future hotlist and reporting features need to distinguish active work from accepted risk without unpacking metadata JSON.

Finding links make rule provenance and evidence explicit. Every persisted finding receives a `CLASSIFIED_BY_RULE` relationship to the matching global rule version. When a primary architecture node is supplied, the finding receives a `PRIMARY_NODE` relationship to that `ArchonNode`. When primary evidence is supplied, the finding receives a `SUPPORTED_BY_EVIDENCE` relationship to canonical `ArchonEvidence`. This shape lets a contributor traverse from a finding to the rule that classified it, the architecture node it concerns, and the evidence explaining why it exists. The writer rejects missing rule, node, or evidence references with explicit persistence errors before opening the write transaction, so the graph does not accumulate dangling finding records.

Metric and generated-summary persistence completes the current snapshot writer shape for computed and narrative outputs. A **metric** is a durable `ArchonMetric` node that stores a computed value for a graph, snapshot, project, architecture node, architecture relationship, or modernization scope. Metrics carry `metricKind`, `scopeKind`, optional node and relationship target stable keys, optional primary evidence, a developer-facing name, numeric value, text value, unit, deterministic metadata JSON, and fingerprint. They are persisted rather than recomputed only at query time because later diff, API, MCP, report, and hotlist packages need stable historical values. For example, if a dependency-count metric changes from one snapshot to the next, a diff package can compare persisted numeric values and fingerprints without rerunning extraction or parsing metadata JSON.

Metric links make the computed value explainable and traversable. When a metric references evidence, it receives `SUPPORTED_BY_EVIDENCE` to canonical `ArchonEvidence`. When it targets an architecture node, it receives `PRIMARY_NODE`. When it targets an architecture relationship, it receives `PRIMARY_RELATIONSHIP` to the `ArchonRelationship` node that represents that edge fact. The writer validates all of those references before opening the transaction. Missing metric node, relationship, or evidence targets return explicit persistence errors rather than creating dangling metric records.

A **generated summary** is a durable `ArchonGeneratedSummary` node containing generated narrative or report-ready content. It stores `summaryKind`, optional target stable key, format, title, content, deterministic metadata JSON, and fingerprint. Summaries are persisted because later markdown export, API, MCP, and reporting features need to retrieve the exact generated content associated with a snapshot or graph fact. Persisting the content also gives future diff behavior something stable to compare when summary text changes across snapshots.

Generated summaries always link to the snapshot that owns them through `SUMMARIZES_SNAPSHOT`. When a summary has a target stable key, the writer links it to the target graph record with `PRIMARY_NODE` for architecture nodes or `PRIMARY_RELATIONSHIP` for relationship-node targets. A summary can also target the snapshot itself by using the snapshot stable key. The writer currently validates summary targets against the snapshot, supplied architecture nodes, and supplied architecture relationships; future slices can expand that target set when additional summary targets become first-class persisted records.

The initialized graph uses stable labels such as `ArchonRepository`, `ArchonSolution`, `ArchonSnapshot`, `ArchonNode`, `ArchonEvidence`, `ArchonRule`, `ArchonFinding`, `ArchonMetric`, and `ArchonGeneratedSummary`. Architecture edges use an additional `ArchonRelationship` label through a **relationship-node pattern**. Neo4j has native relationships, but a relationship itself cannot be linked to evidence nodes as directly as a normal node can. By representing an architecture edge as an `ArchonRelationship` node connected to source and target nodes, Archon can give each edge a stable key, fingerprint, metadata, and evidence links. That keeps relationships as evidence-backed graph facts instead of anonymous database edges.

Constraint and index names use stable `archon_` prefixes, such as `archon_repository_stable_key_unique` and `archon_node_kind_index`. Stable names matter operationally because Neo4j Browser and `SHOW CONSTRAINTS` / `SHOW INDEXES` output can then be compared directly with the source catalog in `Neo4jSchemaStatementCatalog`. If a future test or startup check reports that `archon_rule_code_version_unique` is missing, a contributor can immediately understand that versioned rule catalog identity is not protected in that database.

Neo4j host configuration is represented by the `Neo4j` configuration section. It contains the Bolt-compatible `Uri`, the target `Database`, `Username`, `Password`, `ConnectionTimeout`, `MaxTransactionRetryTime`, and optional `EncryptionMode`. A **Bolt-compatible URI** is the address used by the Neo4j driver protocol, such as `bolt://localhost:7687`; it is separate from the HTTP browser endpoint on port `7474`. The adapter validates these settings before creating the driver and reports only safe setting names and structural problems. Password values and other secret material must come from secure configuration providers in real environments and must not be copied into logs, validation messages, wiki examples, or test assertions.

The final WP003 documentation gate treats the Neo4j persistence foundation as a current repository capability rather than a roadmap promise. The work-package record in `docs/003-Neo4j-Persistence-Foundation/implementation-notes-wp003.md` now serves as the implementation ledger for the graph model, schema names, relationship patterns, write ordering, validation commands, Testcontainers behavior, and out-of-scope boundaries. A **work-package implementation ledger** is the durable repository document that lets a future contributor answer what was actually implemented, why important trade-offs were made, and which commands proved the behavior at the time the work package closed. It complements the wiki: the wiki teaches the current model in contributor-facing prose, while the implementation notes preserve the execution record and validation history.

For contributors extending this area, the important mental model is that WP003 provides persistence of already-assembled graph contracts. It does not decide how extraction finds facts, how rules are loaded from disk, how rules evaluate findings, how summaries are generated, how metrics are computed, or how API and MCP consumers query the graph. Those responsibilities stay assigned to later work packages. This boundary is useful because it keeps the Neo4j adapter small enough to validate with real containers: a test can assemble a deterministic snapshot, recreate the local test graph with the explicit guard phrase, write the snapshot, and query the persisted graph without needing Roslyn workspaces, API endpoints, MCP protocol plumbing, markdown rendering, or UI behavior.

When reviewing or troubleshooting a WP003 graph, start with stable identities and support paths rather than Neo4j internal IDs. A repository, solution, snapshot, architecture node, relationship node, evidence record, finding, metric, or generated summary should be located by its stable key and, where relevant, its snapshot stable key. A rule should be located by rule code plus version. A diff-oriented investigation should compare fingerprints. An explainability investigation should traverse support relationships: from a finding to `CLASSIFIED_BY_RULE`, from facts to `SUPPORTED_BY_EVIDENCE`, from relationship nodes to `RELATIONSHIP_SOURCE` and `RELATIONSHIP_TARGET`, from metrics or summaries to `PRIMARY_NODE` or `PRIMARY_RELATIONSHIP`, and from generated summaries to `SUMMARIZES_SNAPSHOT`. This traversal-first style is the reason the relationship names are stable and documented rather than incidental Cypher details.

Archon uses **Onion Architecture**, which means dependencies should point inward toward the most stable business concepts and away from delivery or infrastructure details. The `Archon.Domain` project is the center. `Archon.Application` may depend on the domain layer, API modules and extractors may depend on application-facing contracts, infrastructure projects adapt external systems, and hosts compose the runtime at the outer edge. A project near the center must not reference a project farther out, because that would make core architecture knowledge depend on a delivery host, database adapter, or other replaceable implementation detail.

Project identity is also normalized at the foundation. A project identity is the repository-root-relative `.csproj` path, such as `src/Archon.Domain/Archon.Domain.csproj`, written with forward slashes. This is deliberately different from an absolute path such as `D:\Dev\Archon\src\Archon.Domain\Archon.Domain.csproj`. Relative normalized identities remain the same across machines, which matters because Archon will later reason about architecture evidence collected from repositories in different developer and CI environments.

The boundary tests in `test/Archon.Tests` enforce these rules without starting any host process. They read project files, classify projects into layers, and inspect `ProjectReference` edges. One important exception is intentional: the `Archon` AppHost references `ArchonApi` and `ArchonMcp` so Aspire can compose them as project resources. That edge is a host composition reference at the outer boundary, not an inward dependency from domain or application code.

For WP003, the boundary tests also verify package-level leakage for Neo4j. The official `Neo4j.Driver` package must remain in `Archon.Infrastructure.Neo4j`; it must not appear in `Archon.Domain` or `Archon.Application`. This distinction is important because an application port such as `IArchitectureSnapshotWriter` should describe persistence capability in Archon terms, not in database-driver terms. If the application layer referenced the Neo4j driver, future tests, query adapters, alternate persistence strategies, and domain model code would become coupled to one replaceable outer implementation. The targeted boundary validation is:

```powershell
dotnet test .\test\Archon.Tests\Archon.Tests.csproj --filter "FullyQualifiedName~Boundary|FullyQualifiedName~Neo4jDriver"
```

This command validates the existing project-reference Onion rules and the Neo4j driver package boundary without starting any host or container.

WP002 has begun adding the architecture graph domain language at the center of the Onion. The first implemented slice is the controlled-value model in `src/Archon.Domain/Graph/ControlledValues`. A **controlled value** is a domain-owned string identity that behaves like a smart enum: code uses named static instances such as `NodeKind.Project` or `EdgeKind.DEPENDS_ON`-style relationship values, while external contracts see only stable strings such as `Project` or `DEPENDS_ON`. This avoids **numeric enum drift**, which is the failure mode where adding, deleting, or reordering ordinary enum members changes serialized numeric meanings by accident. Archon needs stable strings because the same graph vocabulary will later flow through JSON APIs, MCP responses, Neo4j properties, markdown output, tests, and developer documentation.

The controlled values currently define the required WP002 graph vocabulary for node kinds, edge kinds, evidence kinds, rule categories, finding severities, finding statuses, knowledge classifications, metric scopes, and generated-summary categories. These types do not perform extraction and do not persist anything to Neo4j. They are deliberately pure domain contracts: they parse exact external strings, expose deterministic value lists for validation, and serialize through `System.Text.Json` as strings rather than objects or numbers. Later work packages can therefore build graph facts, fingerprints, persistence, API responses, and MCP resources on the same vocabulary without inventing parallel constants.

WP002 also introduces stable-key generation in `src/Archon.Domain/Graph/Identity`. A **stable key** is the durable logical identity for an architecture fact, written as a prefixed string such as `project://src/Customer.Api/Customer.Api.csproj` or `type://Customer.Application.CustomerService`. Stable keys are not database identifiers. A Neo4j internal node ID, a future relational row ID, or a process-local object reference can change when data is recreated, imported, or analyzed on another machine. A stable key is designed to stay the same when the same logical repository artifact, symbol, endpoint, rule, finding, metric, or summary is extracted again.

Path-based stable keys use **repository-relative paths**, meaning paths are written from the repository root rather than from a developer's machine root. For example, `src/Customer.Api/Customer.Api.csproj` is a repository-relative path, while `D:\Dev\Archon\src\Customer.Api\Customer.Api.csproj` is not. The domain helper normalizes separators to forward slashes and rejects absolute or rooted paths so keys remain deterministic across Windows workstations, Linux agents, and CI environments. Extraction slices should call `StableKeyGenerator` rather than assembling strings by hand; this keeps prefixes such as `repository://`, `solution://`, `project://`, `package://`, `endpoint://`, `dbtable://`, `rule://`, `finding://`, `metric://`, and `summary://` consistent across the product.

WP002 now adds deterministic metadata and fingerprint support. **Metadata** is the extension area for extractor-specific details that are useful but not part of the normalized graph contract. Route tokens, HTTP verb sets, options binding details, SQL classification hints, queue transport details, and provider-specific mapping payloads are good metadata candidates. Stable keys, graph kinds, evidence kinds, knowledge classifications, confidence, unknown-state indicators, and primary file or line information are not metadata candidates; those are normalized graph properties that need to remain queryable and comparable as first-class fields. `GraphMetadata` therefore has an explicit empty value, serializes metadata with deterministic property ordering, and rejects known normalized graph property names when they are accidentally placed in metadata.

A **fingerprint** is a deterministic hash of diff-relevant graph content. It answers a different question from a stable key. The stable key asks, “is this the same logical graph fact?” The fingerprint asks, “has the diff-relevant content for this graph fact changed?” Fingerprints are generated from normalized field values and canonical metadata, then represented as `sha256:` strings. They intentionally exclude database IDs, process IDs, absolute machine paths, and other local values unless a caller incorrectly supplies such a value as graph content. For example, two endpoint metadata dictionaries that contain the same route template and HTTP verbs in different insertion orders produce the same canonical metadata string and therefore the same fingerprint input. If the HTTP verbs change from `GET` to `GET` plus `POST`, the canonical metadata changes and so does the fingerprint, because endpoint behavior changed.

WP002 now includes the first **graph fact** contracts in `src/Archon.Domain/Graph/Model`. A graph fact is a domain object that states something Archon knows about an architecture snapshot: a repository was extracted, a solution belongs to that repository, a project node exists, one node depends on another, an evidence record explains a claim, a rule produced a finding, a metric was calculated, or a generated summary was emitted. These models are snapshot-scoped where appropriate, but they are still pure domain contracts. They do not load Roslyn workspaces, run extractors, write Neo4j data, expose API endpoints, or render markdown.

The graph fact model is **evidence-first**. Evidence-first means a fact is designed to carry or link to the explanation that caused the system to believe it. An architecture node can point at the project file, source symbol, configuration file, generated artifact, compiler diagnostic, inference, or manual annotation that supports it. An architecture edge can point at evidence for a reference, call, dependency, navigation, package use, or data-access relationship. A finding can preserve both its rule provenance and the primary evidence that explains why the concern exists. This model helps later contributors answer not only “what did Archon find?” but also “why did Archon believe it?” without needing to infer evidence from incidental logs or persistence details.

Confidence and unknown state are first-class parts of the contract rather than optional notes. **Confidence** is a deterministic decimal from zero through one that lets later code compare certainty in a predictable way. **Knowledge kind** explains whether a fact is a direct fact, an inference, an explicit unknown, or human-confirmed knowledge. **Unknown state** records whether a fact contains unknown data and, when it does, the reason the data is unknown. If a fact uses `KnowledgeKind.Unknown`, or if it declares unknown data, it must carry a non-empty unknown reason. This rule prevents silent nulls from looking like meaningful absence. For example, a future extractor might know that an endpoint calls an external service but be unable to determine the service owner; the graph can retain that uncertainty with an explicit reason instead of dropping the relationship or hiding the limitation in metadata.

Rules, findings, metrics, and generated summaries are also part of the domain language now. A rule is a versioned catalog entry; a finding must preserve both rule code and rule version so historical output stays explainable after rule definitions evolve. A metric is a snapshot output with either a numeric value or a text value, because a metric without a value cannot support reporting or comparison. A generated summary is content associated with a snapshot or target stable key, but markdown export and summarization behavior remain later work. Across these contracts, Neo4j database IDs are intentionally absent. Future persistence can assign store-local IDs, but domain models use stable keys and fingerprints so they remain deterministic before and after persistence.

WP002 now includes application-layer snapshot accumulation in `src/Archon.Application/Extraction`. **Snapshot assembly** is the process of gathering many graph fact contributions into one in-memory `ExtractedArchitectureSnapshot`. That assembled snapshot contains the optional snapshot header, repositories, solutions, nodes, edges, evidence, rules, findings, metrics, generated summaries, warnings, and errors. It is an application contract rather than an extractor, database adapter, host endpoint, or UI feature. Its job is to define the shape future work packages can pass around once extraction has produced facts and before persistence or presentation work begins.

The **extraction accumulator** is `ArchitectureSnapshotAccumulator`. An accumulator is a small stateful builder that accepts contributions from future extractor slices through explicit add and merge methods. A project extractor might add repository, solution, project-node, and project-file evidence facts. A dependency extractor might add edges between project nodes. A rule catalog contributor might add rule definitions, and a rule evaluator might add findings that reference those rule versions. A metrics contributor might add counts, and a summarization contributor might add generated summaries. Those contributors do not need separate top-level persistence models; they can all speak through the same graph fact contracts and let the accumulator produce one assembled snapshot.

Duplicate stable keys have a documented deterministic policy: latest contribution wins for stable-keyed sections. If two contributors add a node with the same stable key, the later node replaces the earlier one in the final snapshot. Rule definitions use an equivalent policy based on rule code plus rule version because they are global catalog entries rather than stable-keyed snapshot facts. This policy gives future extractors and rule contributors a safe way to refine a fact while still emitting one authoritative record for that identity. The final stable-keyed sections are ordered by ordinal stable-key string, and rule definitions are ordered by ordinal rule identity, so output remains predictable even when extractor contribution order varies. Warnings and errors are different: they are diagnostic streams rather than graph facts. The accumulator trims blank diagnostics but preserves repeated non-empty warnings and errors in insertion order because repeated messages can explain repeated extractor observations.

Accumulation is deliberately free of hidden side effects. It does not read source files, load Roslyn workspaces, run analyzers, call Neo4j, map ASP.NET Core endpoints, expose MCP tools, or render markdown. Those behaviors belong to later work packages and outer layers. Keeping accumulation as a pure application contract preserves the Onion Architecture boundary: `Archon.Application` can coordinate domain facts, but it must not depend on infrastructure or host projects.

In the current runtime slice, absence is intentional. `ArchonApi` does not map extraction, query, management, Swagger, Scalar, or UI endpoints. `ArchonMcp` does not map MCP tools, MCP resources, MCP prompts, or architecture-query endpoints. The Neo4j adapter can validate configuration, create a driver, open sessions, report readiness, initialize graph constraints and indexes, run an explicitly guarded local/test graph recreation operation, and persist repositories, solutions, snapshot headers, architecture nodes, architecture relationships, evidence, versioned rule catalog entries, findings, metrics, and generated summaries. Their project homes exist where WP001 needs them, but behavior arrives in later numbered work packages. Contributors should therefore treat missing feature endpoints in WP001 as a correctness condition, not as a defect to fill opportunistically.
