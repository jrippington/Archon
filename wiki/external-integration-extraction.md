# External Integration Extraction

External integration extraction is Archon's static-analysis model for dependencies that leave the analyzed application boundary. An **external integration** is a service, queue, topic, storage target, email channel, payment provider, generated client, or internal service API dependency that application code reaches through source-visible clients, configuration, package references, or runtime wiring. The current WP010 foundation slice establishes the graph vocabulary, stable-key rules, API pipeline registration, and no-live-call safety boundary for this work. Concrete detectors now recognize HTTP and REST client evidence, including `HttpClient`, `IHttpClientFactory`, named clients, typed clients, `HttpRequestMessage`, RestSharp, and narrow REST abstraction calls; RPC or generated-client evidence, including WCF, SOAP/ASMX, generated proxies, `ClientBase<T>`, `ChannelFactory<T>`, and gRPC generated clients; messaging evidence, including Azure Service Bus, NServiceBus, RabbitMQ, MSMQ, and conservative queue-abstraction calls; storage, SMTP/email, and payment-provider evidence, including Azure Blob Storage, Azure File Storage, generic storage abstractions, `SmtpClient`, email sender abstractions, Stripe-style SDK usage, and deterministic payment-wrapper calls; and internal service API correlation that links client-side route evidence to endpoint facts from other analyzed projects when ownership is deterministic.

## Current foundation behavior

The current WP010 slice contributes the integration category inside the consolidated `src/Archon.Extractors` project and a corresponding API pipeline stage named `wp010-external-integrations`. An **extractor category** is a folder and namespace within the consolidated extractor assembly, such as `src/Archon.Extractors/Integrations` with namespace `Archon.Extractors.Integrations`; it is not a standalone project. The consolidated production assembly is built by `src/Archon.Extractors/Archon.Extractors.csproj`, while integration tests live under `test/Archon.Extractors.Tests/Integrations` in `test/Archon.Extractors.Tests/Archon.Extractors.Tests.csproj`. The stage is registered by the existing extraction API module after the WP009 data-access stage. That placement is intentional: project inventory, semantic symbols, configuration facts, dependency-injection facts, runtime facts, and data-access facts can already be in the shared accumulator before the integration slice runs. The API stage can run safely with an empty observation provider, while concrete WP010 detector tests exercise the source-analysis slices directly and project their findings through the same foundation graph path.

The foundation stage uses an observation-provider seam. An **integration observation** is a deterministic source-analysis finding that says source evidence proves a target such as an `ExternalService`, `Queue`, or `Topic`, an owning source node, a relationship kind, evidence location, detector mode, provider, role, confidence context, optional configuration key, and optional unknown reason. The foundation extractor turns those observations into ordinary graph facts: architecture nodes, architecture edges, evidence records, warnings, and errors. It does not scan arbitrary repositories by itself, invent service names, persist directly to Neo4j, expose query endpoints, add MCP behavior, or create user-interface surfaces.

This separation lets future detectors remain small. For example, an HTTP detector can focus on recognizing `HttpClient` or `IHttpClientFactory` evidence and then hand a normalized observation to the foundation extractor. A messaging detector can focus on Azure Service Bus, RabbitMQ, NServiceBus, or MSMQ source shapes and hand queue or topic observations to the same graph-projection path. The projection code remains the single place that decides how external integration observations become stable graph facts.

## HTTP and REST detector behavior

The HTTP and REST detector is a Roslyn-backed source detector inside `src/Archon.Extractors/Integrations`. It reads semantic documents and syntax trees; it does not construct `HttpClient`, call `IHttpClientFactory`, execute RestSharp requests, resolve DNS, read environment variables, or contact the target service. The detector looks for deterministic source evidence and then emits ordinary integration observations that the foundation projection path turns into `ExternalService`, `CALLS_EXTERNAL_SERVICE`, `USES_CONFIG`, evidence, warnings, confidence, and unknown-state graph facts.

A **direct HTTP client** is source code that constructs or uses `System.Net.Http.HttpClient` directly, including constructor-injected clients. The detector recognizes common outbound operation methods such as `GetAsync`, `PostAsync`, `PutAsync`, `PatchAsync`, `DeleteAsync`, `SendAsync`, `GetFromJsonAsync`, and `PostAsJsonAsync` when Roslyn can bind the call to the expected HTTP client or JSON extension owner. A literal absolute URL such as `https://billing.example.test/v1/invoices` identifies an external-service target of `https://billing.example.test` and a relative-path hint of `/v1/invoices`. A literal relative path such as `/v1/accounts` is useful evidence but does not identify the service by itself, so it becomes an explicit unknown unless nearby deterministic configuration or client-registration evidence supplies a target.

An **HTTP request message** is a `HttpRequestMessage` object that carries method and URI details before a later `SendAsync` call. The detector correlates local request-message variables with `SendAsync` when the method and path are visible in source. For example, a request constructed with `HttpMethod.Post` and `"/v1/payments"` records the `POST` operation and the relative path even if the final service target is not statically known. If the request message, path, or target is computed from runtime values, the extractor records an unknown reason rather than inventing a service name.

A **named client** is an `HttpClient` created through `IHttpClientFactory.CreateClient("Name")` or registered through `AddHttpClient("Name", ...)`. A **typed client** is a class registered with `AddHttpClient<TClient>(...)` and usually receives an `HttpClient` through its constructor. The detector records these deterministic names and types as service identities or metadata when a literal base address is not available. When a registration or constructor uses a configuration key such as `Integrations:Billing:BaseUrl`, the detector creates a `USES_CONFIG` relationship to `config://Integrations:Billing:BaseUrl`; it stores the key identity, not the runtime value that the application would read.

RestSharp evidence is handled in the same static way. The detector recognizes `RestClient`, `RestRequest`, resource strings, method selections such as `Method.Get` and `Method.Post`, and `Execute` calls where the symbols or syntax are deterministic. RestSharp base URLs can come from literal constructor arguments or configuration keys. Request resources that are computed from runtime values become explicit unknowns with warnings. Authentication evidence is deliberately reduced to safe mechanism hints such as bearer token, API key, or basic authentication; raw header values, tokens, passwords, and connection-like secret fragments are redacted before they can appear in evidence previews, metadata, diagnostics, or test output.

The detector also includes a conservative REST abstraction rule for project-specific wrapper interfaces or types that look like deterministic REST clients, such as `IApiClient.GetAsync("/health")`. This rule is intentionally narrow. It can record that a wrapper-style REST dependency exists and preserve the wrapper type and resource hint, but it does not guess the underlying service if the source does not prove one. Contributors adding broader wrapper recognition should keep this standard: capture package, namespace, type, invocation, and configuration evidence only when they are deterministic, and prefer an explicit unknown over a plausible but unsupported service name.

## RPC and generated-client detector behavior

The RPC and generated-client detector is the second concrete WP010 detector. It recognizes service-client technologies whose source code is often produced by Visual Studio, connected-service tooling, protocol-buffer generation, or legacy web-reference tooling. A **generated proxy** is a client type created from a service description instead of handwritten application code. In WCF and SOAP systems this can come from a service reference, a connected service, an ASMX web reference, or a generated `Reference.cs` file. In gRPC systems the generated client usually comes from `.proto` compilation and is constructed with a `GrpcChannel`. Archon treats all of these artifacts as static evidence. It reads source files, local generated artifacts, and configuration files; it does not instantiate the generated client, open a WCF channel, create a gRPC transport, resolve endpoint names, or contact the service.

WCF extraction combines several source shapes. A **service contract** is the interface that describes service operations, such as `IOrderService.SubmitOrderAsync`. A WCF generated client often derives from `ClientBase<TContract>`, and handwritten code can also use `ChannelFactory<TContract>` to create a channel for the same contract. The detector records source-visible operation calls, generated client type names, endpoint configuration names, binding names, and transport hints when they are deterministic. A **binding** is WCF's client-side transport and protocol configuration, such as `basicHttpBinding`, `wsHttpBinding`, `netTcpBinding`, or a custom binding. If a `.config` endpoint provides a literal address and binding, the detector attaches those details to the external-service fact and links the integration to the configuration-key stable identity rather than storing any runtime value.

SOAP and ASMX extraction follows the same evidence-first rule. An ASMX proxy that exposes a literal `Url` or appears in a service-reference artifact can produce an `ExternalService` node and a `CALLS_EXTERNAL_SERVICE` relationship from the calling method. A generated proxy with no deterministic endpoint is still useful architecture evidence: Archon emits an explicit unknown external service with a warning explaining that the generated proxy endpoint could not be resolved. This avoids the misleading alternatives of silently dropping a legacy dependency or inventing a plausible service name.

gRPC extraction looks for generated client types, `GrpcChannel.ForAddress(...)`, typed `AddGrpcClient<TClient>(...)` registrations, configuration-key references near generated client setup, and generated client method calls. A **gRPC channel** is the client transport object that carries calls for generated clients to an endpoint address. Literal channel addresses identify known external services. Runtime-computed channel addresses become explicit unknowns, and configuration-key references are preserved as `USES_CONFIG` relationships or metadata without reading the configured value. This means a fixture that uses `Integrations:Grpc:Address` can prove that a gRPC dependency is configuration-backed while still keeping the actual endpoint secret outside the graph unless source evidence already exposes it safely.

Generated artifacts can be large and repetitive, so the detector uses bounded traversal. It orders files deterministically, skips oversized generated artifacts with a warning instead of recursively walking unbounded code, deduplicates repeated package, artifact, configuration, generated-client, and call-site evidence through stable keys, and redacts token-like or connection-like values before snippets, metadata, diagnostics, or warnings leave the extractor. Contributors extending this slice should preserve that shape: artifact evidence is explanatory support, semantic source calls identify ownership, unknowns are explicit, and live service behavior is always outside the extractor boundary.

## Messaging detector behavior

The messaging detector recognizes broker and message-bus dependencies from source-visible producers, consumers, handlers, endpoint configuration, and wrapper calls. A **queue** is a named point-to-point destination where one or more producers send messages and one or more consumers receive or process them. A **topic** is a publish-subscribe destination where published messages can be distributed to subscriptions. A **subscription** is the named view of a topic that a consumer processes. These concepts are modeled as `Queue` and `Topic` graph nodes because they are external integration targets even when they are reached through an abstraction rather than a concrete SDK.

Azure Service Bus extraction looks for deterministic `ServiceBusClient` factory methods, including sender, receiver, and processor creation. A **sender** or **producer** role means source evidence writes to a queue or topic, so Archon emits a `CALLS_EXTERNAL_SERVICE` relationship. A **receiver**, **processor**, or **handler** role means source evidence consumes or handles messages, so Archon emits a `HANDLES` relationship. When a local `appsettings*.json` artifact shows that Service Bus configuration exists, the detector preserves the configuration key identity, such as `Messaging:ServiceBus:ConnectionString`, and links the target through `USES_CONFIG` without storing the connection-string value. Runtime-computed queue names become explicit unknown queues with warnings rather than guessed broker destinations.

NServiceBus extraction treats endpoint configuration and message type declarations as architecture evidence. An **endpoint** is the logical NServiceBus process identity used for routing messages. A **message handler** is a type implementing `IHandleMessages<TMessage>` and a **saga** is a long-running workflow type deriving from `Saga<TData>` that also handles messages. The detector records endpoint names, send operations, publish operations, subscribe operations, handler and saga relationships, transport-provider hints such as Azure Service Bus, routing-target hints, error queue names, and recoverability configuration where they are deterministic. Computed endpoint names and unresolved message identities are recorded as explicit unknowns with diagnostic warnings.

RabbitMQ extraction records queues, exchanges, routing keys, publishers, and consumers. An **exchange** is the RabbitMQ routing entity that receives published messages before they are routed to queues. A **routing key** is source-visible text used by the broker to decide how a published message should flow through an exchange. The detector records `QueueDeclare`, `ExchangeDeclare`, `BasicPublish`, and `BasicConsume` evidence when queue names, exchange names, and routing keys are literal or otherwise compiler-constant. It does not open connections, create channels, inspect broker topology, or ask RabbitMQ which queues exist.

MSMQ extraction covers local `MessageQueue` construction plus `Send` and `Receive` calls where the queue path is deterministic. Queue paths such as `.\private$\orders` are recorded as queue names scoped by the `MSMQ` provider. Generic abstraction extraction is intentionally conservative: wrapper methods such as `PublishAsync`, `SendAsync`, or `EnqueueAsync` are accepted only when the receiver type clearly looks like a queue abstraction and the first argument carries a deterministic queue name. That rule lets Archon preserve wrapper-style messaging dependencies while avoiding broad false positives from unrelated application methods named `PublishAsync`.

Messaging metadata can include the provider, messaging role, operation, message type, endpoint name, subscription name, routing target, routing key, exchange, transport provider, and recoverability hint. Secret-like broker connection strings and password-bearing snippets are redacted before they can enter evidence previews, metadata, warnings, or tests. As with HTTP and RPC extraction, repeated call-site evidence is deduplicated through stable keys, and richer role details may appear on relationships even when a shared queue or topic node was first created by another observation.

## Storage, SMTP/email, and payment detector behavior

The storage, SMTP/email, and payment detector recognizes external-service dependencies that frequently sit near secret-bearing configuration. A **storage target** is a location outside the application boundary where files or objects are read, written, or deleted. The detector currently models deterministic storage targets as `ExternalService` nodes because the graph vocabulary has not introduced first-class storage node kinds. Azure Blob Storage evidence comes from source-visible `BlobServiceClient`, `GetBlobContainerClient`, `GetBlobClient`, upload, download, and delete calls. A **storage account** is the Azure Storage account that owns containers and shares; when source does not expose the account name safely, Archon preserves configuration-key identity and uses conservative display hints rather than reading or validating the connection string. A **container** is an Azure Blob Storage namespace under an account, and a **blob path** is the object path inside that container. Azure File Storage evidence comes from `ShareClient`, directory, file, and download-style calls. A **share** is the Azure Files namespace under a storage account, and a file path is the deterministic directory/file hint seen in source. Generic storage abstraction support is intentionally narrow: wrapper calls are accepted only when receiver naming and literal bucket or path arguments make the storage intent deterministic.

Storage operation metadata is deliberately coarse. A read hint means source calls a download, read, or get-style API. A write hint means source calls upload, write, or save-style APIs. A delete hint means source calls delete or remove-style APIs. These hints explain architecture behavior without claiming runtime data flow. Runtime-computed containers, shares, buckets, blob names, or file names become explicit unknown external services with warnings, because static analysis cannot safely evaluate user input, environment variables, or string construction. Configuration dependencies such as `Storage:Blob:ConnectionString` are recorded through `USES_CONFIG` relationships to configuration-key stable identities, but connection-string values, account keys, shared-access signatures, and similar secrets are redacted before metadata, evidence, diagnostics, or test output can contain them.

SMTP and email extraction covers `SmtpClient`, mail-message construction context, send operations, and common email sender abstractions. An **SMTP host** is the mail server endpoint used by SMTP clients; Archon can record a literal host or a configuration-key dependency such as `Email:Smtp:Host`, but it does not open a network connection or send a message. Sender addresses, recipients, message bodies, templates, and credentials are treated as sensitive payload or operational metadata rather than topology identity. When source proves that an email sender abstraction exists, Archon emits an `ExternalService` fact for the abstraction and records safe provider, client-type, operation, and authentication-hint metadata. Runtime-computed hosts, recipients, or template names are represented through explicit unknowns or limited metadata rather than guessed endpoints.

Payment-provider extraction is the most aggressively redacted part of this slice. A **payment provider** is an external system that processes payment operations, such as Stripe or a project-specific gateway. The detector recognizes known SDK-style source evidence such as Stripe `ChargeService` usage and deterministic payment wrapper calls such as a gateway method whose endpoint is supplied by a configuration key. It records provider hints, endpoint-key hints, authentication mechanism hints, usage sites, and operation hints such as charge. It never stores card data, payment tokens, API secrets, customer payment identifiers, or secret-bearing request payload values. A **redaction** is the replacement of sensitive source or configuration text with a safe marker before the value can be persisted, hashed for display, logged, asserted in tests, or copied into warnings. Ambiguous provider names, dynamically loaded payment integrations, runtime-computed endpoint keys, and unresolved payment endpoints become explicit unknowns rather than inferred provider facts.

## Internal service API correlation behavior

Internal service API correlation is the part of WP010 that treats calls between projects inside the same analyzed repository as service dependencies without pretending they are live infrastructure. An **internal service API** is an HTTP endpoint exposed by one analyzed project and called by another analyzed project. The correlation detector consumes prior endpoint facts from the runtime slice, including endpoint stable keys, project stable keys, controller stable keys, method stable keys, HTTP methods, route templates, optional base URL configuration keys, and optional base URLs. It then inspects client-side source calls such as `HttpClient.GetAsync("https://orders.internal.test/api/orders/42")` and links the call only when both sides agree through deterministic route and ownership evidence.

This conservative requirement is important. Project names, namespaces, typed-client names, or package names may suggest that a client belongs to another service, but suggestion alone is not ownership proof. A client call can be correlated when a prior endpoint fact proves `GET /api/orders/{id}` for the `Orders.Api` project and the client source proves either the same route plus the same service base URL or a matching base URL configuration key such as `Services:Orders:BaseUrl`. Route templates match concrete paths only segment by segment: a parameter segment such as `{id}` can match one concrete segment, but unrelated paths, missing segments, or extra path segments do not match. If several endpoints match the same route and no base URL or configuration key disambiguates ownership, the extractor emits an explicit unknown rather than choosing one by ordering or by name.

Known internal service calls still use `ExternalService` nodes and `CALLS_EXTERNAL_SERVICE` relationships so downstream consumers can reason about all outbound dependencies through the same WP010 vocabulary. The metadata marks the dependency with `integrationCategory=InternalService`, `isInternalService=true`, the HTTP operation, the relative path, and stable keys for the endpoint, controller, method, and owning project when those keys are known. This preserves a direct path from the client call to the provider-side graph facts without introducing a new persistence model or a direct Neo4j write path from extractor code. Unknown internal calls keep the source evidence, warning, unknown state, and unknown reason so contributors can see that a call exists but ownership or route resolution was not deterministic.

For example, suppose `Orders.Api` exposes `GET /api/orders/{id}` through `OrdersController.GetById`, and `Sample.Client` calls `GetAsync("https://orders.internal.test/api/orders/42")`. If the endpoint fact records the same base URL or the same `Services:Orders:BaseUrl` configuration key, Archon can link the client method to the internal service target and carry endpoint, controller, method, and project stable keys in metadata. If the client instead calls `GetAsync(dynamicPath)` or only calls `/api/customers/17` while no matching endpoint fact exists, the detector records an unknown internal service target. This gives maintainers a truthful graph: deterministic internal API dependencies are visible, and unresolved service ownership remains visible as uncertainty instead of becoming a false positive.

## Graph facts and relationship vocabulary

External integration targets use graph vocabulary that already exists in the domain model. Known outbound service dependencies become `ExternalService` nodes. Messaging targets become `Queue` or `Topic` nodes. Primary relationships use existing controlled relationship kinds such as `CALLS_EXTERNAL_SERVICE`, `HANDLES`, `USES_CONFIG`, and `DEPENDS_ON`. The foundation slice does not introduce a parallel integration-specific persistence model. It contributes to the same `ExtractedArchitectureSnapshot` sections used by repository, Roslyn, configuration, runtime, data-access, and HTTP/REST integration extraction.

Evidence remains first class. Each projected observation creates a source-code evidence record with a repository-relative path, optional one-based line range, optional symbol and containing-symbol names, a redacted snippet preview where supplied, a snippet hash, deterministic metadata, confidence, and unknown state. The same evidence can support the target node and the relationship that connects the source node to that target. If a configuration key is provided, the target can also receive a `USES_CONFIG` relationship to the existing configuration-key stable key. HTTP and REST metadata can include safe operation, relative path, named-client, typed-client, provider, and authentication-mechanism hints. RPC and generated-client metadata can include operation, endpoint name, binding type, service contract, generated client type, transport, provider, and configuration-key hints. Messaging metadata can include operation, message type, endpoint name, subscription name, routing target, routing key, exchange, transport provider, recoverability, provider, and role hints. Storage, email, and payment metadata can include provider, client type, read/write/delete or charge operation hints, storage container/share/path hints, SMTP host key, payment provider, endpoint key, authentication hint, and configuration-key identity. Internal service metadata can include `isInternalService`, the client route, base URL configuration key, endpoint stable key, controller stable key, method stable key, project stable key, and internal service name when deterministic correlation succeeds. Normalized graph identity still lives in stable keys, node kinds, edge kinds, confidence, unknown state, and evidence links.

Unknowns are explicit rather than guessed. If source evidence proves that an integration exists but not the deterministic target name, the extractor emits an unknown target with `KnowledgeKind.Unknown`, `UnknownState`, a medium confidence value, a warning, and an unknown reason. This is different from omitting the fact. Omission would hide an architecture dependency; an explicit unknown records that the dependency exists but cannot be named from static evidence yet.

## Stable-key rules

Stable keys for integration facts must be deterministic and independent of developer-machine paths, temporary paths, enumeration order, database IDs, live network state, broker state, storage state, or external-service availability. Known external services use logical service identity through keys such as `externalservice://Billing API`. Known queues and topics include the provider or transport in the logical name, such as `queue://AzureServiceBus:orders` or `topic://AzureServiceBus:invoices`, so same-named targets on different transports do not collide.

Unknown external-service keys are evidence-location scoped. They use the repository-relative evidence path, a source line, and a hash of the detector discriminator. This produces placeholder-safe keys such as `externalservice://unknown/src/App/Client.cs/42/<hash>` without leaking absolute roots or runtime endpoint values. Relationship keys are semantic and endpoint-based: the relationship kind, source stable key, and target stable key define identity. Evidence keys include the normalized evidence location and detector mode so repeated extraction of the same source produces the same output.

These rules matter because Archon snapshots are compared, persisted, and queried after the original extraction process has finished. A stable key must keep meaning after the graph has been recreated, after a different developer analyzes the same repository path on another drive, or after a CI agent runs the same fixture in a temporary working directory.

## Safety boundary

WP010 is static analysis only. The foundation stage and concrete detectors must not execute analyzed application code, start the Aspire AppHost, run target services, call DNS, open HTTP connections, validate credentials, connect to queue brokers, enumerate storage accounts, browse containers or shares, send email, call payment providers, or inspect live infrastructure. They must treat source files, project files, configuration files, generated artifacts, and Roslyn semantic models as evidence and stop there.

Diagnostics follow the same shared snapshot contract as other extraction slices. Provider warnings and errors are copied into the accumulator so API run status and persisted snapshots can explain degraded integration collection. A diagnostic must be credential-safe and should not contain raw connection strings, secret values, stack frames, environment variables, or full request metadata values. Secret-like source snippets are redacted before they can become evidence previews.

## Contributor workflow

When adding a concrete integration detector, keep detector responsibility separate from projection responsibility. Add production code to the appropriate folder under `src/Archon.Extractors/Integrations`, add matching tests under `test/Archon.Extractors.Tests/Integrations`, and preserve the `Archon.Extractors.Integrations` and `Archon.Extractors.Tests.Integrations` namespace conventions. Do not create new `Archon.Extractors.Integrations` or `Archon.Extractors.Integrations.Tests` projects; the old category project directories were retired after consolidation. A detector should collect deterministic observations from one source family, such as HTTP client source, RestSharp source, WCF generated artifacts, gRPC generated clients, queue producer/consumer calls, storage SDK calls, SMTP senders, or payment SDK usage. It should then provide observations through the WP010 provider seam so the foundation extractor handles graph-node, edge, evidence, confidence, warning, and unknown projection consistently.

Fixture tests should prove both positive and degraded behavior. A literal endpoint fixture should assert an `ExternalService` node and a `CALLS_EXTERNAL_SERVICE` edge. A computed endpoint fixture should assert an explicit unknown service fact and warning. HTTP and REST fixtures should cover direct `HttpClient`, injected `HttpClient`, `IHttpClientFactory.CreateClient`, named and typed `AddHttpClient` registrations, `HttpRequestMessage`, RestSharp client/request/execute flows, deterministic wrapper calls, duplicate call-site deduplication, configuration-backed base addresses, redacted authentication snippets, and dynamic path unknowns. RPC and generated-client fixtures should cover WCF `ClientBase<T>` clients, `ChannelFactory<T>` usage, service-reference or connected-service artifacts, ASMX proxies, endpoint configuration, binding metadata, gRPC generated clients, `GrpcChannel` creation, typed `AddGrpcClient<TClient>` registration, runtime-computed channel unknowns, duplicate generated-client call-site deduplication, and large generated artifact safeguards. Messaging fixtures should cover Azure Service Bus sender, receiver, processor, topic subscription, and handler evidence; NServiceBus endpoint, handler, saga, send, publish, subscribe, routing, transport, error queue, and recoverability evidence; RabbitMQ publisher, consumer, exchange, queue, and routing-key evidence; MSMQ sender and receiver evidence; generic queue-abstraction calls; dynamic names; unknowns; redaction; and deduplication. Storage, email, and payment fixtures should cover Azure Blob and Azure File target hints, read/write/delete operations, generic storage abstractions, `SmtpClient`, mail-message send sites, email sender abstractions, provider configuration keys, payment SDK calls, deterministic payment wrappers, dynamic target unknowns, deduplication, and aggressive redaction across evidence, metadata, diagnostics, and test output. Internal service fixtures should cover a positive route-and-endpoint match, a no-endpoint negative case, computed route unknowns, duplicate client calls that collapse by stable key, redacted client setup snippets, cancellation, and feasible VB.NET parity limits when the current detector does not support a language-specific client-call syntax. A literal queue or topic fixture should assert the `Queue` or `Topic` stable key, provider metadata, evidence path, and relationship direction. A configuration-backed fixture should assert the `USES_CONFIG` edge to a configuration-key stable key or the preserved configuration-key metadata when the fixture intentionally isolates the integration extractor from first-class configuration nodes. Every fixture should avoid real credentials, real customer payment identifiers, real SMTP settings, real storage connection strings, and live services; it should use temporary repository roots or in-memory source documents and assert repository-relative paths rather than absolute paths.
