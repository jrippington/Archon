# WP003 Implementation Notes - Neo4j Persistence Foundation

## Work Item 1 - Neo4j Configuration, Driver Lifecycle, and Health Probe Slice

Work Item 1 establishes the first runnable Neo4j persistence-foundation capability. The implementation does not create graph schema, write architecture snapshots, expose persistence APIs, start extraction orchestration, or add destructive graph recreation. Its purpose is narrower and foundational: Archon can now bind Neo4j connection settings, validate them before use, create the official Neo4j .NET driver through dependency injection, open database-targeted sessions through a small infrastructure abstraction, and run a readiness probe against a real Neo4j database.

The strongly typed configuration contract is `Neo4jOptions` in `src/Archon.Infrastructure.Neo4j/Configuration`. It binds from the `Neo4j` configuration section and includes the Bolt-compatible URI, database name, username, password, connection acquisition timeout, maximum transaction retry time, and optional encryption mode. `Neo4jOptionsValidator` validates the required fields before driver creation or health probing and deliberately reports only setting names and structural problems. It never echoes the configured password, because options validation failures can be surfaced through startup exceptions, health details, logs, or developer dashboards.

Driver lifecycle is centralized in the `Driver` folder. `Neo4jDriverFactory` translates validated Archon options into the official `Neo4j.Driver` configuration and logs only credential-safe details such as URI scheme, host, and database name. `INeo4jSessionProvider` and `Neo4jSessionProvider` hide database selection and singleton driver ownership from higher-level infrastructure components. The dependency-injection container owns the singleton `IDriver`; callers only open short-lived `IAsyncSession` instances and dispose those sessions after each operation.

The `AddArchonNeo4j` extension in `src/Archon.Infrastructure.Neo4j/DependencyInjection` is the public infrastructure-composition entry point for this slice. It binds and validates options, registers the factory, singleton driver, session provider, concrete health check, and the ASP.NET Core health-check registration named `neo4j`. Host projects can call this extension from their composition root when they are ready to include Neo4j readiness. The implementation does not require automated tests to start the Aspire AppHost; tests use in-memory configuration and Testcontainers directly.

The health probe is implemented by `Neo4jHealthCheck`. It opens a read session and executes `RETURN 1 AS healthy`, which exercises configuration binding, authentication, network connectivity, database selection, and Cypher execution without requiring schema or data. Failures are categorized as configuration, authentication, network, or query failures where the driver API exposes enough information to do so. Health-result data contains only a coarse `failureKind` value and never includes credentials.

Test coverage was added under `test/Archon.Infrastructure.Neo4j.Tests`. Unit tests cover validation success, validation failure messages that avoid secret leakage, unsupported encryption values, in-memory dependency-injection registration, health-check registration, and singleton driver disposal through a factory seam. The integration test uses `Testcontainers.Neo4j` to start a real Neo4j database, registers the same infrastructure services used by host composition, and verifies the health check returns `Healthy`. This confirms the slice works end-to-end without launching the Aspire AppHost as a blocking validation process.

## Work Item 2 - Graph Schema Initialization Slice

Work Item 2 makes a clean Neo4j database become an Archon graph store before any snapshot data is written. The slice adds an application-layer initialization port, a stable schema name catalog, an explicit ordered statement catalog, and a Neo4j initializer that runs the catalog idempotently. It still does not persist repositories, solutions, snapshots, nodes, evidence, findings, metrics, rules, generated summaries, or destructive graph recreation data.

The application contracts live in `src/Archon.Application/Graph/Persistence`. `IArchitectureGraphInitializer` exposes one asynchronous operation, `InitializeAsync`, with cancellation support and no Neo4j driver types. `GraphInitializationResult`, `PersistenceError`, `PersistenceWarning`, and `PersistenceStage` report safe result details that hosts and later orchestration code can understand without depending on infrastructure. This preserves the Onion Architecture boundary: the application layer owns the port and result vocabulary, while `Archon.Infrastructure.Neo4j` owns the database-specific implementation.

The schema names live in `Neo4jSchemaNames`. Stable labels include `ArchonRepository`, `ArchonSolution`, `ArchonSnapshot`, `ArchonNode`, `ArchonRelationship`, `ArchonEvidence`, `ArchonRule`, `ArchonFinding`, `ArchonMetric`, and `ArchonGeneratedSummary`. Work Item 2 chooses the relationship-node pattern for architecture relationships. In this pattern, an architecture edge is represented as an `ArchonRelationship` node rather than only as a native Neo4j relationship. That decision allows later persistence slices to apply uniqueness constraints, indexes, stable keys, fingerprints, metadata, and evidence links to relationships in the same way they apply them to other graph facts.

`Neo4jSchemaStatementCatalog` contains explicit `CREATE CONSTRAINT ... IF NOT EXISTS` and `CREATE INDEX ... IF NOT EXISTS` statements. The constraints enforce repository, solution, and snapshot stable-key uniqueness; snapshot-scoped uniqueness for architecture nodes, relationship nodes, evidence, findings, metrics, and generated summaries; and rule uniqueness by rule code plus version. The indexes support lookup by repository association, snapshot scope, node and edge kind, evidence kind, rule code and category, finding severity and status, knowledge kind, confidence, metric kind and scope kind, generated-summary kind, and fingerprints. Constraint and index names use stable `archon_` prefixes so Neo4j Browser, logs, and metadata queries can be read operationally.

`Neo4jGraphInitializer` implements the application port in `src/Archon.Infrastructure.Neo4j/Schema`. It opens a write session through `INeo4jSessionProvider`, executes statements one at a time in catalog order, logs the schema object kind and name, supports cancellation between statements, and returns completed-statement counts in `GraphInitializationResult`. Errors are mapped to credential-safe application diagnostics. The initializer is registered through `AddArchonNeo4j` as `IArchitectureGraphInitializer`, alongside the schema statement catalog.

## Work Item 3 - Guarded Graph Recreation Slice

Work Item 3 adds the first explicitly destructive Neo4j maintenance capability for Archon. The capability is intentionally narrow: it clears Archon-owned graph records in a local development or automated integration-test database, then re-runs schema initialization so the database is immediately ready for later persistence slices. It does not add a production API endpoint, does not run during ordinary host startup, does not run from the health check, and must not be confused with a migration or data-repair mechanism.

The application contracts live in `src/Archon.Application/Graph/Persistence`. `IArchitectureGraphRecreator` exposes the destructive operation without Neo4j driver types. `GraphRecreationRequest` carries a deliberately loud exact confirmation phrase, `DELETE ARCHON GRAPH DATA AND RECREATE SCHEMA`, and exposes `CreateAuthorized` for tests and local tooling that need to make the destructive intent readable. `GraphRecreationResult` records whether the request was authorized, whether recreation succeeded, how many Archon-owned nodes were deleted, how many schema statements ran afterward, and any safe warnings or errors. Unauthorized requests return the stable error code `GraphRecreationNotAuthorized` before infrastructure opens a write session.

`Neo4jGraphRecreator` implements the application port in `src/Archon.Infrastructure.Neo4j/Recreation`. The guard check happens before any database mutation. When the request is authorized, the implementation deletes only nodes carrying Archon-owned labels from the closed `Neo4jSchemaNames` catalog: repositories, solutions, snapshots, architecture nodes, relationship nodes, evidence, rules, findings, metrics, and generated summaries. The clear statement uses parameterized Cypher for the label list and `DETACH DELETE` so relationships attached to those Archon nodes are removed with the records. No caller-provided label or relationship type is interpolated into Cypher. After clearing data, the recreator delegates to `IArchitectureGraphInitializer`, which keeps the reset path aligned with the same idempotent constraints and indexes used by Work Item 2.

The recreator is registered by `AddArchonNeo4j` as `IArchitectureGraphRecreator`, but registration alone does not make recreation reachable from production behavior. No host endpoint, API route, snapshot writer, health check, or automatic startup hook invokes it. Future local tooling or tests must still supply the exact confirmation phrase through `GraphRecreationRequest` before any data is removed.

## Work Item 4 - Minimal Snapshot Persistence Slice

Work Item 4 adds the first end-to-end snapshot write path into Neo4j. The slice is intentionally minimal but complete for its scope: it persists repository records, solution records, one snapshot header, architecture nodes, canonical evidence records, snapshot-to-solution relationships, and node-to-evidence support relationships. It does not persist architecture relationship records, rules, findings, metrics, generated summaries, query APIs, MCP resources, markdown export, rule loading, or API-triggered extraction orchestration.

The application contracts live in `src/Archon.Application/Graph/Persistence`. `IArchitectureSnapshotWriter` accepts the application-owned `ExtractedArchitectureSnapshot` contract and returns `SnapshotPersistenceResult`. `SnapshotPersistenceCounts` reports aggregate counts for repositories, solutions, snapshots, architecture nodes, canonical evidence nodes, snapshot-solution relationships, and node-evidence relationships. The result contract reports success, the snapshot stable key when known, warnings, and safe errors without exposing Neo4j driver types, transaction summaries, internal IDs, or database exceptions.

The Neo4j implementation lives in `src/Archon.Infrastructure.Neo4j/Persistence`. `Neo4jSnapshotPersistenceMapper` maps WP002 repository, solution, snapshot header, architecture node, and evidence contracts into parameter dictionaries. Query-critical fields such as stable keys, snapshot scope, node kind, evidence kind, knowledge kind, confidence, unknown-state values, and fingerprints remain first-class Neo4j properties; only extension data is stored as deterministic `metadataJson`. Snapshot warnings and errors are stored as deterministic JSON arrays. `Neo4jPersistenceStageLogger` centralizes credential-safe stage logging, and `Neo4jArchitectureSnapshotWriter` performs validation, schema initialization, evidence deduplication, and transactional writes.

The writer validates the minimal snapshot before opening a write transaction. A snapshot must include a header, the header repository must be present in the repository section, every solution must reference a supplied repository, minimal node and evidence records must share the snapshot header stable key, and architecture nodes may not reference missing primary evidence. Missing references return explicit `PersistenceError` codes such as `MissingNodeEvidenceReference` rather than silently dropping graph facts or support relationships.

Persistence runs in a single Neo4j write transaction after schema initialization succeeds. The ordering is repository, solution, snapshot header, architecture nodes, canonical evidence, snapshot-to-solution relationships, and node-to-evidence relationships. Records are merged by stable-key identity, never by Neo4j internal IDs. Repository, solution, and snapshot records use global stable keys, while architecture nodes and evidence records use snapshot-scoped composite identity. The writer uses parameterized Cypher and stable relationship names from the schema catalog: `INCLUDES_SOLUTION` and `SUPPORTED_BY_EVIDENCE`.

Evidence deduplication is snapshot-scoped. The mapper builds a canonical evidence identity from snapshot stable key and evidence payload fields, excluding the evidence stable key itself so equivalent evidence records inside one snapshot collapse to the first canonical evidence node. Node support relationships are remapped to that canonical evidence stable key. Because the snapshot stable key is part of the deduplication identity, identical evidence payloads in different snapshots remain separate records.

## Work Item 5 - Architecture Relationship Persistence Slice

Work Item 5 extends the Neo4j snapshot writer from node-shaped persistence into traversal-ready relationship persistence. The implementation keeps the relationship-node pattern that was established in the schema slice. An architecture edge from the WP002 contract is persisted as an `ArchonRelationship` node rather than as an anonymous native Neo4j relationship. This choice is necessary because architecture relationships are evidence-backed graph facts: they need stable keys, edge kinds, endpoint stable keys, directness, knowledge classification, confidence, unknown-state data, deterministic metadata JSON, primary evidence references, and fingerprints. A plain Neo4j relationship can hold properties, but it cannot itself link to evidence as a first-class graph record. The relationship-node pattern gives each edge the same durable identity and evidence model as other Archon facts.

`Neo4jSnapshotPersistenceMapper` now maps `ArchitectureEdge` into relationship-node parameters. The mapper preserves snapshot scope, edge stable key, `edgeKind`, source and target node stable keys, `isDirect`, knowledge kind, confidence, unknown-state fields, primary evidence stable key, canonical metadata JSON, and fingerprint as first-class Cypher parameters. The writer uses those parameters to merge `ArchonRelationship` nodes by `(snapshotStableKey, stableKey)`, which allows multiple relationship facts between the same source and target when the stable key or edge kind differs.

`Neo4jArchitectureSnapshotWriter` now validates edge references before opening the write transaction. Relationship records must share the snapshot header stable key, source node stable keys must exist in the snapshot node section, target node stable keys must exist in the snapshot node section, and primary edge evidence must refer to supplied evidence. Missing references return explicit error codes: `MissingRelationshipSourceNodeReference`, `MissingRelationshipTargetNodeReference`, and `MissingRelationshipEvidenceReference`. This preserves the Work Item 4 rule that the writer must not silently drop unsupported or dangling graph facts.

The transactional write order is now repository, solution, snapshot header, architecture nodes, canonical evidence, architecture relationship nodes, snapshot-to-solution relationships, node-to-evidence relationships, relationship endpoint links, and relationship-to-evidence links. Endpoint links use stable relationship type names from `Neo4jSchemaNames`: `RELATIONSHIP_SOURCE` connects the relationship node to its source architecture node, and `RELATIONSHIP_TARGET` connects it to its target architecture node. Edge evidence uses the existing `SUPPORTED_BY_EVIDENCE` relationship from the `ArchonRelationship` node to the canonical `ArchonEvidence` node. This makes traversal explicit: a query can move from a relationship fact to its source, target, and evidence without reading Neo4j internal IDs or inferring evidence from metadata.

## Work Item 6 - Rules and Findings Persistence Slice

Work Item 6 extends snapshot persistence from structural architecture facts into versioned rule and finding history. A **rule catalog entry** is a global `RuleDefinition` record identified by rule code plus rule version. It is global because a rule version should not be copied once per snapshot; the same rule version can classify findings across many snapshots while remaining one durable catalog node. A **finding** is a snapshot-scoped concern produced by, or otherwise classified against, a rule version. Findings keep their own stable keys and fingerprints so later hotlist, suppression, query, MCP, markdown, and historical comparison packages can reason about a concern without depending on Neo4j internal IDs.

The application snapshot contract now includes a `Rules` section alongside repositories, solutions, nodes, edges, evidence, findings, metrics, summaries, warnings, and errors. `ArchitectureSnapshotAccumulator` can add and merge rule definitions by rule code plus version, then emits them in deterministic order. This keeps rule catalog contribution in the application layer and avoids introducing disk-backed rule loading or rule evaluation in WP003. Work Item 6 persists rule contracts supplied to the writer; it does not decide how those rules are discovered or executed.

`Neo4jSnapshotPersistenceMapper` now maps `RuleDefinition` and `FindingRecord` instances into Neo4j parameters. Rule mapping preserves `ruleCode`, `ruleVersion`, name, category, default severity, default status, enabled state, description, serialized definition JSON, source URL JSON, built-in flag, owner scope, and deterministic metadata JSON. Finding mapping preserves snapshot scope, stable key, rule code, rule version, severity, status, title, description, knowledge kind, confidence, unknown-state fields, primary node stable key, primary evidence stable key, first-seen and latest-seen snapshot stable keys, suppression reason, suppressed-by actor, metadata JSON, and fingerprint.

The writer validates findings before opening a transaction. Each finding must share the snapshot header stable key, reference a supplied rule code and version, reference an existing primary node when a primary node is supplied, and reference supplied evidence when primary evidence is supplied. Missing references return explicit safe error codes: `MissingFindingRuleReference`, `MissingFindingNodeReference`, and `MissingFindingEvidenceReference`. This keeps Work Item 6 aligned with earlier persistence slices: dangling graph facts are rejected rather than silently persisted with broken links or incomplete support paths.

The transactional write order now adds rules and findings after architecture relationship nodes and before support links are created. Rules are merged as `ArchonRule` nodes by `(ruleCode, ruleVersion)`, which allows multiple versions of the same rule code to coexist. Findings are merged as `ArchonFinding` nodes by `(snapshotStableKey, stableKey)`. Each finding then receives a `CLASSIFIED_BY_RULE` relationship to the matching rule version, an optional `PRIMARY_NODE` relationship to the primary architecture node, and an optional `SUPPORTED_BY_EVIDENCE` relationship to canonical evidence. Finding evidence uses the same per-snapshot canonical evidence remapping as node and relationship evidence, so duplicate evidence payloads do not create duplicate evidence nodes just because a finding references them.

`SnapshotPersistenceCounts` now reports rule and finding counts in application terms: rules upserted, findings persisted, finding-to-rule relationships, finding-to-primary-node relationships, and finding-to-evidence relationships. These counts intentionally describe what the writer attempted in the domain model rather than exposing Neo4j driver summaries or internal database IDs.

## Work Item 7 - Metrics and Generated Summaries Persistence Slice

Work Item 7 completes the WP003 writer path for snapshot-scoped computed data and durable narrative output. A **metric** is a first-class `MetricRecord` that stores a computed value for a graph, snapshot, project, node, relationship, or modernization scope. A **generated summary** is a first-class `GeneratedSummary` that stores generated narrative content for a snapshot or target graph record. Persisting these records matters because later diff, API, MCP, markdown, reporting, and hotlist work can retrieve stable metric and summary records rather than recomputing metrics or regenerating summaries during every read.

`Neo4jSnapshotPersistenceMapper` now maps metrics and generated summaries into Neo4j parameter dictionaries. Metric mapping preserves snapshot scope, stable key, metric kind, scope kind, optional node target stable key, optional relationship target stable key, optional primary evidence stable key, name, numeric value, text value, unit, deterministic metadata JSON, and fingerprint. Generated-summary mapping preserves snapshot scope, stable key, summary kind, optional target stable key, format, title, content, deterministic metadata JSON, and fingerprint. These query-critical fields remain first-class properties rather than being hidden inside metadata JSON so later query and diff packages can filter, compare, and traverse without parsing extension data.

`Neo4jArchitectureSnapshotWriter` now validates Work Item 7 references before opening the write transaction. Metric records must share the snapshot header stable key, may only reference supplied architecture nodes, may only reference supplied architecture relationship nodes, and may only reference supplied evidence. Generated summaries must share the snapshot header stable key and, when a target stable key is supplied, that target must be the snapshot itself, a supplied architecture node, or a supplied architecture relationship. Missing references return explicit safe error codes: `MissingMetricNodeReference`, `MissingMetricRelationshipReference`, `MissingMetricEvidenceReference`, and `MissingGeneratedSummaryTargetReference`.

The transactional write order now adds `ArchonMetric` and `ArchonGeneratedSummary` nodes after findings and before Work Item 7 support links. Metrics merge by `(snapshotStableKey, stableKey)` and persist target/evidence stable keys as properties. A metric can receive `SUPPORTED_BY_EVIDENCE` to canonical evidence, `PRIMARY_NODE` to a target architecture node, and `PRIMARY_RELATIONSHIP` to a target `ArchonRelationship` node. Generated summaries merge by `(snapshotStableKey, stableKey)`, receive `SUMMARIZES_SNAPSHOT` to the owning `ArchonSnapshot`, and can receive `PRIMARY_NODE` or `PRIMARY_RELATIONSHIP` to the target graph record. The target links intentionally use stable graph relationships rather than Neo4j internal IDs, and metric evidence uses the same per-snapshot canonical evidence remapping used by nodes, relationships, and findings.

`SnapshotPersistenceCounts` now reports metric and summary counts in application terms: metrics, metric-to-evidence relationships, metric-to-target relationships, generated summaries, generated-summary-to-snapshot relationships, and generated-summary-to-target relationships. The counts remain independent of Neo4j driver summary objects and preserve the existing behavior that failed persistence returns empty counts.

## Work Item 8 - Full Mixed Snapshot Validation and Host Composition Slice

## Work Item 9 - Documentation, Implementation Record, and Final Wiki Review Gate

Work Item 9 closes WP003 by turning the per-slice implementation notes into a consolidated current-state record. No product behavior or source code was changed for this work item. The completed persistence foundation now consists of validated Neo4j configuration, dependency-injection owned driver lifecycle, a credential-safe health probe, idempotent schema initialization, explicitly guarded local/test graph recreation, and complete snapshot persistence for repositories, solutions, snapshot headers, architecture nodes, architecture relationship records, evidence, versioned rule catalog entries, findings, metrics, and generated summaries.

The core design decision is that Archon persists architecture knowledge as stable graph facts rather than as database-generated records. A stable key is the logical identity for a graph fact, and a fingerprint is the deterministic diff-relevant hash for that fact's content. Neo4j internal IDs are intentionally absent from application contracts, persistence results, tests, wiki examples, and implementation notes. Repository, solution, and snapshot nodes use globally unique stable keys, while architecture nodes, architecture relationship nodes, evidence, findings, metrics, and generated summaries use snapshot-scoped identity. Rule catalog entries are the exception because they are global versioned definitions identified by rule code plus rule version.

The initialized Neo4j labels are `ArchonRepository`, `ArchonSolution`, `ArchonSnapshot`, `ArchonNode`, `ArchonRelationship`, `ArchonEvidence`, `ArchonRule`, `ArchonFinding`, `ArchonMetric`, and `ArchonGeneratedSummary`. Architecture edges use the relationship-node pattern through `ArchonRelationship`: each edge is a node with its own stable key, fingerprint, edge kind, endpoint stable keys, metadata, confidence, unknown-state fields, and evidence link. This trade-off is intentional. Native Neo4j relationships are excellent for traversal, but a native relationship cannot itself point to evidence as a first-class graph record. The relationship-node pattern gives relationship facts the same explainability and stable identity model as nodes, findings, metrics, and summaries.

Stable relationship names are part of the public graph vocabulary for later query, MCP, markdown, diff, and reporting packages. `INCLUDES_SOLUTION` connects snapshots to included solutions. `RELATIONSHIP_SOURCE` and `RELATIONSHIP_TARGET` connect an `ArchonRelationship` node to its source and target `ArchonNode` records. `SUPPORTED_BY_EVIDENCE` connects nodes, relationship nodes, findings, and metrics to canonical evidence. `CLASSIFIED_BY_RULE` connects findings to the exact rule version that classified them. `PRIMARY_NODE` connects findings, metrics, and summaries to a primary architecture node. `PRIMARY_RELATIONSHIP` connects metrics and summaries to a relationship-node target. `SUMMARIZES_SNAPSHOT` connects generated summaries to their owning snapshot. These names are documented in source, tests, this implementation record, and `wiki/home.md` so later work can traverse the graph without inventing parallel vocabulary.

Schema initialization uses stable operational names for constraints and indexes. The uniqueness constraints are `archon_repository_stable_key_unique`, `archon_solution_stable_key_unique`, `archon_snapshot_stable_key_unique`, `archon_node_snapshot_stable_key_unique`, `archon_relationship_snapshot_stable_key_unique`, `archon_evidence_snapshot_stable_key_unique`, `archon_rule_code_version_unique`, `archon_finding_snapshot_stable_key_unique`, `archon_metric_snapshot_stable_key_unique`, and `archon_generated_summary_snapshot_stable_key_unique`. Indexes use the same `archon_` prefix and cover repository association, snapshot scope, status, kind fields, knowledge kind, confidence, rule code, rule category, severity, metric scope, summary kind, and fingerprints where the schema catalog defines those lookup paths. Initialization is idempotent through `CREATE CONSTRAINT ... IF NOT EXISTS` and `CREATE INDEX ... IF NOT EXISTS` statements, so tests and future startup checks can safely re-run it.

Snapshot persistence has one coordinated ordering: validate the snapshot in application terms, initialize schema, canonicalize evidence, then write repositories, solutions, the snapshot header, architecture nodes, canonical evidence, architecture relationship nodes, rule catalog entries, findings, metrics, generated summaries, and finally support relationships. The support-link phase depends on the earlier record phase so references are present before traversable relationships are created. The writer rejects missing repository, solution, node, relationship, evidence, rule, metric, and generated-summary references with explicit safe error codes rather than silently dropping records or creating dangling paths.

Evidence deduplication remains scoped to one snapshot. Equivalent evidence payloads in a single snapshot collapse to one canonical `ArchonEvidence` node, and references from nodes, relationship nodes, findings, and metrics are remapped to that canonical stable key. The snapshot stable key is part of the deduplication identity, so equivalent evidence from different snapshots remains separate. This preserves historical isolation while avoiding duplicate evidence records inside one snapshot.

Graph recreation remains deliberately destructive and deliberately narrow. `GraphRecreationRequest` requires the exact confirmation phrase `DELETE ARCHON GRAPH DATA AND RECREATE SCHEMA`; unauthorized requests return a safe application error before any write session opens. Authorized recreation deletes only nodes carrying Archon-owned labels from the closed schema catalog and then invokes the same idempotent initializer. No production API endpoint, health check, startup hook, query API, MCP tool, or snapshot writer invokes recreation.

Testcontainers behavior is consistent across the Neo4j integration tests. The tests start short-lived Neo4j Docker containers under test control, use the same infrastructure services as the implementation, and do not start the Aspire AppHost. This gives the health, schema, recreation, snapshot, relationship, rule/finding, metric/summary, and full mixed validation slices a real Neo4j database while avoiding a blocking local distributed-app process during automated validation.
